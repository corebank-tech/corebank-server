# DB 데이터 마이그레이션 및 시딩 가이드라인

본 문서는 Flyway 마이그레이션 스크립트(`V__`, `R__`)와 시딩 데이터(`seed`) 파일의 파일명 규칙, 역할, 그리고 배포 환경에 따른 분리 기준에 집중한 가이드라인입니다.

## 1. V__ (Versioned) 파일: 스키마 및 일회성 데이터 변경
* **목적**: 테이블 생성, 컬럼 변경 등 **DB 스키마 구조(DDL)** 변경과 과거 이력이 보존되어야 하는 데이터(예: 약관)의 **초기화 및 일회성 보정(DML)**
* **파일명 규칙**: **`V{yyyyMMddHHmm}__{설명}.sql`** (예: `V202608051430__add_account_nickname.sql`, `V202608061441__insert_terms_v1_0.sql`)
  * V1, V2와 같은 순번은 동시 개발 시 충돌하므로 반드시 **타임스탬프** 방식을 사용합니다.
* **실행 환경**: `local`, `test`, `prod` 등 **모든 환경**
* **주의사항**:
  * 한 번 적용된 `V__` 파일은 **절대 수정해서는 안 됩니다.** (수정 시 마이그레이션 체크섬 불일치로 부팅 실패)
  * 테스트용 더미 데이터나 초기 시드 데이터를 `V__` 파일에 `INSERT` 하지 마세요. 데이터 수정 시 파일을 건드릴 수 없어 관리가 어렵고, 운영(`prod`) 환경에 불필요한 데이터가 유입될 위험이 큽니다.

## 2. R__ (Repeatable) 파일: 재실행 가능한 기준 데이터
* **목적**: 시스템 구동 및 운영에 필수적이며 과거 이력 보존이 필요 없는 **교체 가능한 마스터 데이터**(예: 공통 코드, 단순 상품 마스터 등) 시딩
* **파일명 규칙**: **`R__{설명}.sql`** (예: `R__system_common_codes.sql`, `R__seed_master_data.sql`)
* **실행 환경**: `local`, `test`, `prod` 등 **모든 환경**
* **주의사항**:
  * 운영(`prod`) 환경에도 반드시 존재해야 하는 데이터만 작성합니다.
  * 파일이 변경되면 전체가 재실행되므로, 약관(terms)과 같이 버전 이력이 중요한 데이터나 보안상 분리되어야 하는 관리자 계정 등은 V 스크립트나 별도 부트스트랩을 사용해야 합니다.
  * 중복 실행 에러 방지를 위해 단순 `INSERT` 대신 **`INSERT INTO ... ON DUPLICATE KEY UPDATE`** 구문으로 작성합니다.

## 3. local-demo-data.sql: 로컬/배포 QA 전용 더미 데이터
* **위치**: `src/main/resources/db/seed/local-demo-data.sql` (Flyway 마이그레이션 경로 밖)
* **목적**: 로컬 기능 테스트 및 시연용으로 필요한 **가짜/더미 데이터**(예: 테스트용 '홍길동' 고객 계정, 임의의 거래 내역 등) 시딩
* **실행 환경**: `local` 또는 명시적인 `qa-seed` 프로필이 활성화된 환경
  * 로컬 개발은 `local`을 사용합니다.
  * 팀 QA 배포는 `prod,qa-seed`를 사용하여 운영 RDS에 QA 데이터를 적재합니다.
  * `prod` 단독 실행에서는 더미 데이터를 적재하지 않습니다.
* **주의사항**:
  * Flyway가 자동으로 읽어가는 `db/migration/` 폴더에 넣지 마십시오.
  * `qa-seed`는 QA용 더미 데이터가 상주해도 되는 배포 환경에서만 활성화합니다.
  * 배포 QA 계정과 4자리 계좌비밀번호는 공개 저장소의 고정 해시를 사용하는 공개 픽스처입니다. 실제 개인정보·자금·운영 자격증명으로 사용하지 않으며 로그인 비밀번호는 팀 내부 채널로만 공유합니다.
  * 세 계정을 팀원이 공유하므로 로그인·계좌비밀번호를 반복해서 틀리거나 별칭·표시순서를 변경하면 다른 팀원의 QA에도 영향을 줍니다.
  * 로컬은 개발 편의를 위해 개별 SQL 오류 후 계속 진행하지만, `qa-seed`는 부분 적재를 숨기지 않도록 첫 오류에서 애플리케이션 기동을 실패시킵니다.
  * 배포는 애플리케이션 healthcheck와 SSM 실행 결과를 확인하므로 시드 오류나 기동 실패가 발생하면 GitHub Actions 배포 Job도 실패합니다.
  * 재배포 시 고객의 비밀번호·개인정보·로그인 이력은 덮어쓰지 않고, 정확히 일치하는 QA 시드 계정의 로그인 잠금만 해제합니다.
  * 정확한 QA 시드 소유자가 일치하는 계좌는 잔액·상태·출금계좌 등록·계좌비밀번호 잠금·별칭을 초기값으로 복구합니다. 타인 소유 계좌번호와 충돌하면 해당 계좌는 변경하지 않고 적재 검증에서 기동을 실패시킵니다.
  * 현재 시드에는 `ledger_entry`가 없으므로 초기 잔액에 대응하는 과거 거래내역은 제공하지 않습니다. 거래내역 픽스처가 필요하면 별도 이슈로 추가합니다.
