## 2026-10-01 — 개선 전 베이스라인

```
환경: 운영 ALB 경유 EC2 1대(t3.small, 2 vCPU) · RDS(MySQL) / 부하 생성: 별도 리눅스 서버(4코어 8GB)
데이터: PH-60 시드 (고객 1만 · 계좌 3만 · 이체 23.5만 · 원장 50만)
일시: 2026-10-01 17:21~18:10 KST
조건: load.js 기본값 — 3분간 초당 이체 시도 5 → 60건(iteration/s, 요청으로는 ×4), 세션 풀 20, 건당 19,876원
```

`harness.md` §2-1 의 「공식 수치는 `POST /transfers` 구간만」은 지연뿐 아니라 **처리량에도 적용된다.**

한도 경로(`checkAndReserve`) 분리 측정은 Micrometer Timer 적용 후로 미룬다 — [#532](https://github.com/corebank-tech/corebank-server/issues/532) 로 분리했고 선행은 [#531](https://github.com/corebank-tech/corebank-server/issues/531) 이다.

**정합성 (`integrity.js`, 동일 계좌 100건 동시) — 조건부 합격**

> ⚠️ **아래 판정은 재실행이 필요하다.** `verify_integrity.sql` 의 원장 짝 쿼리가 `INNER JOIN` 이라
> **「성공인데 원장이 0행」인 이체를 조인 단계에서 잃어버린다**(PR #530 리뷰 지적, MySQL 8.4 에서 재현 확인).
> 한도 쿼리도 usage 행이 없는 고객을 놓친다. 즉 `0건 어긋남` 은 **그 유형을 검사하지 않은 0** 이다.
> 쿼리를 고친 뒤 같은 데이터에 다시 돌려 이 절을 갱신한다 — 데이터는 남아 있어 재측정은 필요 없다.

| 항목 | 값 | 기준 | 판정 |
|---|---|---|---|
| 잔액 오차 | **0원** (99,960,617 → 97,973,017, 차이 1,987,600 = 19,876 × 100) | 0 | ✅ |
| 데드락 | 발생 없음 | 기록 | — (기록 항목) |
| 원장 짝 무결성 | **0건 어긋남** (`broken_ledger_pairs=0`) | 100% | ⚠️ 쿼리 보정 후 재실행 |
| 한도 적립 합 일치 | **0건 어긋남** (`limit_usage_mismatches=0`) | 일치 | ⚠️ 쿼리 보정 후 재실행 |
| 잔액-원장 대조 (DB) | **0건 어긋남** (`balance_mismatches=0`) | 0 | ✅ |

`verify_integrity.sql` 을 운영 RDS 에서 실행한 결과다.

| | |
|---|---|
| 실행 시점 | **2026-10-01 20:37 KST** — 부하 4회·정합성 모두 종료 후 |
| 집계 범위 | `@from_at` · `@to_at` 을 **기본값 그대로** 둬서 `2026-10-01 00:00 ~ 10-02 00:00` **전일**이다 |

따라서 아래 건수는 17:21~18:10 한 구간이 아니라 **그날 harness 가 만든 전부**다 — 부하 4회 + 중단된 1회 + 정합성 100건 + 스모크. **총 이체 1,671건 / 성공 1,500건 / 실패 171건 / 성공 금액 36,578,063원.**

k6 가 센 이체 성공 수로 설명되는 몫은 **1,292건**이다 — 완주 4회 1,015(217·254·274·270) + 중단 회차 152 + 정합성 100 + 스모크·디버깅 25. **나머지 208건은 이 기록으로 설명하지 못한다.** 같은 날 다른 트랙이 운영에서 이체를 돌렸거나, 전사에 출력이 안 남은 초기 시행이 있었을 것으로 보이지만 **확인하지 않았다.**

설명 못 한 208건이 남아도 결론은 바뀌지 않는다. **22.70/s 이 이체 처리량이었다면 완주 4회만으로 17,352건이 남았어야 한다.** 실제는 전일 전체가 1,671건이다 — 10배 규모가 다르다.

**요청의 절반이 커넥션을 못 받아 실패하는 상황에서도, 잔액은 1원도 틀리지 않았다.** 동일 계좌 100건 동시에서 잔액 차가 정확히 19,876 × 100 이었고, 잔액-원장 대조도 0건 어긋남이었다. 이 둘은 쿼리 보정과 무관하게 성립한다 — 잔액 쪽은 `INNER JOIN` 결함의 영향을 받지 않는다.

**성능 한계와 정합성은 분리돼 있다.** 서버는 느려지고 거절했지만, 받아들인 건의 잔액은 어긋나지 않았다. 「성공 응답이 나갔는데 원장이 안 맞는」 결함이 **정말로 0건인지는 원장·한도 쿼리를 고쳐 다시 확인한다.**

### 한계점과 원인

**이 서버는 초당 2.5건의 이체만 접수하고 그중 1.4건만 성공시킨다. 병목은 이체 로직이 아니라 DB 커넥션 풀이다.**

목표 도착률 60건에 iteration 처리량이 22.7건에서 멈췄고, 1,182건은 시작조차 못 했다(dropped). **완주한 iteration 조차 89% 는 토큰 발급 단계에서 떨어져 이체를 호출하지 못했다.** 그 지점의 서버 로그가 원인을 직접 가리킨다.

```
HikariPool-1 - Connection is not available, request timed out after 3002ms
(total=10, active=10, idle=0, waiting=23)
```

커넥션 10개가 전부 점유된 채 23개가 대기하다 3초 타임아웃으로 떨어졌다. 예외는 `SQLTransientConnectionException` → `JDBCConnectionException` 을 거쳐 `CMN9999`(500)로 나갔다.

증거가 네 겹으로 같은 곳을 가리킨다.

| 출처 | 값 |
|---|---|
| 설정 | `maximum-pool-size: 10` · `connection-timeout: 3000` |
| 측정 | `http_req_duration` med **4회 모두 3.02초** |
| 서버 로그 | `Connection is not available` **39,594건** (3시간 범위) |
| 자원 | **CPU 0.38%** · 메모리 27% (521MB / 1.86GB) |

**중앙값이 4회 모두 3.02초**로 `connection-timeout: 3000` 에 붙어 있다. 요청의 절반 이상이 커넥션을 기다리다 타임아웃으로 끝났다는 뜻이고, 회차마다 소수점까지 같다는 것은 이 값이 부하의 함수가 아니라 **설정이 만든 상수**임을 말한다.

**자원이 병목이 아니라는 것도 확인했다.** 측정 중 서버는 한 번도 죽지 않았고(`Up 21 hours (healthy)`), CPU 는 0.38%, 메모리는 27% 였다. t3.small 2 vCPU 에서 **자원이 남아도는데 요청의 절반이 실패했다.** 서버가 힘들어서가 아니라 DB 로 가는 통로가 10개뿐이어서다.

**이체 p99(14.82s)가 전체 플로우 p99(8.95s)보다 크다.** 보통은 전체가 4요청 합이라 더 커야 하는데 뒤집혔다. 앞 3단계는 실패하면 3초에 끝나지만, 이체까지 도달한 요청은 커넥션을 더 오래 기다리기 때문이다. 대기가 이체 단계에 몰려 있다.

무너진 순서는 `/otp/issue` 500 → OTP 만료(`OTP0104`, 발급·검증 간격 180초 초과) → `/accounts/{id}/password/verify` 500 → OTP 발급 락 5초 대기 실패(`CMN0303`) 였다. 전부 커넥션을 못 받아 생긴 2차 증상이다.

**설정은 `application-prod.yml`(P4 `astrokan`, `d6ff9f9f`)의 `maximum-pool-size: 10` · `connection-timeout: 3000` 이다.**

**timeout 을 늘리는 것은 대책이 아니다.** 커넥션 수가 그대로면 처리량은 변하지 않고 실패를 늦게 알릴 뿐이며, 스레드가 더 오래 묶여 전체가 느려진다. 풀 크기를 올리는 쪽이 직접적이되 RDS `max_connections` 한도 안에서 WAS 대수를 곱해 계산해야 한다.

### 다른 트랙에 미치는 영향

**P4 LOCK-TUNE(S3)은 현재 상태로 측정이 불가능하다.** 요청이 이체 로직에 도달하기 전에 커넥션을 못 받고 떨어지므로, 락을 개선해도 수치가 움직이지 않는다. 풀을 먼저 조정해야 락 튜닝의 효과를 잴 수 있다.

### 재측정 방법

S4 재측정은 같은 harness·같은 구간으로 **4회 완주**하고 중앙값을 비교한다. 비교 대상은 `이체 접수 2.50/s` · `이체 성공 1.37/s` · `이체 도달률 11.0%` · `에러율 51.5%` · `이체 p99 14.82s` 다. **`iterations/s` 는 비교 대상이 아니다** — 어느 단계에서 떨어졌는지를 감춘다.

p99 를 얻으려면 요약 옵션이 필요하다. 기본 출력에는 p90·p95 까지만 나온다.

```bash
k6 run -e BASE_URL=https://<측정 대상>/api/v1 \
  --summary-trend-stats="avg,min,med,p(90),p(95),p(99),max" perf/k6/load.js
```
