### 한계점과 원인

**이 서버의 이체 처리 한계는 초당 약 23건이고, 병목은 이체 로직이 아니라 DB 커넥션 풀이다.**

목표 도착률 60건에 실제 처리량이 22.7건에서 멈췄고, 1,182건은 시작조차 못 했다(dropped). 그 지점의 서버 로그가 원인을 직접 가리킨다.

```
HikariPool-1 - Connection is not available, request timed out after 3002ms
(total=10, active=10, idle=0, waiting=23)
```

커넥션 10개가 전부 점유된 채 23개가 대기하다 3초 타임아웃으로 떨어졌다. 예외는 `SQLTransientConnectionException` → `JDBCConnectionException` 을 거쳐 `CMN9999`(500)로 나갔다.

증거가 네 겹으로 같은 곳을 가리킨다.

| 출처 | 값 |
|---|---|
| 설정 | `maximum-pool-size: 10` · `connection-timeout: 3000` |
| 측정 | `http_req_duration` med **4회 모두 3.02초** |
| 서버 로그 | `Connection is not available` **39,594건** (3시간 범위) |
| 자원 | **CPU 0.38%** · 메모리 27% (521MB / 1.86GB) |

**중앙값이 4회 모두 3.02초**로 `connection-timeout: 3000` 에 붙어 있다. 요청의 절반 이상이 커넥션을 기다리다 타임아웃으로 끝났다는 뜻이고, 회차마다 소수점까지 같다는 것은 이 값이 부하의 함수가 아니라 **설정이 만든 상수**임을 말한다.

**자원이 병목이 아니라는 것도 확인했다.** 측정 중 서버는 한 번도 죽지 않았고(`Up 21 hours (healthy)`), CPU 는 0.38%, 메모리는 27% 였다. t3.small 2 vCPU 에서 **자원이 남아도는데 요청의 절반이 실패했다.** 서버가 힘들어서가 아니라 DB 로 가는 통로가 10개뿐이어서다.

**이체 p99(14.82s)가 전체 플로우 p99(8.95s)보다 크다.** 보통은 전체가 4요청 합이라 더 커야 하는데 뒤집혔다. 앞 3단계는 실패하면 3초에 끝나지만, 이체까지 도달한 요청은 커넥션을 더 오래 기다리기 때문이다. 대기가 이체 단계에 몰려 있다.

무너진 순서는 `/otp/issue` 500 → OTP 만료(`OTP0104`, 발급·검증 간격 180초 초과) → `/accounts/{id}/password/verify` 500 → OTP 발급 락 5초 대기 실패(`CMN0303`) 였다. 전부 커넥션을 못 받아 생긴 2차 증상이다.

**설정은 `application-prod.yml`(P4 `astrokan`, `d6ff9f9f`)의 `maximum-pool-size: 10` · `connection-timeout: 3000` 이다.**

**timeout 을 늘리는 것은 대책이 아니다.** 커넥션 수가 그대로면 처리량은 변하지 않고 실패를 늦게 알릴 뿐이며, 스레드가 더 오래 묶여 전체가 느려진다. 풀 크기를 올리는 쪽이 직접적이되 RDS `max_connections` 한도 안에서 WAS 대수를 곱해 계산해야 한다.

### 다른 트랙에 미치는 영향

**P4 LOCK-TUNE(S3)은 현재 상태로 측정이 불가능하다.** 요청이 이체 로직에 도달하기 전에 커넥션을 못 받고 떨어지므로, 락을 개선해도 수치가 움직이지 않는다. 풀을 먼저 조정해야 락 튜닝의 효과를 잴 수 있다.

### 재측정 방법

S4 재측정은 같은 harness·같은 구간으로 **4회 완주**하고 중앙값을 비교한다. 비교 대상은 `22.70 TPS` · `에러율 51.5%` · `이체 p99 14.82s` 다.

p99 를 얻으려면 요약 옵션이 필요하다. 기본 출력에는 p90·p95 까지만 나온다.

```bash
k6 run --summary-trend-stats="avg,min,med,p(90),p(95),p(99),max" perf/k6/load.js
```
