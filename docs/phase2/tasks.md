# 2차 태스크 레지스트리

> **이 파일이 정본인 것** — 2차 태스크 하나하나의 소유자·스프린트·인일·선행·기한·범위·완료 기준·트랙 간 계약(인터페이스 시그니처, 머지 순서, 출력값).
> **정본이 아닌 것** — 공통 규칙·달력·지표·범위 밖·결정 이력은 [README.md](README.md), 용어 이름은 [glossary.md](glossary.md).

**코드 현황 기준:** `dev` `5f41d5ce` (2026-09-23). 각 절의 "현황" 줄은 이 시점 실측이다.

## 사용 규칙

- **태스크 ID는 바꾸지 않는다.** `PH-xx`는 기획 번호이고, FE는 화면 ID(`B-9`, `C-1`, `ADM-04` …)를 쓴다. 쪼갠 태스크는 `-①`·`-②`를 붙인다.
- **한 사실은 한 곳에만 적는다.** 소유자·인일·기한은 §1 표에만 둔다. §2 상세 절은 범위·계약·완료 기준만 적는다.
- **태스크를 끝내는 PR에서 이 파일도 함께 고친다.** §1 표의 상태 칸과 §2의 "현황" 줄이 대상이다. 인일이나 스프린트를 바꾸면 [README.md §4](README.md#4-트랙과-인일)의 합계도 같은 PR에서 고친다.
- **소유자 = 구현하고 머지 책임을 지는 사람.** 다른 트랙이 쓰는 인터페이스는 제공 태스크 절에 시그니처를 적는다. 쓰는 쪽은 그 절을 링크만 한다.
- 담당 표기: P1 주유나 `YounaJ00` · P2 정선우 `vsopsw` · P3 김다연 `danhandev`(기획 리드) · P4 이건 `astrokan` · P5 류재성 `bprosefan` · P6 장영훈 `cy389`

상태 값 — `완료` · `진행`(PR 열림 또는 착수) · `예정` · `조건부`(선행이나 여유가 생겨야 착수) · `대체`(결정으로 다른 태스크가 대신한다. 인일은 대신하는 태스크로 넘어간다).

### PH-32. 도메인 이벤트 발행 골격

- 이벤트 클래스 — `TransferCompleted(transactionNumber, sourceType, amount, fromAccountId, toAccountId, occurredAt)` · `TransferFailed(...)` · `SubscriptionOpened(...)` · `AccountMatured(...)`. (#505에서 이체는 `TransferSettled` 하나로 합쳤다 — 성공·실패는 `status`, 이체 종류는 `txType`.) `AccountMatured`는 PH-15(#671)에서 `account.api` 타입 정의 및 `ACTIVE → MATURED` 전이 시 발행하며, 2차에는 소비하지 않는다. `refId`는 `accountId`이고, 현재 `notification.ref_id` 유형에는 해당하지 않는다(P1 협의).
- `@TransactionalEventListener(phase = BEFORE_COMMIT)` 리스너 자리와 **JdbcTemplate INSERT 규약**을 문서로 남긴다. 규칙은 [README §3-3](README.md#3-3-이벤트아웃박스)을 따른다.
- `publishEvent` 자리와 페이로드는 P4와 합의한다. 자리 표시는 PH-99(10/2)가 하고, 두 줄은 EVT-2(10/6)가 넣는다.
- 테스트: BEFORE_COMMIT 리스너 INSERT가 커밋에 실리는지 통합 테스트(PH-99 골격 위), 리스너 예외 시 롤백을 테스트로 고정.
- **완료 기준:** 롤백되면 이벤트가 발행되지 않는다. 리스너 INSERT가 커밋된다.
- **현황:** #436 완료 (PR #505) — 이체 발행을 엔진 한 곳으로 모았고 EVT-2 를 대신한다.

> 10/19 [ADR-0010](../adr/0010-outbox-spring-modulith-event-publication-registry.md)로 구현 방법을 바꿨다. `outbox` 테이블을 직접 만들지 않고 Spring Modulith Event Publication Registry를 쓴다.

- `EVENT_PUBLICATION` 테이블(Flyway + `schema_reference.md` + ERD) — 업무와 같은 커밋에 AFTER_COMMIT 리스너마다 1행이 남는다.
- 리스너가 성공하면 행을 지운다(`completion-mode=delete`). **남은 행 = 아직 전달되지 않은 이벤트**다.
- 재전달은 재제출 API로 한다(At-Least-Once). 멱등은 구독 측(②)에서 잡는다.
- **현황:** #437 완료 (PR #703) — 개선 전 · 후 수치는 [ADR-0010 §검증](../adr/0010-outbox-spring-modulith-event-publication-registry.md#검증).

**②**

- 즉시 · 타행이체는 [PH-01](#ph-01-알림-도메인-인수--영속성) #706에 함께 들어간다. 예약 · 자동이체 회차 #707 · 상품가입 #708 · 구독 실패 처리 #709. #393~#396을 현재 아웃박스 설계(PR #703) 기준으로 다시 쓴 이슈다.
- **알림 문구는 업무 도메인이 만들고, notification은 최소 계약으로 받는다(10/26, PR #723 리뷰 A안 · [ADR-0010](../adr/0010-outbox-spring-modulith-event-publication-registry.md) 「알림 최소 계약」).** 업무 이벤트가 `notification.api.NotificationRequestCarrier`를 구현해 완성된 `NotificationRequest`를 싣고, AFTER_COMMIT 리스너 `NotificationRequestedListener` 하나가 받는다. 업무 · 채널이 늘어도 notification의 알림함 저장 코드는 바뀌지 않는다.
- 두 번째 수신은 no-op이고, 알림 실패는 이체에 영향을 주지 않는다.
- **멱등 키는 업무 키 `(type, ref_id)`다.** `uk_noti_type_ref`가 두 번째 행을 막는다. 발행 기록은 지워지고 구독자는 그 ID를 받지 않는다.
- **예약 · 자동이체 알림은 배치 이벤트로만 싣는다(10/22 결정).** 배치가 결과마다 발행해 `notification.ref_id` 규약(예약 → `scheduled_transfer_id`, 자동 → `execution_id`)을 지킨다. 엔진은 예약 · 자동이체의 `TransferSettled`(`refId = transfer_id`)를 발행하지 않는다 — 알림 이벤트는 알림이 필수값이다(#706 · PR #723 리뷰 A안, PR #738 리뷰).
- auth `LoginPasswordChangedSessionListener`는 #641(PH-49c)에서 BEFORE_COMMIT으로 바뀌어 발행 기록 대상이 아니다. 재제출은 다른 WAS의 메모리 세션까지 끊는 복구 수단이 아니다([ADR-0010](../adr/0010-outbox-spring-modulith-event-publication-registry.md) 결과).
- **현황:** #706 완료(알림 도메인 · 최소 계약 · 리스너 1개 · 즉시 · 타행이체 알림 · `uk_noti_type_ref`). #707 PR #738(예약 · 자동이체 이벤트가 같은 계약으로 알림을 싣는다, 실패 사유는 `TransferResult.customerFailureReason()`). #708 · #709 남음.

실패 처리는 「즉시 재시도 → 주기 재제출 → 상한 초과는 포기 · 알림 → 수동 재처리」 순이고, 단계마다 프레임워크 기능을 쓴다.

| 단계 | 쓰는 기능 | 손으로 짜나? |
|---|---|---|
| 구독 실행 | `@ApplicationModuleListener` — 비동기 · `REQUIRES_NEW` · AFTER_COMMIT | ❌ |
| 즉시 재시도 | `@Retryable` + `@EnableResilientMethods`(Spring Framework 7) | ❌ 설정값만 |
| 주기 재제출 | `IncompleteEventPublications.resubmitIncompletePublications(ResubmissionOptions)` — 재제출 횟수(`completionAttempts`)가 상한을 넘은 건은 필터로 빼서 포기한다(행은 남는다) | 스케줄 메서드 1개 |
| 재기동 후 전달 | `republish-outstanding-events-on-restart`와 주기 재제출 중 하나 — 다중 인스턴스 중복을 보고 고른다 | ❌ |
| 멈춘 발행 정리 | `spring.modulith.events.staleness.*` — `PUBLISHED` · `PROCESSING` · `RESUBMITTED`에서 오래 멈춘 발행(처리 중 프로세스가 죽은 건 등)을 `FAILED`로 바꿔 재제출 대상에 넣는다 | ❌ 설정값만 |
| 포기 건 알림 | 재제출 횟수가 상한을 넘은 건수를 ERROR 로그와 지표로 | 조회 1개 |
| 수동 재처리 | `FailedEventPublications.resubmit(ResubmissionOptions)` — 원인을 고친 뒤 운영자가 `FAILED` 건을 다시 보낸다 | 호출 1줄 |

**완료 기준:** 발행 직후 프로세스를 죽여도 재기동 후 전달된다. 알림 유형 4종마다 결과 1건에 알림 1건이 생긴다. 중복 발행해도 1건이다.

### PH-103. 알림 최소 계약 — 문구는 각 도메인이 만든다

**PR #723 리뷰(rookedsysc) 채택분이고 PH-102의 선행이다.** S4 BE 코드 예외는 [D-33](README.md#d-33--1026--p1)이다.

| 항목 | 결정 |
|---|---|
| 계약 | 공통 payload(`customerId` · `type` · `refId` · `title` · `content` · `occurredAt`). 채널 · 예약 발송 · 우선순위는 요구가 생길 때 추가 |
| 문구 · 마스킹 · 오류코드 → 고객 문구 | 각 업무 도메인. notification의 오류코드 문자열 복제(AGENTS §3-2)가 사라진다 |
| notification | 유스케이스 하나(`createNotification`)로 저장 · 중복 방지 · 채널 전달만 |
| 채택하지 않음 | Inbox 테이블 · worker — Modulith 발행 기록이 리스너별 재시도를 이미 맡는다([ADR-0010](../adr/0010-outbox-spring-modulith-event-publication-registry.md)) |
| 합의 | 이벤트 4종의 소유자 — `transfer.api` P4 · `scheduledtransfer.api` · `autotransfer.api` P5 · `subscription.api` P3. 발행부 수정은 착수 전에 각 소유자에게 알린 뒤 P1이 하고, 소유자는 PR 리뷰를 맡는다 |

**완료 기준:** notification에 다른 도메인 오류코드 문자열이 없다. 새 업무 알림을 추가할 때 notification 유스케이스를 고치지 않는다. ADR-0010에 「알림 최소 계약」 절이 있다.

### PH-102. 알림 이메일 채널 (① 구현 → ② 운영 SMTP)

**이후 AI agent를 붙이려면 외부 채널이 필요해 2차에 넣는다.** S4에 BE 코드가 들어가는 예외는 [D-33](README.md#d-33--1026--p1)이다. [PH-103](#ph-103-알림-최소-계약--문구는-각-도메인이-만든다)(알림 최소 계약) 뒤에 착수한다.

이체 결과 등 알림 이벤트를 알림함과 함께 이메일로도 보낸다. 알림함 저장은 같은 DB INSERT라 실패가 드물지만, 메일은 외부 전송이라 실패 · 중복이 실제로 난다 — PH-96-② 재시도 · 멱등을 외부 채널에서 검증하는 몫이다.

| 항목 | 결정 |
|---|---|
| 전달 | 같은 이벤트를 받는 두 번째 `@ApplicationModuleListener`. Modulith가 리스너마다 발행 기록을 따로 남겨 채널별로 재시도된다([ADR-0010](../adr/0010-outbox-spring-modulith-event-publication-registry.md)) |
| 중복 방지 | 발송 기록 `UNIQUE (type, ref_id)`. 발송 직후 기록 전에 죽으면 1통 더 갈 수 있다 — 최소 1회 전달 |
| 수신자 | `customer.api`에 이메일 조회 메서드 1개 추가 — P1 작업, P6 리뷰. 이메일은 로그 · 이벤트에 남기지 않는다 |
| 개발 · 테스트(①, P1) | Mailpit(가짜 SMTP 서버) — compose 추가는 P5 리뷰 |
| 운영 발송(②, P5) | SMTP 계정 · `SPRING_MAIL_*` 환경변수 · 아웃바운드 587 · compose 리뷰. 발송 수단(SMTP · SES)은 ① 착수 전에 정하고, 계정 신청 같은 대기 작업은 ①과 병행한다. ② 전까지 운영에서 메일 채널은 꺼 둔다 |

**완료 기준:** 메일 채널 on/off 설정이 있고 운영 기본값은 off다. 이체 1건에 메일 1통. 같은 이벤트를 두 번 받아도 1통. 메일 서버가 내려가 있으면 발행 기록이 남고, 다시 올라온 뒤 재제출로 1통 간다.

### FE #136. 관리자 세션 정책 · 로그인 훅 교체

PH-49a-① 문서로 정책을 대신한다. 별도 화면은 없다. FE 로그인 훅을 `/admin/auth/login`으로 바꾸고 30분 만료를 반영한다(FE `requirements-admin.md` REQ-ADM-006·007).

**완료 기준:** 관리자 로그인이 `/admin/auth/login`을 호출하고, 관리자 세션이 30분 무조작 후 만료돼 `/admin/login`으로 이동한다.

### FE C-5. correlation id 헤더 전파

### PH-15. 만기 — 감지 · MATURED 전이 · 원리금 · 만기해지 API

**목적:** COB에서 만기도래 예·적금 계좌를 `MATURED`로 전환하고, 고객 요청 시 원리금을 출금계좌로 지급한 뒤 상품 계좌를 `CLOSED`로 종료한다.

#### 1. 만기 감지 및 상태 전이 (#633)

- `batch.api.CobStep`의 `order=3` 만기 감지 스텝에서 `nextBusinessDay(COB_DATE)`를 기준으로 만기 대상을 조회한다. 체인 순서는 [PH-43](#ph-43-cob-파이프라인) 계약을 따른다.
- `ACTIVE` 예·적금 계좌만 `ACTIVE → MATURED`로 전이한다. `SUSPENDED`·`DORMANT` 계좌는 기존 상태를 유지하며, 정지·휴면 해제 이후 처리 정책은 PH-16에서 확정한다.
- keyset 페이지 조회와 청크별 트랜잭션을 사용한다. 동일 영업일 재실행 시 이미 `MATURED`인 계좌는 중복 전이하지 않는다.
- 실제 상태 전이(`markMatured() == true`)에서만 `AccountMatured` 이벤트를 발행한다. 이벤트는 `account.api`의 `DomainEvent` 구현체이며 `refId=accountId`, `status=SUCCESS`, `errorCode=null`을 사용한다.
- `account_status_history`에 변경 전·후 상태, 계약 만기일, 전이 기준 영업일, 처리 시각, 발생 원인(`COB`)을 기록한다.
- 상태 변경·감사 이력 저장·이벤트 발행은 같은 청크 트랜잭션에서 처리한다. 2차에서는 `AccountMatured` 알림 소비자를 구현하지 않는다.

#### 2. 계좌 조회 및 FE 연동 (#671)

- `GET /api/v1/accounts/{accountId}` 응답에 nullable `maturityDate`를 추가하고, 기존 `status` 필드로 `MATURED` 상태를 반환한다.
- 기존 응답 구조를 유지하는 Expand 방식으로 적용한다.
- FE B-3은 `status`와 `maturityDate`를 이용해 만기 안내를 표시한다. 실제 해지 가능 여부는 서버의 만기해지 검증 결과를 기준으로 판단한다.

#### 3. 고객 만기해지 API (#685)

- **엔드포인트:** `POST /api/v1/accounts/{accountId}/maturity-termination`. 로그인 세션, CSRF, `Idempotency-Key`, `Account-Password-Auth-Token`이 필요하다.
- **인증:** 해지할 상품 계좌의 비밀번호를 `POST /api/v1/accounts/{accountId}/password/verify`로 검증하여 300초 유효한 일회용 인증 토큰을 발급받는다. 고객·계좌에 묶인 토큰을 만기해지 서비스에서 검증·소비한다. OTP는 이번 범위에 포함하지 않는다.
- **사전 조건:** 가입 상태 `SUCCESS`, 고객 소유 예·적금 계좌의 `MATURED` 상태와 `maturity_date <= KST 달력상 현재일`을 확인한다. 가입 당시 지정한 수취 계좌는 본인 소유의 `ACTIVE` 입출금 계좌이며 출금계좌로 등록돼 있어야 한다. 종료 시 상품 계좌를 잠금 조회하여 만기일·상태·잔액 조건을 재검증한다.
- **만기 처리 방식:** `maturity_handling=TRANSFER`만 지원한다. `RENEW`(자동 재예치)는 거부하며 재예치 처리는 후속 작업으로 분리한다.
- **처리 순서:** 영업일 gate 획득 → 사전 검증 → 비밀번호 인증 토큰 검증·소비 → PH-14 `InterestPaymentUseCase.pay()`로 이자 계산·지급 → 상품 계좌의 최신 잔액 조회 → 상품 유형별 원금 정합성 검증 → `LedgerDepositUseCase.transferBetween(..., MATURITY, ...)`로 원리금 전액 이체 → 잠금 후 수취 계좌 재검증 → `MATURITY` GL 기표 → 상품 계좌 잠금 조회 및 잔액 0원 재검증 → `MATURED → CLOSED` 전이 및 감사 이력 저장.
- **원금 계산:** 이자 지급 후 조회한 상품 계좌의 실제 잔액에서 세후이자를 차감하여 원금을 산출한다. 최종 이체금액은 원금과 세후이자의 합계다.
- **정기예금 원금 정합성(#685):** 이자 지급 후 실제 계좌 잔액에서 세후이자를 차감한 원금이 가입 당시 `product_subscription.subscription_amount`와 일치하는지 검증한다. 계약 원금이 누락·비정상적이거나 금액이 불일치하면 이체 전에 `CMN` 내부 정합성 오류로 거부하고 같은 트랜잭션의 이자 지급을 롤백한다.
- **정기적금 원금 정합성(#730):** 정기적금의 `subscription_amount`는 가입 시 약정한 회차별 납입액이므로 누적 원금과 직접 비교하지 않는다. `transfer.api.LedgerPrincipalBalanceQuery`를 통해 실제 원장 순합계(입금 - 출금, `INTEREST` 제외)를 조회한다. 취소정정은 원거래와 반대기표를 함께 합산하여 순효과를 반영한다. 이자 지급 후 상품 계좌 잔액에서 세후이자를 차감한 실제 원금과 원장 누적 원금이 일치하지 않으면 `CMN9999`로 거부한다. 원금 검증은 원리금 이체 전에 수행하며, 실패하면 동일 트랜잭션의 이자 지급·원장·GL·이력도 롤백한다. 원장 조회는 transfer 도메인의 공개 API → application 포트 → persistence 어댑터 구조를 사용한다.
- **원장 계약:** PH-99의 `transfer.api.LedgerDepositUseCase`를 사용하며 `LedgerPair`를 직접 생성하지 않는다. 만기해지 원장은 상품 계좌 출금 1행과 고객 계좌 입금 1행, 총 2행이다. 기표·조회 순서는 [transfer_seam.md](transfer_seam.md) §8을 따른다.
- **GL 계약(#714):** `GlTxType.MATURITY`(`MAT`)로 차변 `20100` 예수금과 대변 `20100` 예수금에 원리금 이체금액을 동일하게 기표한다. `referenceKey`와 `tradeDate`는 `transferBetween()` 결과의 `transactionNumber()`·`tradeDate()`를 그대로 사용한다. 세전이자와 원천세는 별도 `INT` 전표에서 처리하며 `MAT` 전표에 중복 기표하지 않는다.
- **트랜잭션:** 이자 지급·원리금 이체·GL 기표·계좌 종료·감사 이력을 동일 트랜잭션에서 처리한다. 금융 처리 실패 시 변경사항을 롤백한다. 계좌비밀번호 토큰 소비는 별도 저장소 정책을 따르므로 실패 후 재인증이 필요할 수 있다.
- **멱등성:** 동일 멱등키·동일 요청의 완료 결과는 최초 응답을 재생한다. 다른 키로 재요청하더라도 계좌 상태와 이자 지급 이력을 이용해 중복 지급을 방지한다.

### PH-14. 이자 지급 · 원천징수

- PH-12 `InterestCalculationUseCase`를 재사용해 `InterestResult(gross, tax, net, appliedRate)`를 얻는다. 계산 정책은 [이자 계산 정책](interest_calculation_policy.md)을 따른다.
- PH-15·PH-16이 재사용할 `subscription.api.InterestPaymentUseCase`를 제공한다. 만기해지는 약정금리·상품 계산 방식을, 중도해지는 중도해지이율·단리를 전달한다.
- `net > 0`이면 PH-99의 `transfer.api.LedgerDepositUseCase.credit(..., INTEREST, ...)`로 상품 계좌에 **세후이자**를 입금한다.
- GL 분개는 `gl.api.JournalPostingUseCase.post(...)`로 직접 기표한다. 원천세가 있으면 `INTEREST` 전표 1건에 4행, 원천세가 0원이면 2행을 남긴다.
  - 차 `50100` 이자비용 `gross` / 대 `20100` 예수금 `gross`
  - 차 `20100` 예수금 `tax` / 대 `20200` 원천세예수금 `tax` (`tax > 0`일 때만)
  - 전표 유형은 `GlTxType.INTEREST`, 전표번호 접두는 `INT`다.
  - `referenceKey`는 원장 `transactionNumber`, `tradeDate`는 원장 반환값을 그대로 사용한다.
  - 확정된 분개 패턴의 정본은 [gl_journal_patterns.md](gl_journal_patterns.md) §3-6이다.
- `gross = 0`이면 원장·GL을 생성하지 않고 지급 이력만 저장한다. 0원 원장·분개 행은 생성하지 않는다.
- 신규 `interest_payment` 테이블에 세전이자·원천세·세후이자·지급 사유·원장 거래번호·거래일·지급 시각을 기록한다.
- `account_id` UNIQUE 제약과 지급 이력 조회를 통해 중복 지급을 차단한다. 중복 지급 오류코드는 `PRD0302`다.
- 지급 서비스는 `@Transactional(MANDATORY)`를 사용한다. PH-15·16의 원리금 이체 및 `CLOSED` 전이와 동일한 트랜잭션에서 원장·GL·이력을 함께 커밋하거나 롤백한다.
- 검증 대상: 정상 지급, 이자 0원, 세금 0원, 중복 지급, 동시 요청, 원장·GL·이력 정합성, 후속 작업 실패 시 전체 롤백.
- **범위 밖:** 비과세·세금우대, 만기해지·중도해지 API 자체, 계좌 `CLOSED` 전이.

### PH-58. 엣지 계층

### PH-21. 전표 기표 구조 · 개시 잔액 · 분개 패턴표

- **정본은 [gl_journal_patterns.md](gl_journal_patterns.md)**(PR #491). 아래는 요약이고, 어긋나면 그 문서를 따른다.
- 전표번호: `yyyyMMdd-TTT-NNNNNN`(19자, `voucher_no VARCHAR(20)`). `yyyyMMdd`는 거래일, `TTT`는 `OPN`·`TRF`·`SUB`·`INT`, `NNNNNN`은 (거래일, 유형)마다 1부터 시작하는 **6자리** 일련번호다. 4자리로는 PH-60b 첫날부터 넘친다. PH-40 전에는 `LocalDate`로 임시 채번한다.
- 전표 단위 차대변 일치 검증(도메인 + DB 제약)
- 개시 잔액 전표(`OPN`): 차 `10100` 현금성 / 대 `20100` 예수금(고객 잔액 합계) + 대 `30100` 개시잔액(차액). 0원 줄은 만들지 않는다. P6 적재 순서는 계정 시드 → 개시 전표 → 거래 전표다.
- **당행 이체(`TRF`)와 상품가입 초입금(`SUB`)은 둘 다 차 `20100` 예수금 / 대 `20100` 예수금이다.** 상품가입은 고객의 입출금계좌에서 새 예적금계좌로 옮기는 내부 이동이라 **현금성 계정이 끼지 않는다.** 차대변은 맞아서 검증에 걸리지 않으므로 틀려도 드러나지 않는다. 주의한다.
- 당초 미확정이었던 후속 패턴은 각 소유 트랙에서 확정했다. 이자 지급(P2 PH-14)은 [분개 패턴표](gl_journal_patterns.md) §3-6, 타행 미결제 2패턴(P4 PH-33-②)은 §3-5를 따른다. **PH-60b는 두 업무 패턴을 생성하지 않는다.**
- **개시·이체·상품가입 패턴은 9/30에 P6에 넘긴다.**
- **완료 기준:** 차대변이 맞지 않는 전표는 예외로 거부된다. 개시 시점 시산표가 맞는다.

### PH-24. GL 분개 서비스 · 이체 기표 훅 · `gl.api`

**계약 — 9/30까지 문서로 먼저 낸다(P4·P2가 기다린다). 구현은 10/1에 착수한다** — S2 10/6~12에 PH-28 베이스라인과 겹쳐 4.5일이 들어가지 않는다.

```java
// gl.api
public interface JournalPostingUseCase {
    void post(JournalRequest request);   // 실패 시 예외를 던진다 — 삼키지 않는다
}
public record JournalRequest(String txType,         // gl_voucher.tx_type 값: OPENING · TRANSFER · PRODUCT_SUBSCRIPTION · INTEREST (타행은 PH-33-②가 추가)
                             String referenceKey,   // 원 거래번호 — 원장·이체와 전표를 잇는 키
                             LocalDate tradeDate,
                             List<JournalLine> lines) {}
public record JournalLine(String accountCode, JournalDirection drCr, long amount) {}
public enum JournalDirection { DEBIT, CREDIT }   // gl.domain 에서 gl.api 로 옮긴다 — 아래
```

- 헤더 금액은 두지 않는다. 금액은 줄마다 있고 전표 합계는 줄에서 계산한다(OPN처럼 줄 금액이 다른 전표가 있다).
- **`JournalDirection`·`GlTxType`을 `gl.domain`에서 `gl.api`로 옮긴다.** 지금은 `gl.domain`에 있는데(PR #478 머지분), `#349`가 건 `Api mayNotAccessAnyLayer()` 때문에 **`gl.api`가 `gl.domain`을 참조하면 `LayerArchitectureTest > gl`이 깨진다.** 공유 어휘를 소유 도메인의 `api`에 두는 것은 [ADR-0006](../adr/0006-domain-contract-surface.md)(#495 초안, PH-24 PR에서 함께 머지. 0004·0005 는 다른 결정이 먼저 썼다) 결정 2와 같은 방향이다. `String`으로 두면 규칙은 피하지만 호출하는 트랙(P2 PH-14 · P4 PH-33-②)이 문자열 오타를 컴파일에서 못 잡는다. 타행 유형은 PH-33-②가 `tx_type` CHECK를 넓히는 V 파일과 같은 PR에서 enum 값을 추가한다.
- **`post()`는 호출자 트랜잭션 안에서만 돈다(`MANDATORY`).** 트랜잭션 없이 부르면 즉시 실패한다. `REQUIRED`면 트랜잭션 없는 호출(예: 배치)에서 전표가 원장과 다른 커밋에 들어가고, 아래 "GL이 이벤트가 아니라 동기 포트인 이유"가 깨진다.
- **`gl_voucher`에 `reference_key` 컬럼을 새 V 파일로 추가한다**(PR #478 스키마에는 없다). `NOT NULL` + `UNIQUE (tx_type, reference_key)`. 이 키가 없으면 "이체 1건당 전표 1건" 검증과 PH-28b 분개누락 탐지가 원장과 조인할 수 없다.
    - **같은 키로 두 번 부르면 예외다(no-op 아님).** 조용히 넘기면 원장만 두 번 기표된 상태가 가려진다. 예외면 원장까지 롤백된다.
    - 개시 전표의 키는 `OPENING-{yyyyMMdd}`(거래일)다.
    - PH-60b 시드(10/2)가 이 V 파일보다 먼저 들어간다. V 파일은 기존 행의 키를 채운 뒤 `NOT NULL`·`UNIQUE`를 건다. PH-60b 시드는 `TRANSFER`·`PRODUCT_SUBSCRIPTION` 전표의 `description`에 원장 `transaction_number`를 남긴다(개시 전표 제외). V 파일은 이 값을, 개시 전표는 `OPENING-20260901`을 `reference_key`로 옮긴다.
    - 역분개를 도입하면(#129, 2차 범위 밖) 원 전표와 같은 키를 쓰지 말고 별도 `tx_type`(예: `REVERSAL`)을 둔다. Apache Fineract는 역분개에 원 거래와 같은 `transaction_id`를 쓰고 DB 유일 제약 없이 애플리케이션에서 중복을 거른다 — 전표 헤더 테이블이 없어서다. 우리는 `gl_voucher`가 있어 유일 제약을 건다.
- 전표 생성 + 분개 기표 서비스. `product_gl_mapping` 은 만들지 않는다 — 예수금 계정이 `20100` 하나라 모든 매핑이 같은 값이고 FE 시산표·정보계 지표도 예수금 하나를 전제한다. 예수금을 나눌 때 도입한다(2차 범위 밖).
- `GlLedgerPostingHook implements transfer.api.LedgerPostingHook` — 이체 유형별 패턴표로 전표 1건. **예외를 던진다(= 이체 롤백).**
- 상품가입 초입금 기표(`LedgerPair.forProductSubscription` 완료 지점). `ProductSubscriptionDepositService` 가 원장 저장 직후 훅 B 를 부른다.
- 정정 체인(#548) 기표. `TransferCorrectionService` 가 원장 저장 직후 훅 B 를 부른다 — 취소정정은 `REVERSAL`(`REV`), 정상거래는 `TRF`.
- 채번은 전용 커넥션 풀(3개)로 한다. 이체 트랜잭션 안에서 메인 풀 커넥션을 하나 더 꺼내면 동시 기표 수가 풀 크기에 닿을 때 순환 대기로 멈춘다.
- 훅 전/후 이체 성능 저하율은 훅이 릴리스 1에 함께 나가 운영에서 잴 수 없어 P3가 로컬(PH-60b 적재)에서 쟀다. 결과는 [harness_results.md §7](harness_results.md#7-ph-24-훅-b-전후--2026-10-1920-로컬)이다.
- **완료 기준:** 이체 1건당 전표 1건, 차대변 일치. 훅에서 예외가 나면 이체가 롤백된다(테스트).

### PH-99. 이체 파이프라인 확장점(seam)

**`TransferExecutionService.execute()`는 P4만 고친다.** 다른 트랙은 아래 훅에 구현체만 등록한다. 구현 규칙·정책 전문은 [transfer_seam.md](transfer_seam.md)다.

```

 ├─ 채번 (기존)                                                     ← 채번 뒤라 거부돼도 ERROR 행이 남는다
 ├─ [훅 A] TransferPreCheck 체인 (락 이전 · 읽기 전용 · order 순)

 ├─ OTP 소비 (기존)
 ├─ requiresNewTransactionTemplate.execute {                       ← PH-80이 S2에 재작성

 │     한도 (기존)                                                  ← 고객 단위 행 락. 커밋까지 쥔다

 │     원장 기표 LedgerPair (기존)
 │     [훅 B] LedgerPostingHook.afterLedger(ctx)                   ← P3 PH-24 (예외 → 롤백 = 이체 실패)

 │   }
 └─ failTransfer() REQUIRES_NEW { tradeDate = gate로 읽기; ERROR 저장; publishEvent(new TransferSettled(...)) }

[Spring Modulith — P1 PH-96] 구독 AFTER_COMMIT 리스너(PH-96-②)마다 EVENT_PUBLICATION 1행을 같은 커밋에 남긴다 (ADR-0010)
```

### PH-80. TIMEOUT · 정정 체인 · 자동 재시도 금지

- **순서:** 10/8 머지까지 S2 영업일이 3일(10/6~8)뿐이라 4일 작업이 들어가지 않는다. 그래서 둘로 나눈다. `ProcessResultStatus`와 무관한 정정 체인·INVALID·역행 금지·재시도 금지 규약은 **S1에 PH-99 직후 착수**한다. TIMEOUT 추가만 P5 회차 현황(10/6)을 받은 뒤 한다. **그래서 PH-99는 9/30까지 끝내는 것을 목표로 한다.** PH-99가 10/1 이후로 밀리면 S1분도 S2로 넘어가므로, 10/8 머지 범위를 P1(B-9)·P5와 다시 맞춘다.
- `ProcessResultStatus`(현재 SUCCESS · ERROR · PROCESSING)에 **TIMEOUT**을 추가한다. `transfer.status` 컬럼(VARCHAR(12), 값은 주석으로만 관리)의 주석을 Flyway로 바꾸고 `schema_reference.md`·ERD를 고친다.
    - 이 enum은 자동이체 실행 기록도 공유한다.
    - **P5가 10/6에 주는 "회차 상태 사용 현황 + 배치 회차는 TIMEOUT을 쓰지 않는다" 문서를 PR 본문 근거로 단다. PR 리뷰는 P5가 한다.**
- 원거래를 **INVALID**로 표기하고 `ref_transfer_id`를 둔다. 정정 체인은 원거래 INVALID → 취소정정 INSERT → 정상거래 INSERT다(DELETE 0건).
- 상태 역행 금지 검증, 자동 재시도 금지 규약 문서와 리뷰 체크 항목

### PH-101. Redis 제거 (① 구현 S2 → ② 판정 측정 S3)

결정과 근거는 [ADR-0007](../adr/0007-remove-redis.md)이다. ①은 #580, ②는 #593, 계획 문서 반영은 #581이다.

**①**

- 인증 토큰 7종 · OTP 발급 잠금 · 약관 열람 이력을 MySQL로 옮긴다(`auth_token` · `otp_issue_lock` · `terms_view_history`). **포트는 그대로 두고 어댑터만 바꾼다.**
- 토큰 저장과 소비는 호출자 트랜잭션에 참여한다. 상품가입이 롤백되면 소비도 롤백된다(#498 해결). OTP 발급 잠금만 `REQUIRES_NEW`다.
- **저장소 스위치** `app.ephemeral-store.provider: redis | jdbc`로 구현을 고른다. 운영 기본값은 `jdbc`다. ② 판정까지 Redis 구현 · 의존 · 운영 Redis 컨테이너를 남긴다. Redis 상태는 `provider=redis`일 때만 배포 헬스체크에 포함된다. 스키마는 AGENTS.md 규칙 6을 따른다.
- **2단계(S3, 0.5인일):** ② 판정을 통과하면 Redis 어댑터 · 스위치 · `build.gradle` · yml · `docker-compose.yml` · 배포 compose · 테스트 컨테이너에서 Redis를 뺀다. 판정에 실패하면 `provider=redis`로 되돌리고 원인 사용처를 분석한다.
- P4 완충에서 P3 · P6 대신 수행한다 — [D-14](README.md#d-14--92123--p4-제안-리드-승인)의 예외([D-27](README.md#d-27--109--팀-합의)).
- **완료 기준:** 1단계 — 같은 토큰 동시 소비는 실제 MySQL에서 1건만 성공. #498 재현 절차 통과. `provider=jdbc`면 로컬에서 Redis 없이 기동. 2단계 — `src` · 빌드 · 배포 설정에 Redis 참조 0건.

**②** — A'·B'로 Redis 제거를 판정한다. PH-49c 영향은 기존 환경의 C로 별도 측정하고, 검증된 C를 PH-30 개선 전 기준선으로 채택한다.

- 릴리스 1 이미지(커밋 `1709c355`, PH-49c 미포함)를 운영에 배포하고 PH-60b를 적재한 뒤, LOCK-TUNE 전에 A'·B'를 같은 날 잰다. **같은 이미지에서 Redis/JDBC 저장소 모드만 바꾸고**, 회차마다 번갈아(A' → B' → A' → B' …) 잰다.
  - **A'** = 운영 이미지 그대로 `provider=redis`로 재기동(Redis 있음). 별도 이미지나 Flyway 완화가 필요 없다.
  - **B'** = 운영 그대로(`provider=jdbc`).
- harness는 PH-30 `perf/k6/load.js`다. 엔드포인트별 p95·p99, 수준별 성공률·에러율, 포화 시작 도착률, RDS CPU·connection, `vmstat`, 정합성을 기록한다. "이체만" 지표는 토큰 발급 요청을 빼므로 이 비교에 쓰지 않는다.
- 판정 기준은 ADR-0007의 표(상대 기준)와 5/s 절대 하한이다. 측정 전에 합의하고, 결과를 본 뒤 바꾸지 않는다.
- **B'는 PH-49c 적용 전의 참고 수치다.** P6은 릴리스 2의 기존 단일 EC2·RDS에서 `provider=jdbc`로 예열 후 4회 C를 측정한다([PH-49c 측정 계획](ph49c_jdbc_session.md#운영-성능-재측정-계획)). C가 B′ 대응 조건과 정합성을 충족하면 PH-30 개선 전 기준선으로도 채택한다. D는 생략하고 P1은 릴리스 3을 같은 기존 환경에 수동 배포한 뒤 S4를 측정한다. A'·B' 측정 전에는 개선 작업을 운영에 반영하거나 `main`을 추가 배포하지 않고, 시드 대역 테스트도 멈추는 조건이었다. A′/B′ 8회 측정은 완료됐다.
- **A′/B′ 기한은 10/22였다.** 당시 지연 대비안은 PH-49c가 없는 **릴리스 1 이미지 `1709c355`에서 A'·B' 모두** 재고 두 회차 사이에는 `provider`만 바꾸는 것이었다([ADR-0007](../adr/0007-remove-redis.md#측정과-판정)). 릴리스 1 이미지를 다시 사용할 수 없으면 릴리스 2 측정값으로 Redis 제거를 판정하지 않고 보류하는 조건이었다. A′/B′ 8회가 완료되어 이 대비안은 적용하지 않았다. 후속 PH-30 기준선은 검증된 C다.
- **완료 기준:** A'·B' 결과를 `harness_results.md`에 기록하고 ADR-0007에 판정을 남긴다. 통과하면 ① 2단계로 넘어가고, 미달이면 `provider=redis`로 되돌린 뒤 원인 사용처를 정한다.

### PH-43. COB 파이프라인

**계약 (10/6 레포에 먼저 머지):**

```java
// batch.api
public interface CobStep {
    String name();
    int order();
    void run(LocalDate businessDate);   // 각 스텝은 @Transactional 자기 경계를 연다. 마감 중단은 CobStepHaltException(#600)
}
```

**스텝 체인 (순서 소유 P5):**

| 순서 | 스텝 | 구현 소유 | 등록 시점 |
|---|---|---|---|
| 1 | 영업일 전환 (저장된 영업일이 달력보다 미래가 아닌지 확인 후, 이전 영업일을 `COB_DATE`로 들고 다음 영업일로 넘김 — 러너가 스텝 루프 전에 직접 수행, `CobStep` 아님) | P5 | S2, 완료 |
| 2 | 대사 | P4 PH-38 | 등록 완료(#604) — hard 중단 #663 머지(PR #717) |
| 3 | 만기 감지 | P2 PH-15 | 10/19 머지(#647) |
| 4 | 휴면 전환 | P2 PH-16 | 자리만 10/16 · 등록 10/30까지 |

> **자동·예약이체는 COB 스텝이 아니다.** 기존 `DailyTransferBatchScheduler`가 매일 00:10,
> 달력 날짜 기준으로 그대로 돈다(2026-09-28 결정). 자동·예약이체는 휴일에도 지정일에
> 실행해야 하는데(REQ-AUTO-001), COB는 영업일에만 돌아서 COB 안에 넣으면 연휴 중 지정된
> 회차가 실행될 날이 없어진다.
>
> **"영업일 전환"이 왜 맨 앞인가.** 마지막 스텝으로 두면, COB가 도는 동안 들어온 거래가
> 아직 이전 영업일로 찍히는데 대사 스텝은 이미 끝난 뒤라 그 거래가 어느 쪽 대사에도 안
> 잡히는 틈이 생긴다. 그래서 먼저 영업일을 넘기고, 이후 스텝들은 그 직전 영업일(`COB_DATE`)을
> 마감 대상으로 쓴다. 상세는 [ADR-0004](../adr/0004-cob-step-order-cob-date.md).

- **파티션 생성 호출 스텝은 없다**([#379 규격](#379-규격-전달)).
- **정보계 ETL은 COB 스텝이 아니다.** 온프레미스에서 따로 돈다([PH-76](#ph-76-정보계-etl), [D-25](README.md#d-25--927--리드-제안1020-팀-확정)).
- 러너: 전용 `CobScheduler`(23:30)가 `CobRunnerUseCase`를 호출하고, `CobRunnerService`가 스텝을 순서대로 부르며 `BatchExecutionLockPort`로 단일 실행한다. 스텝이 `CobStepHaltException`을 던지면 남은 스텝을 생략하고 즉시 중단한다(#600) — 단, 영업일 전환은 스텝 루프 밖이라 되돌리지 않는다.
- 대사 정책: 불일치 ≤ 임계(예: 10)면 soft(리포트·로그), 초과면 hard(마감 중단, `CobStepHaltException`으로 표현, #600). hard를 던지려면 #663의 `COB_DATE` 저장·실패 스텝 재실행이 먼저 필요했고, #663에서 갖춰 hard를 켰다([ADR-0004](../adr/0004-cob-step-order-cob-date.md) 후속 결정).
- 배치 실행 기록 테이블(#603, 완료·PR #606): job · step · 영업일 · 시작/종료 · 상태 · 실패 사유. **조회 API는 범위 밖**이다. **스텝 내용과 무관한 러너 인프라라 대사·만기감지 스텝을 안 기다리고 바로 착수했다.** **이 테이블은 관측용 append-only 기록일 뿐, 재시작의 체크포인트로 보장하지 않는다 — 기록 저장 실패는 무시하고 배치를 계속 진행한다(PR #606 셀프리뷰, vsopsw R2). #663은 별도 체크포인트 테이블 `cob_checkpoint`를 두기로 정했다.**
- 실패 스텝부터 다시 실행할 수 있다(#663). 러너가 `cob_checkpoint`에 `COB_DATE`와 스텝 진행을 남기고, 다음 `run()`이 미완료 날짜를 오래된 순으로 PENDING 스텝만 이어서 돌린다. 재개 중 HALTED면 그날 밤 새 COB는 시작하지 않는다.
- COB 베이스라인: 15만 계좌 순차, 단일 EC2. 60b 베이스라인(PH-11·28·38·43)은 각자 개선 PR 직전 코드로 한 번에 하나씩 재고(D-27), 순서는 [D-31](README.md#d-31--1019--팀-합의)을 따른다. 측정 시점에 대사·만기감지가 몇 개 꽂혀 있는지 #663에서 확인한다. 현황(10/20 P5): 선행이 모두 풀렸고 대사 부분은 P4가 10/25에 재서 중앙값 1,188초다([ph38_baseline_results.md](ph38_baseline_results.md)). COB 전체는 10/26 첫 운영 COB에서 약 19분 45초가 나왔다. 체인은 대사와 만기 감지이고, 휴면 스텝(10/30 통합)은 이번 기준선에서 뺀다.
- **선행은 PH-40뿐이다.** 대사 배치를 기다리지 않는다(선행 순환 정정).
- **완료 기준:** 스텝이 순서대로 돌고 기록이 남는다. 대사 후 원장 합계 = 잔액 합계이고, 불일치 시 정책대로 동작한다.
- 현황: 러너·스텝 인터페이스(`CobRunnerService`·`CobStep`·`CobScheduler`)는 머지됐다(PR #543·#557). **하드 중단 신호(`CobStepHaltException`)도 머지됐다(#600).** **배치 실행 기록 테이블(`batch_execution_history`)도 구현 완료(#603).** **`COB_DATE` 저장·실패 스텝부터 재개·대사 hard 활성화도 구현했다(#663, 운영 임계는 배포 환경변수로 1000에서 시작해 릴리스 2 첫 대사 결과를 본 뒤 낮춘다).** 대사는 COB 스텝(`LedgerReconciliationCobStep`, `order=2`)으로 편입됐고 독립 스케줄러는 없앴다(#604). 멱등키 정리는 여전히 독립 스케줄러로 돈다. `DailyTransferBatchService`(자동·예약이체)는 COB 스텝이 아니라 별도로 존재한다.

- **온프레미스 독립 작업이다.** COB 스텝이 아니다([D-25](README.md#d-25--927--리드-제안1020-팀-확정)). 자동 적재는 #556이 원천 `business_date_cutoff`와 date-fence를 구현한 뒤에만 켠다. 레플리카의 `business_date_cutoff(base_date=D, status=CLOSED)`가 유일한 시작 신호이고, `batch_execution_history`(#603)는 관측용이라 신호로 쓰지 않는다. cutoff는 D 거래를 모두 drain한 뒤 영업일 전환과 같은 원천 트랜잭션으로 커밋되어야 하며, 복제는 `replica_preserve_commit_order = ON`으로 그 순서를 보존한다. 상세 조건은 [info_mart.md](info_mart.md) §3-0~§3-1이다.
- 레플리카는 10/28 복제 시작(P2 PH-70-②) 뒤에 생긴다. 그 전에는 온프레미스 MySQL에 덤프를 적재해 개발하고, 복제가 시작되면 원본을 레플리카로 바꾼다. **Plan B:** 복제가 늦으면 덤프 적재로 시연한다.

### PH-100. 하이브리드 연결 (① 온프레미스 VM S2 → ② VPN 연결 S3)

온프레미스는 신한DS 자체 서버다([D-25](README.md#d-25--927--리드-제안1020-팀-확정)).

**①**

- 부트캠프 VM 1대 안에서 역할을 논리적으로 분리한다.
    - 정보계·DR 영역: Nginx · 정보계 API · 계정계 API(DR 대기, AWS 사용 불가 시 기동) · MySQL 레플리카 · 마트
    - 대외·모니터링 영역: 모의 대외기관 · Prometheus · Grafana
- SSM 하이브리드 활성화로 등록한다. 인바운드 SSH는 열지 않는다.
- Customer Gateway를 준비한다. 고정 공인 IP와 UDP 500·4500이 필요하다([O-10](README.md#8-미결)). 테스트용 VM에서는 확인했고(#624), 최종 VM은 강사님이 확정하므로 그때 다시 확인한다.

**②**

- Site-to-Site VPN: VPN Gateway ↔ Customer Gateway, IPsec 터널 1개(터널 1만 쓰고 VM이 먼저 접속), 정적 라우팅(온프레미스 대역 1개)
- 터널은 VPN apply(P2 리허설 apply 뒤) 직후 VM 쪽 설정으로 세운다([VM 설정 절차](ph100_vpn_vm_runbook.md)). binlog 복제(P2 PH-70-②) · 대외 전문 · 메트릭 수집 · 정보계 조회가 이 터널을 지난다.
- NAT 뒤 VM의 strongSwan 설정 요점(#624 테스트). `ipsec.conf`(연결 설정): 온프레미스가 먼저 접속하고(`auto=start`), `leftid`는 내부 IP가 아닌 공인 IP로 두며, `forceencaps=yes`로 UDP 캡슐화를 강제하고, `mark`로 터널에 태울 패킷을 좁힌다. `strongswan.conf`(`/etc/strongswan.d/*.conf`로 포함되는 charon 설정): `charon { install_routes = no }`로 라우팅 표 변경을 막는다. AWS 정적 라우팅의 트래픽 선택기가 `0.0.0.0/0`이라 둘 중 하나라도 빠지면 VM의 기본 경로가 터널로 들어가 SSH가 끊긴다.
- **순서:** P2가 RDS 3306 허용 규칙을 적용한 뒤 VPN apply와 VM 터널 설정을 하고, 터널로 RDS 3306 연결 검증을 마친 뒤에 PH-70-② 복제를 시작한다.
- **한계(단일 터널):** 터널 1만 쓰므로 터널 1이 끊기면 binlog 복제 · 대외 전문 · 메트릭 수집 · 정보계 조회가 멈춘다. 가용성이 필요해지면 터널 2 설정과 전환 검증을 따로 한다(이 범위 밖).
- **완료 기준:** 온프레미스에서 사설 IP로 WAS 8080(#756 보안 그룹 규칙)과 RDS 3306(허용 규칙은 P2가 추가)에 닿고, WAS에서 온프레미스 정보계 API와 모의 대외기관에 닿는다. 온프레미스의 인터넷 공개 포트는 Nginx 443 하나다.

- PH-60b 계좌번호는 실제 당행 코드 `088`과 상품별 prefix(요구불 `10`, 기본 정기예금 `20`, 단기 정기예금 `23`, 정기적금 `32`)를 사용하고 `account_number_sequence`에서 전용 대역을 예약한다. PH-60의 `860` 규칙을 재사용하지 않는다. 고객 아이디는 `^[a-z][a-z0-9]{5,15}$`를 만족하는 `ph60b00001~ph60b50000`을 사용한다.
- 분개는 [gl_journal_patterns.md](gl_journal_patterns.md)의 `TRF`·`SUB` 패턴으로 **거래 1건당 `ledger_entry` 2행·전표 1건·분개 2행**을 만든다. PH-60의 개시 전표 `20260901-OPN-000001`은 그대로 사용하며, **PH-60b는 개시 전표를 추가하지 않는다.** 신규 계좌 잔액은 직접 주입하지 않고 기존 PH-60 계좌에서 발생한 TRF 또는 SUB 거래 원장으로 형성한다. **`SUB`의 차변은 예수금이다(현금성 아님).** `INT`와 타행 미결제는 만들지 않는다.
- PH-60 이체 23.5만 건에는 TRF 전표 23.5만 건·분개 47만 행을 별도로 보완한다. TRF와 SUB 전표 `description`에는 해당 거래 원장의 `transaction_number`를 저장한다. 2026-09-01 보완 전표가 `20260901-TRF-000001~235000`을 사용하므로 같은 날의 PH-60b TRF 전표는 `235001`부터 채번한다.
- 자동이체와 예약이체는 각각 1만 건으로 고정한다. SUB 10만 건 안에서 `PRD_SHORT_DEP` 정기예금 1천 개를 2026-09-01에 가입하고 2026-10-01에 만기시켜 기준일에 `MATURED` 상태로 만든다. 다른 정기예금 1천 개는 만기일이 2026-10-24~11-22인 `ACTIVE` 만기 임박 후보로 만들고, 나머지 SUB 9만 8천 건은 일반 `ACTIVE` 예·적금으로 구성한다. 상태 데이터 때문에 거래·원장·전표·분개를 추가하지 않는다. 요구불계좌 1천 개는 `ACTIVE` 휴면 후보로 만들고, 2026-09-01 SUB 출금 이후 거래 대상에서 제외해 `COALESCE(last_transaction_at, created_at)` 기준 365일 무거래 정책을 사용한다.
- 자동이체 시작일은 실제 적재일 다음 날로 두고 최초 실행일은 시작일 당일을 포함해 처음 도래하는 `transfer_day`로 계산한다. 예약이체 실행일도 적재일 다음 날 이후로 분산해 적재 직후 실행 누락 상태가 생기지 않게 한다.
- 예·적금 계좌 10만 개에는 `product_subscription`을 각 1행 생성한다. PH-60b 가입일은 모두 2026-09-01~10-05다. `PRD_SHORT_DEP`은 1·2개월, `PRD_REGULAR_SAVE`는 6~24개월, `PRD_BASIC_DEP`은 6~36개월 범위에서 가입하며 가입금액·단위·`applied_rate`도 상품 마스터를 따른다. 만기 임박 1천 개는 단기예금 1·2개월 가입으로 2026-10-24~11-22 만기 범위를 맞춘다(10/31은 해당 기간 조합으로 만들 수 없어 제외). 2개월 금리 구간은 상품 마스터에 추가한다.
- PH-60 기존 요구불계좌에서 자금을 공급할 때 9/1 개시 입금 뒤 같은 날의 다른 거래보다 먼저 TRF 5만 건을 실행한다. 건당 950만 원, PH-60 계좌당 5건으로 공급액을 4,750만 원으로 제한하고 같은 날의 PH-60 기존 출금까지 합산해 일 한도 5,000만 원을 지킨다. 정상 쓰기를 중단한 유지보수 시간에 실제 입출금 대상 계좌만 ID 오름차순으로 1,000개씩 `SELECT ... FOR UPDATE` 잠금하고 5만 건 구간마다 현재 잔액을 다시 조회한다. 핫스팟 100계좌의 급여일 한도 초과는 부하·이상거래 탐지용 의도된 데이터로 문서화한다. 상품 조회는 행 부재 시 `EmptyResultDataAccessException`을 처리해 적재 전에 명확히 실패시킨다.
- 실행 플래그는 PH-60 최소 시드 `app.phase2-seed.minimum.execute=true`, PH-60b 대량 시드 `app.phase2-seed.bulk.execute=true`로 분리한다. 두 플래그를 동시에 허용하지 않는다.
- PH-60b 전용 ID 대역과 단계별 트랜잭션·체크포인트는 [ph60b_bulk_seed.md](ph60b_bulk_seed.md)를 따른다. 적재 후 [gl_journal_patterns.md](gl_journal_patterns.md) §5의 자가 검증 SQL을 실행한다.
- TRF·SUB 적재 후 `occurred_at, ledger_entry_id` 순으로 `balance_after`와 계좌 잔액을 정규화하고, 계좌 잔액=원장 합계·시간순 누계·거래별 원장 쌍을 완료 검증에서 확인한다. 완료 시드의 재실행은 거부한다.
- 실제 MySQL 테스트에서 PH-60 GL 보완 `INSERT ... SELECT`와 거래 구간 실패 후 커밋 유지·체크포인트 재개를 검증한다.
- 재현 가능한 시드값을 쓰고, QA 데모 대역(`V202609161800`, #439·#444)과 겹치지 않게 한다.
- PH-60의 실행법·전용 대역·검수 SQL·실측 결과는 [ph60_minimum_seed.md](ph60_minimum_seed.md)를 따른다. 대량 시드는 HTTP/Swagger 엔드포인트로 노출하지 않으며, 정기 배포와 분리된 일회성 작업에서 `phase2-seed` 프로필과 명시적 실행 플래그를 함께 지정할 때만 실행하고 검증 완료 후 자동 종료한다.
- **P4 검수를 통과해야 완료다**(원장 짝 · 원장 합계 = 잔액 합계 · 전표 차대변). 적재 시간을 기록한다.
- **10/16 릴리스 1 전에 적재한다**([D-27](README.md#d-27--109--팀-합의)). 릴리스 1에 들어갈 [PH-24](#ph-24-gl-분개-서비스--이체-기표-훅--glapi)의 `gl_voucher.reference_key` 마이그레이션보다 먼저 들어가야 기존 행을 채운 뒤 제약을 걸 수 있다(P3 확인). 10/6 한계선과 10/8 개선 전 수치 마감은 지나갔으므로, 60b 베이스라인(PH-11 · PH-28 · PH-38 · PH-43)은 각자 개선 PR 직전 코드로 한 번에 하나씩 잰다.
