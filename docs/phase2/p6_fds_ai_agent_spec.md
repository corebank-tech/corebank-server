# P6 AI Agent 기반 이상거래 탐지·조사 시스템 — 최종 개발 명세서 (v3)

> **최종 채택 아키텍처:** Spring Boot 실시간 FDS 탐지·보류 + LangGraph 비동기 보류 사건 추가 위험 조사 Agent  
> **프로젝트 기간:** 2026-10-26 ~ 2026-11-17 / **발표:** 2026-11-18  
> **팀 구성:** 총 6명, 그중 AI 담당 1명(본인). 아래 역할은 제안이며 실제 팀 업무 배정과 다를 수 있다.  
> **대상:** 고객 주도 **당행 즉시이체**. 타행·예약·자동이체 제외.  
> **핵심 변경:** 별도 `PENDING_REVIEW` 상태 없음. **서버가 먼저 `HELD` 처리한 뒤 Agent가 비동기 조사**한다.  
> **문서 성격:** 개발·연동·시연을 위한 설계안. 실금융 운영 기준이나 검증된 사기 탐지 임계값을 뜻하지 않는다.
> **문서 관계:** 이 명세서는 이전 타당성 검토안의 보류 전 Agent 판정 흐름을 대체한다. [제안서](p6_fds_ai_agent_proposal.md)는 배경·공수 근거이며, 이체 보류·토큰·재실행의 확정 계약은 [transfer_seam.md §9](transfer_seam.md#9-훅-c--이체-보류-771)를 우선한다.

## 1. 프로젝트 개요

### 1.1 개발 배경

단일 이체 금액만 확인하는 방식으로는 작은 금액을 짧은 시간에 반복 송금하는 거래나 고객이 이체 화면에서 주저하는 행동을 충분히 설명하기 어렵다. 이 프로젝트는 **화면 행동 신호 + 성공 이체 이력 + 현재 요청**을 결합해 의심 거래를 이체 실행 전에 보류하고, 이후 AI Agent가 추가 거래 맥락을 조사해 관리자 의사결정을 지원한다.

핵심은 **AI가 원장을 직접 제어하지 않는 것**이다. 거래를 실제로 멈추고 재개하는 권한은 Spring Boot에 남기고, AI Agent는 **이미 보류된 사건 안에서** 추가 위험 신호 발견, 증거 수집, 조사 결과 정리, 조치 권고를 담당한다. 서버 A/B를 통과한 이체는 Agent 조사 대상이 아니므로 이 설계로 추가 탐지하지 못한다.

### 1.2 목표

1. React 즉시이체 화면에서 7종 행동 이벤트를 수집한다.
2. Spring Boot가 망설임 규칙과 반복 이체 정책 A/B를 실시간 계산한다.
3. 조건 충족 시 **출금·입금·원장 기표 이전**에 해당 이체를 `HELD`로 저장한다.
4. `HELD` 발생 이벤트를 통해 Python/FastAPI의 LangGraph Agent를 비동기로 실행한다.
5. Agent는 Tool을 사용해 보류 거래의 이력과 추가 위험 맥락을 조사하고 **서버 1차 보류 사유와 구별되는 보류 사건 내 추가 발견 사항**을 기록한다.
6. 관리자가 아웃바운드 콜 결과를 기록하고 승인·거절한다.
7. 승인 시 P6이 관리자 권한·콜 결과를 확인하고 P4의 `release()`가 `HELD` 건을 `EXECUTING`으로 선점한다. 내부 `execute()`는 보류 행 상태·원본 요청과 최신 거래 조건을 검증해 한 번 실행한다. 최초 OTP를 다시 검증하거나 재사용하지 않는다.
8. 정상 거래, 정책 A, 정책 B, AI 장애, 관리자 거절·승인을 시연한다.

### 1.3 비목표

- 실제 사기 확률 또는 실제 금융권 탐지율의 입증
- AI의 계좌 정지·고객 거래 거절 권한
- LLM이 직접 잔액 수정, 원장 기표, 이체 실행
- 자동 전화·문자 발송, 실시간 외부 금융 데이터 조회
- ViT, 다중 Agent, RAG, 별도 MCP 서버, SHAP 심층 시각화
- **관리자 승인 후 고객 재인증** 및 OTP 보관·재사용

### 1.4 Agent 명칭과 정체성

**권장 명칭:** `AI Agent 기반 이상거래 탐지 및 조사 시스템` / `FDS Investigation Agent`.

이 시스템은 **Spring Boot의 실행 전 규칙 탐지·보류 + AI Agent의 보류 사건 내 추가 위험 신호 발견·조사**로 구성된다. Agent가 단순히 `HELD` 사유를 자연어로 요약하기만 한다면 조사 Agent라는 명칭도 약하다. Agent는 조회 Tool을 호출하고 결과에 따라 추가 조사 Tool을 선택해, 서버의 A/B 보류 사유에 포함되지 않은 관찰 사실을 구조화된 `secondaryFindings`로 생성한다. 단, Agent는 **`HELD` 사건에만 실행**되므로 A/B를 통과한 거래의 누락 사기를 찾아내는 별도 2차 탐지망은 아니다. 추가 발견은 관리자 검토 참고 정보이며 서버의 필수 보류 정책을 우회하거나 변경하지 않는다.

## 2. 최종 아키텍처

### 2.1 전체 흐름

```text
[고객 React 즉시이체]
   ├─ 7종 행동 이벤트 → Spring Boot 행동 이벤트 API → MySQL
   └─ 이체 요청(flowId, idempotencyKey)
                        │
                        ▼
             [Spring Boot 이체 실행 경계]
               ├─ 인증·고객 소유권 검증
               ├─ 계좌비밀번호 토큰·OTP 소비 (훅 C 판정 전)
               ├─ 한도 적립 → 훅 C (고객 단위 락 유지)
               ├─ 행동 피처·망설임 규칙
               ├─ 성공 이체 이력 + 현재 요청 집계
               └─ 정책 A / B 원자적 판정
                        │
             ┌──────────┴────────────┐
             │                       │
          정상 거래               A/B 충족
             │                       │
       기존 이체 실행          기표 트랜잭션 롤백
       (원장 기표)             → 새 트랜잭션에 HELD 저장 (원장 미기표)
                                     │
                                     ▼
                            [비동기 조사 작업]
                                     │
                          Python FastAPI / LangGraph
                             ├─ Tool 1: 거래 이력
                             ├─ Tool 2: 추가 맥락 조회
                             └─ 보류 사건 내 추가 위험 발견·권고
                                     │
                                     ▼
                           [조사 결과 영속 저장]
                                     │
                                     ▼
                           [관리자 검토·콜 기록]
                              ├─ 거절 → REJECTED
                                     └─ 승인 → 관리자 권한·콜 결과 검증 → release() 선점
                                         │
                                         ▼
                                  sourceId가 있는 내부 execute()에서
                                  EXECUTING 보류 행·원본 요청 검증 → 기존 기표 로직
                                   → SUCCESS
```

**중요:** XGBoost 행동 점수는 초기에는 **보조 지표**로 저장·제공한다. 모델 점수만으로 보류하지 않는다. 학습 데이터가 합성이므로 점수를 실제 사기 확률로 표기하지 않는다.

### 2.2 동기·비동기 경계

| 구간 | 처리 방식 | 장애 시 원칙 |
|---|---|---|
| 행동 이벤트 저장·규칙 계산 | 이체 전 동기 | 필수 입력 누락·검증 실패 시 명시적 오류 또는 안전한 대체 정책 |
| A/B 정책 판정 및 `HELD` | 이체 전 동기 | 서버가 책임, AI 응답을 기다리지 않음 |
| 정상 이체 실행 | 기존 이체 트랜잭션 | 기존 멱등·정합성 유지 |
| Agent 거래 조사 | `HELD` 이후 비동기 | 실패해도 `HELD` 유지, 재시도·관리자 수동 검토 |
| 관리자 승인 후 실행 | P6 권한·콜 결과 확인 → P4 `release() → execute()` | `EXECUTING` 보류 행·원본 요청과 최신 잔액·한도·계좌 상태를 확인하고 OTP 재사용 없이 한 번 실행 |

### 2.3 왜 `PENDING_REVIEW`를 없애는가

서버가 **AI 조사 전에 이미 `HELD`를 확정**하므로, 조사 대기만을 표현하는 별도 거래 상태가 필요 없다. 대신 **거래 상태**와 **AI 조사 상태**는 분리한다.

- 거래 상태: `HELD`, `SUCCESS`, `REJECTED`, `EXPIRED` 등
- 조사 상태: `QUEUED`, `RUNNING`, `COMPLETED`, `FAILED` 등

`HELD` + `QUEUED`는 '보류되었고 아직 AI 조사 전'을 의미한다. `PENDING_REVIEW`를 이름만 바꿔 숨기는 구조가 아니라, **보류 결정을 서버가 선행했다는 업무 의미의 변경**이다.

### 2.4 이체 계약과 연결

기존 `TransferPreCheck`는 읽기 전용 거부·예외 훅이므로 `HELD`에 사용하지 않는다. 즉시이체의 **훅 C(`TransferHoldPolicy`)는 한도 적립 뒤, 계좌 락·기표 전에** P6 정책을 읽기 전용으로 판정한다. HOLD면 P4가 기표 트랜잭션을 롤백하고 새 트랜잭션에 원본 요청과 `TransferHeld`를 함께 남긴다. P6 정책은 고객 락을 쥔 훅 안에서 외부 호출·DB 쓰기를 하지 않고, 비활성 스위치일 때 DB도 읽지 않는다. 상세 계약은 [transfer_seam.md §9](transfer_seam.md#9-훅-c--이체-보류-771)를 따른다.

## 4. FE 행동 이벤트 및 망설임 판정

### 4.1 수집 이벤트 7개

모든 이벤트는 `flowId`, `seqNo`, `eventType`, `occurredAt`, `step`을 포함한다. `flowId`는 이체 시도마다 새로 생성한다.

| 이벤트 | 발생 시점 | 목적 |
|---|---|---|
| `TRANSFER_ENTER` | 즉시이체 화면 첫 진입 | 시도 시작 |
| `RECIPIENT_CONFIRMED` | 수취계좌 확인 성공 | 수취인 확인 시간 |
| `AMOUNT_EDITED` | 최초 확정 금액을 다시 수정 완료 | 금액 재수정 횟수 |
| `STEP_BACK` | 확인 단계에서 입력 단계 복귀 | 단계 왕복 |
| `CONFIRM_ENTER` | 확인 화면 진입·재진입 | 확인 체류 시작 |
| `CONFIRM_LEAVE` | 확인 화면 이탈·인증 이동 | 확인 체류 종료 |
| `SUBMIT_REQUESTED` | 인증 후 실제 이체 API 요청 직전 | 요청과 행동 연결 |

계좌번호 원문·비밀번호·OTP·메모 원문을 행동 이벤트에 저장하지 않는다. 이벤트 발생 횟수 자체를 사기 판정에 사용하지 않는다. `occurredAt`은 실제 시각(`Date.now()` 기반)으로 기록한다. `confirmActiveSeconds`는 확인 화면이 열려 있고 `document.visibilityState === 'visible'`인 구간의 `performance.now()` 차이만 누적한다. `visibilitychange`에서 hidden으로 바뀌면 열린 구간을 닫고, visible로 돌아오면 새 구간을 시작한다. `CONFIRM_LEAVE`에서도 열린 구간을 닫는다. `performance.now()` 값을 달력 시각인 `occurredAt`에 넣거나 hidden 구간을 활성 체류에 더하지 않는다. FE 시각과 경과 시간은 신뢰할 수 없는 참고값이므로 서버 수신 시각·순서·허용 범위를 검증한다.

### 4.2 파생 피처

```text
backCount                 : 확인 → 입력 복귀 횟수
amountRevisionCount       : 확정 금액 재수정 횟수
confirmActiveSeconds      : 활성 확인 화면 체류 초
recipientConfirmSeconds   : 수취인 확인 소요 초
totalFlowSeconds          : 전체 이체 흐름 소요 초
hesitationWarning         : 규칙 기반 망설임 여부
behaviorRiskScore         : XGBoost 보조 위험 점수
```

### 4.3 망설임 규칙

다음 세 조건 중 **2개 이상**이면 `hesitationWarning=true`:

1. `backCount >= 1`
2. `amountRevisionCount >= 2`
3. `confirmActiveSeconds >= 60`

이 수치는 **데모 가설값**이며 실제 사기 거래에서 검증된 기준이 아니다. 망설임 하나만으로 이체를 보류하지 않는다.

### 4.4 이벤트 누락·변조 대응

- `(flowId, seqNo)` 중복 방지, 이벤트 수·크기·순서 제한
- 인증 고객에게 귀속된 `flowId`만 허용
- FE가 전송한 위험 점수·고객 ID·금액은 서버의 최종 판단 근거로 신뢰하지 않음
- 행동 이벤트가 누락되어도 **서버의 거래 반복 정책 B는 항상 검사**
- 필수 행동 정보가 없으면 망설임을 추정하지 않으므로 정책 A는 성립하지 않는다. 정책 B는 거래 이력만으로 계속 검사한다.
- 훅 C에서 행동 이벤트 또는 거래 이력 **조회 자체가 실패**하면 조회 예외로 이체를 `ERROR`로 확정한다. 이벤트가 정상 조회됐지만 없는 경우와 구별하고, 판정을 건너뛰어 실행하지 않는다.

## 5. 서버의 1차 FDS 정책

### 5.1 공통 집계

**고객 전체 출금계좌**에서 동일 수취계좌로 발생한 **직전 10분 성공 이체**를 조회하고, **현재 미실행 이체 요청**을 가상으로 추가한다. 시간창은 `TransferHoldContext.requestedAt` 기준 **`[requestedAt - 10분, requestedAt)`**으로, 시작 시각은 포함하고 요청 시각은 제외한다. 실패·취소·거절·보류 건은 성공 이체 횟수에 넣지 않는다.

P4 `RecentTransferQuery`는 기존 `ix_transfer_wacc`로 고객의 출금계좌마다 당행 즉시·예약·자동이체의 커밋된 `SUCCESS`를 읽고, `invalidated_at`이 있는 무효화 행은 제외한다. 현재 요청은 이 조회 결과에 없으므로 아래 계산에서 한 번만 더한다. `transfer`에는 FDS용 인덱스·컬럼을 추가하지 않는다.

신규 수취인 판정의 `hasSucceededBefore`는 시간 하한 없이 과거 성공 이력을 읽을 수 있다. 고객 락을 쥔 조회 비용을 P4가 #832에서 측정해 11/6까지 공유할 예정이며, 결과에 따라 정책 B의 조회 기준·구현을 P4와 다시 합의한다. 측정 전에는 비용이나 정책 변경을 확정값으로 쓰지 않는다.

```text
count10m  = 직전 10분 성공 이체 횟수 + 1(현재 요청)
amount10m = 직전 10분 성공 이체 금액 합계 + 현재 요청 금액
```

첫 수취인 여부는 현재 요청 직전 단순 조회가 아니라 **반복 묶음의 첫 이체 이전** 이력을 기준으로 계산한다. 이미 2건 송금했다는 이유로 3번째 이체에서 '기존 수취인'이 되어버리는 오류를 방지한다.

### 5.2 정책 A — 망설임 + 신규 수취인 + 반복 송금

```text
hesitationInWindow == true
AND newRecipientAtWindowStart == true
AND count10m >= 3
AND amount10m >= 1_500_000
```

`hesitationInWindow`는 현재 요청만이 아니라 **같은 반복 묶음에서 관측된 적어도 한 이체 시도**의 망설임을 포함한다. 이를 위해 과거 성공 이체에 연결된 행동 결과를 보존해야 한다.

P6은 성공 이체 ID(`refId`)와 `flowId` 연결을 자기 테이블에 멱등 저장한다(`refId` 유니크). P4가 `TransferSettled`에 nullable `flowId`를 추가한 PR이 머지된 **뒤** 성공 이벤트 리스너를 연결한다. 연결 저장 부품은 먼저 준비할 수 있다. 커밋 후 이벤트 처리 지연으로 앞선 이체의 연결이 잠시 없을 수 있으므로, 그때에도 정책 B는 `RecentTransferQuery`만으로 판정한다. `flowId`는 FE 이체 요청의 선택 필드이며 요청 지문에 포함한다. FDS가 인증 고객의 흐름인지 검증한다.

**시연:** 신규 수취인에게 50만 원씩 2회 성공 → 세 번째 50만 원 요청 → 반복 묶음 내 망설임 있음 → 세 번째 요청만 `HELD`.

### 5.3 정책 B — 망설임 없는 강한 반복 송금

```text
count10m >= 3
AND amount10m >= 3_000_000
```

수취인 신규 여부·망설임은 필수 조건이 아니다. A를 우선 평가하고 A가 성립하지 않을 때 B를 평가한다. **정책 B는 AI·행동 로그 장애와 무관하게 서버가 실행 전 검사**해야 한다.

### 5.4 임계값의 성격

`10분·3회·150만 원·300만 원`은 **시연용 초기 가설값**이다. 금융권 표준, 법적 기준 또는 실증 최적값이 아니다. 정상 반복 송금의 오탐 가능성이 있으므로 시나리오별 결과를 기록하고 발표에서 한계를 명시한다.

### 5.5 동시성·우회 방지

두 개의 세 번째 요청이 동시에 들어와도 P4가 한도 적립에서 잡은 **고객 단위 행 락**을 커밋까지 쥔 채 훅 C를 실행하므로 같은 고객의 판정과 기표는 직렬화된다. 훅 C의 성공 이력 조회가 앞 요청의 커밋을 보는지 동시성 테스트로 검증한다. 멱등키와 유니크 제약으로 같은 이체 요청이 중복 실행되지 않도록 한다. 훅 C에서 조회 예외가 나면 이체 `ERROR`로 확정하며 판정을 건너뛰어 실행하지 않는다.

## 6. XGBoost 행동 위험 모델 — AI 담당

### 6.1 역할

XGBoost는 행동 피처를 받아 **행동 위험 점수**를 산출한다. `hesitationWarning`과 구별된 보조 신호이며, 초기 MVP에서는 `HELD`를 단독 유발하지 않는다. 관리자 화면과 Agent 조사 컨텍스트에 제공한다.

### 6.2 합성 데이터 설계

- 정상: 빠른 이체, 신중한 첫 이체, 금액 정정, 화면 비활성화, 수취인 확인 지연
- 의심: 단계 왕복·재수정·긴 확인 체류의 다양한 조합
- 거래 위험 B: 행동 망설임 없이 반복 송금하는 별도 시나리오
- **규칙 3개 중 2개를 합성 라벨의 유일한 생성 공식으로 사용하지 않음**
- 생성기 시드·시나리오 원형·라벨 이유를 기록
- 동일 시나리오 원형이 학습/평가에 동시에 섞이지 않도록 분할

### 6.3 학습·평가

```text
Python pandas + scikit-learn + xgboost
→ 합성 이벤트 생성
→ flow 단위 피처 생성
→ 학습/검증/시험 분할
→ XGBClassifier 학습
→ 모델 및 피처 명세 저장
→ FastAPI 추론 엔드포인트 제공
```

권장 산출물: `model.json`, `feature_schema.json`, `training_config.json`, `evaluation.json`, 데이터 생성 스크립트. 평가 지표는 Precision, Recall, F1, 혼동행렬, 오탐률. **합성 데이터 성능은 실제 사기 탐지 성능으로 해석하지 않는다.**

### 6.4 추론 연동

MVP에서는 **Python FastAPI에서 XGBoost 추론**하도록 통일해 Python/Java 라이브러리 호환 문제를 줄인다. 다만 이체 경로에서 Python 추론을 필수 동기 호출로 만들면 장애 결합이 생기므로, **서버 A/B 정책은 모델 결과 없이도 작동**해야 한다. 가능하면 FE 이벤트 제출 후 미리 점수를 계산·저장하거나, `HELD` 이후 Agent 조사 시 보조 점수로 제공한다. 모델 점수의 계산 시점과 사용 가능 시점을 API 계약에서 명시한다.

## 7. LangGraph 비동기 보류 사건 조사 Agent — AI 담당

### 7.1 Agent의 목표와 권한

**목표:** 서버가 이미 보류한 거래에 대해 추가 거래 맥락을 능동적으로 조사하고, **서버의 A/B 보류 사유와 구별되는 추가 위험 신호**를 찾아 관리자에게 근거·확인 질문·권고 조치를 제시한다. 서버가 통과시킨 이체는 이 Agent의 조사 범위 밖이다.

**권한:** 승인된 읽기 Tool 호출, 조사 결과 제출. **금지:** 거래 실행, 원장 변경, 계좌 정지, 보류 해제, 자동 거절, 고객 인증 정보 접근.

### 7.2 권장 Tool 설계

기존 설계의 `request_hold_validation`은 **이미 서버가 `HELD`를 확정한 뒤에는 중복 기능**이므로 제거하거나 읽기 전용 검증 Tool로 변경한다.

| Tool | 입력 | 출력 | Agent에게 필요한 이유 |
|---|---|---|---|
| `get_transfer_history` | `transferHoldId`, 제한된 조회 조건 | 최근 성공 이체, 동일 수취인 패턴, 금액·시각 | 반복·분할 송금 맥락 재구성 |
| `get_recipient_context` | `transferHoldId` | 고객 전체 기준 수취인 과거 거래, 최초 거래 시점, 다른 출금계좌에서의 송금 요약 | A/B 규칙과 다른 친숙도·계좌 간 패턴 조사 |
| `get_behavior_summary` *(선택)* | `transferHoldId` | 행동 타임라인·XGBoost 점수·특징 | 서버가 제공한 행동 근거 교차 확인 |

**MVP 권장:** Tool 2개(`get_transfer_history`, `get_recipient_context`) + 행동 요약은 최초 Agent 입력에 포함. 단순히 같은 정보를 두 Tool로 나누는 것만으로는 충분하지 않다. 각 Tool이 서로 다른 조사 질문에 답하도록 API와 결과를 설계한다.

### 7.3 보류 사건 내 추가 발견 예시

서버의 A/B는 동일 수취인·10분·횟수·누적액을 중심으로 한다. Agent는 다음 **추가 맥락**을 검토한다.

1. **금액 분할의 규칙성:** 연속 이체 금액이 동일하거나 일정한 패턴인지.
2. **여러 출금계좌 사용:** 고객의 서로 다른 출금계좌에서 같은 수취인으로 이체가 집중되는지.
3. **수취인 친숙도:** 반복 묶음 이전에 실제 거래가 거의 없었는지.
4. **행동-거래 신호 불일치:** 망설임 점수는 낮지만 반복 송금이 강한지, 또는 망설임은 강하지만 거래 반복 근거는 약한지.
5. **관리자 확인 질문:** 고객이 송금 목적과 수취인 관계를 설명할 수 있는지 등 확인 필요 항목.

이 항목은 **보류 건의 추가 조사 후보 가설**이며, 실제 사기라고 단정하거나 새로운 보류 기준을 자동 집행하지 않는다. 서버 A/B에 이미 사용된 동일 사실을 표현만 바꿔 추가 발견으로 중복 기재하지 않는다. 실제 데이터/API에 없는 정보는 Agent가 추측해서 채우지 않는다.

### 7.4 LangGraph 흐름

```text
START
  ↓
validate_hold_context
  ↓
plan_investigation
  ↓
get_transfer_history
  ↓
assess_information_gap
  ├─ 추가 맥락 필요 → get_recipient_context ─┐
  └─ 추가 맥락 불필요 ───────────────────────┤
                                            ↓
                                    synthesize_findings
                                            ↓
                                    validate_json_schema
                                            ↓
                                     submit_report
                                            ↓
                                           END
```

**Agent다움을 만드는 지점:** `assess_information_gap`에서 조회 결과에 따라 두 번째 Tool 사용 여부와 조사 초점을 결정한다. 다만 재현성을 위해 최대 Tool 호출 횟수·조회 기간·토큰·실행 시간을 제한한다. 시연에서는 두 번째 Tool이 필요한 경우와 필요 없는 경우를 각각 보여주고, **서버 보류 사유와 Agent의 추가 관찰 사실을 별도 영역에 표시**한다.

### 7.5 입력/출력 계약 예시

**Agent 작업 입력:**

```json
{
  "investigationId": "inv-123",
  "transferHoldId": 123,
  "policyCode": "A",
  "behaviorSummary": {
    "hesitationWarning": true,
    "backCount": 1,
    "amountRevisionCount": 2,
    "confirmActiveSeconds": 71,
    "behaviorRiskScore": 0.81,
    "modelVersion": "xgb-demo-v1"
  },
  "transferSummary": {
    "amount": 500000,
    "recipientAccountMasked": "***-**-1234"
  }
}
```

**조사 결과:**

```json
{
  "investigationId": "inv-123",
  "transferHoldId": 123,
  "status": "COMPLETED",
  "secondaryFindings": [
    {
      "code": "REGULAR_SPLIT_AMOUNTS",
      "description": "최근 동일 수취인 송금액이 일정한 금액으로 반복됨",
      "evidenceTransferIds": [101, 102],
      "confidence": "OBSERVED"
    }
  ],
  "missingInformation": [],
  "recommendedAction": "MANUAL_CUSTOMER_CONFIRMATION",
  "suggestedQuestions": [
    "최근 동일 수취인에게 반복 송금한 목적을 확인해 주세요."
  ],
  "summary": "서버 정책 A로 보류되었으며, 조사 결과 금액 분할 패턴이 추가로 확인됨."
}
```

`transferHoldId`와 `evidenceTransferIds`는 각각 P4의 보류 ID와 성공 이체 `refId`에 대응하는 정수 예시다. `secondaryFindings[].confidence`의 허용 값은 `OBSERVED`(조회 결과에서 직접 확인)와 `INFERRED`(조회 사실을 바탕으로 추론)이며, 수치화된 사기 확률이 아니다. Agent는 조회하지 않은 이체 ID를 만들거나 관찰 사실을 사기 확정으로 표현해서는 안 된다. 서버는 JSON Schema뿐 아니라 `evidenceTransferIds`가 **해당 `transferHoldId`의 인증된 고객·허용된 조회 결과에 실제 포함되는지** 검증한 뒤 저장한다. 일치하지 않는 근거는 추가 발견으로 표시하지 않고 조사 오류로 남긴다.

### 7.6 비동기 실행과 장애 처리

- P4는 보류 저장과 같은 커밋에 `TransferHeld`를 발행한다. P6은 기존 이벤트 발행 기록과 연결해 조사 작업을 내구성 있게 등록한다. 단순 '트랜잭션 커밋 후 HTTP 호출'만 사용하면 호출 실패 시 조사 작업이 유실될 수 있다. 별도 `fds_outbox`는 기존 기록만으로 충족되지 않는 요구가 확인될 때만 둔다.
- 작업 키는 `transferHoldId`로 고정한다. 조사 작업 테이블에 `transfer_hold_id` 유니크 제약을 두고, 최초 생성한 `investigationId`를 같은 보류 건의 이벤트 재전달·워커 재시도에 재사용한다.
- `TransferHeld` 리스너는 조사 작업 행 커밋이 끝난 뒤에만 성공을 반환한다. 작업 큐 전달은 그 커밋 뒤에 한다. 작업 저장 실패 시 리스너가 실패해 이벤트 기록이 재전달되도록 하고, 저장 실패·재전달·중복 사건 각각을 검증한다.
- `QUEUED → RUNNING → COMPLETED / FAILED` 상태를 관리한다.
- Agent 오류·타임아웃은 거래 `HELD` 상태를 변경하지 않는다.
- 재시도는 제한 횟수·백오프를 적용하고, 최종 실패 시 관리자가 서버 정책 근거만으로 검토할 수 있게 한다.
- 동일 `HELD`에 중복 보고서가 생기지 않도록 버전/유니크 키를 둔다.
- LLM 출력은 검증되지 않은 텍스트로 취급하며 DB·API 권한 판단에 사용하지 않는다.

### 7.7 보안

Tool은 사용자 임의 고객 ID 대신 **서버가 발급한 `transferHoldId`**를 받아 인증·인가된 내부 API를 통해 데이터 범위를 제한한다. 서비스 간 인증, 최소 권한, 계좌번호 마스킹, 프롬프트 인젝션 대비(거래 메모·외부 문자열을 지시문으로 취급하지 않음), 개인정보 최소 전송, 로그 보존 정책을 적용한다.

## 8. 실제 이체 보류·관리자 승인 설계 — BE 담당 중심

### 8.1 상태 모델

**이체 보류 상태** (`transfer.status`와 별도):

```text
이체 요청
  ├─ 정상 → 기존 이체 실행 → SUCCESS / ERROR / TIMEOUT
  └─ 위험 → HELD
              ├─ 관리자 승인 → EXECUTING → EXECUTED / FAILED
              ├─ 관리자 거절 → REJECTED
              ├─ 고객 취소 → CANCELLED
              └─ 만료 → EXPIRED
```

보류 건이 실행되면 별도 `transfer` 행에 `SUCCESS` 또는 `ERROR`가 남는다. **`HELD`는 `transfer.status` 값이 아니다.** 실행은 `transferType=IMMEDIATE`, `source_type=HELD`, `source_id=보류 ID`로 기존 `execute()`를 한 번 호출하며, 원장 거래유형과 GL 매핑은 그대로다. 기존 `uk_transfer_source_execution_date`가 중복 실행을 막는다. P4의 `AT_TIME`은 해제 시각에 실행하고, `ON_APPROVAL`은 보류한 영업일 안에 승인되지 않으면 만료된다. 이번 #772는 `AT_TIME`을 구현하고 `ON_APPROVAL` 만료·관리자 흐름은 FDS 착수 때 구현한다. 보류 중 출금·입금·원장 기표는 없어야 한다.

**조사 상태:** `QUEUED`, `RUNNING`, `COMPLETED`, `FAILED` (거래 상태와 독립).

### 8.2 데이터 소유권과 P6 저장 모델

`transfer_hold`와 원본 요청·보류 상태 전이·`TransferHeld`는 P4 소유다. 아래 P4 항목은 P6이 새 테이블을 설계하는 지시가 아니며, 컬럼·제약의 정본은 [transfer_seam.md §9](transfer_seam.md#9-훅-c--이체-보류-771)와 #772 구현을 따른다.

```text
transfer_hold
  P4 소유: 원본 요청·요청 지문·인증 완료 시각·정책 코드·해제 방식/시각·flowId·보류 상태

fds_behavior_flow / fds_behavior_event
  flow_id, customer_id, event fields, derived features

P6 성공 이체·행동 연결 (테이블명 미정)
  성공 transfer ref_id (UNIQUE), flow_id; P4 TransferSettled.flowId 추가 PR 머지 뒤 리스너 연결

fds_investigation
  investigation_id (PK), transfer_hold_id (UNIQUE)
  investigation_status, attempt_count
  agent_version, model_version
  secondary_findings_json, summary, error_code
  created_at, completed_at

P6 조사 작업 (테이블명 미정)
  transfer_hold_id (UNIQUE), investigation_id (안정적인 작업 ID), 상태, 시도 횟수, 다음 재시도 시각

fds_audit_log
  actor, action, transfer_hold_id, before_status, after_status, occurred_at (FDS 상세 보조 기록)
```

개인정보·계좌정보 저장은 기존 암호화·접근 제어 정책을 따른다. P6은 기존 이벤트 발행 기록과 조사 작업 저장의 경계를 확인하고, 별도 `fds_outbox`는 충족되지 않는 요구가 있을 때만 추가한다. 새 스키마가 확정되면 Flyway 증분 파일·`schema_reference.md`·`corebank_erd.md`를 함께 갱신한다.

관리자 콜 결과 기록·승인·거절 등 변경은 기존 `AuditLog`에 기록한다. `fds_audit_log`는 보류 상태 전이의 상세 보조 기록이며 기존 `AuditLog`를 대체하지 않는다. 업무 변경·`AuditLog`·해당 FDS 보조 기록은 같은 트랜잭션에서 커밋하거나 함께 롤백한다.

P4는 `transferHoldId`로 원본 요청·상태를 읽는 `transfer.api` 조회 계약을 제공한다(조회 구현은 FDS 착수 때). P6은 A/B 판정 근거·행동 요약·Agent 읽기 Tool을 소유하며 P4의 영속성 구현을 직접 참조하지 않는다. FDS 훅 C는 지연이체보다 낮은 `order`로 승인 보류를 우선 판정한다. 비활성 스위치에서는 DB 조회 없이 `proceed()`한다.

### 8.3 관리자 업무

1. `HELD` 목록과 정책 A/B 근거 확인
2. AI 조사 상태·추가 발견·증거 조회
3. 아웃바운드 콜을 **관리자가 직접 수행**하고 결과 기록
4. 승인 또는 거절 선택
5. 서버가 관리자 권한, 콜 결과 필수 여부, 상태 전이 가능 여부 검증
6. 승인 시 현재 계좌 상태·잔액·한도·중복 실행 여부 재검증
7. P4 `release()`가 `EXECUTING`으로 선점한 뒤 토큰 없는 내부 `execute()`로 원본 요청을 한 번 실행하고 결과·감사 기록 저장

`ON_APPROVAL` 건은 보류한 영업일이 지나면 `EXPIRED`로 종료한다. 승인된 건은 지연이체 설정이 함께 해당해도 다시 지연하지 않고 즉시 실행한다. P4 #772는 `AT_TIME`만 구현하므로 만료·관리자 연동은 FDS 착수 범위에 포함한다.

AI 조사 상태는 관리자 승인 가능 여부와 별개다. `QUEUED`·`RUNNING`·`FAILED` 상태에서도 관리자는 **서버 A/B 근거와 고객 콜 결과만으로** 검토·승인 또는 거절할 수 있다. 이 경우 AI 추가 발견이 아직 없거나 실패했다고 명시하고 감사 기록에 남긴다. AI 보고서가 늦다는 이유만으로 보류 해제 절차를 무기한 멈추지 않는다.

### 8.4 보류 시 OTP 소비와 고객 재인증 없는 승인 실행

**이번 프로젝트에서는 관리자 승인 후 고객 재인증을 요구하지 않는다.** 일반 즉시이체의 검증 순서를 유지해 계좌비밀번호 토큰과 OTP를 훅 C 판정 전에 소비한다. 정책 A/B가 성립하면 P4는 기표 트랜잭션을 롤백하고 새 트랜잭션에서 **변경 불가능한 원본 요청**과 `TransferHeld`를 함께 저장한다. 보류 중 원장 기표·출금·입금은 없다. 토큰 원문은 저장하지 않는다. 보류 저장이 실패하면 `transfer`에 ERROR 행을 남기고 실패 응답을 돌려준다. 이미 소비된 토큰 때문에 같은 멱등 키 재요청도 인증 토큰 오류로 끝나고 보류·기표가 생기지 않는다. 고객은 다시 인증해 새 요청을 보낸다([transfer_seam.md §9-3](transfer_seam.md#9-3-hold일-때-p4가-보장하는-것)).

관리자는 보류 요청의 고객·출금계좌·수취계좌·금액을 수정할 수 없고 **원본 요청 그대로 승인 또는 거절**한다. 변경이 필요하면 기존 보류 건을 종료하고 고객이 새 요청을 시작해 다시 인증한다. P6은 관리자 권한·콜 결과를 먼저 확인한다. P4의 `release()`는 보류 행을 `HELD → EXECUTING`으로 조건부 선점하고 원본 요청의 `sourceId`에 보류 ID를 넣어 토큰 없이 내부 `execute()`를 호출한다. `execute()`는 인증을 건너뛰기 전에 보류 행이 `EXECUTING`인지, 출금계좌·수취계좌번호·금액이 원본과 같은지 확인한다. 일반 고객 즉시이체는 두 토큰이 필수이며, 토큰과 `sourceId`를 함께 보내도 거부한다. 실행 시 잔액·한도·계좌 상태를 다시 검사하고, `source_type=HELD`로 한 번 기표한다. HTTP 요청은 `sourceId`를 받지 않는다([transfer_seam.md §9-4](transfer_seam.md#9-4-실행거절취소)).

P4의 토큰 소비·보류 저장·해제 계약은 문서로 확정됐으며, #772와 FDS 구현·테스트 통과 여부는 별도로 확인한다. P6은 관리자 권한·콜 결과·조사 작업의 내구성·내부 API 인증을 구현한다. 문서 계약만으로 재인증 없는 실행이 실제 동작한다고 발표하지 않는다.

### 8.5 정확히 한 번 실행

관리자 승인 중복 클릭, 네트워크 재시도, 동시 승인, 실행 성공 후 응답 유실을 테스트한다. 상태 조건부 변경(`HELD → EXECUTING`), 기존 이체 멱등키, 실행 결과 연결, 재시도 시 상태 조회를 결합한다. 단순한 프런트 버튼 비활성화만으로는 충분하지 않다. 이체 실행 트랜잭션과 보류 상태 업데이트가 분리될 경우 결과 불명 상태를 안전하게 조정해야 한다.

## 9. API 계약 초안

> 아래 URL은 **컨트롤러 매핑 기준 초안**이다. 외부 호출에는 서버의 `/api/v1` 컨텍스트 경로를 앞에 붙인다(예: `/api/v1/transfers`). `TransferHeld`, 훅 C, `flowId`를 이체 요청 지문에 넣는 규칙은 P4 계약이며, P6 API 경로·필드는 구현 전에 확정한다.

| 호출 | 경로 | 주요 기능 |
|---|---|---|
| FE → BE | `POST /fds/behavior-flows/{flowId}/events` | 이벤트 일괄 저장 |
| FE → BE | `POST /transfers` | 기존 즉시이체 + 선택 `flowId`, 멱등키 |
| BE → FE | 이체 응답 | 정상 실행 또는 `HELD` + `transferHoldId` |
| 내부 작업 | `TransferHeld` 이벤트 → P6 조사 작업 | P4 보류 저장·발행은 같은 커밋, P6 작업 등록·재시도는 별도 설계 |
| AI → BE | `GET /internal/fds/holds/{transferHoldId}/history` | Tool 1 거래 이력 |
| AI → BE | `GET /internal/fds/holds/{transferHoldId}/recipient-context` | Tool 2 수취인 맥락 |
| AI → BE | `PUT /internal/fds/investigations/{investigationId}/report` | 조사 결과 멱등 저장 |
| 관리자 | `GET /admin/fds/holds` | 목록 |
| 관리자 | `GET /admin/fds/holds/{transferHoldId}` | 상세·조사 결과 |
| 관리자 | `POST /admin/fds/holds/{transferHoldId}/call-record` | 콜 결과 |
| 관리자 | `POST /admin/fds/holds/{transferHoldId}/approve` | P6 권한·콜 결과 확인 후 P4 `release()` 호출 |
| 관리자 | `POST /admin/fds/holds/{transferHoldId}/reject` | P6 권한 확인 후 P4 `reject()` 호출 |

보류 목록·상세 API는 고객 식별 정보와 이체 맥락을 반환하는 고객 개인정보 조회로 분류해 `X-Access-Reason` 헤더, `AccessReason` 유효값 검증, 조회 감사 기록을 적용한다. 콜 결과 기록 API는 고객 확인 결과를 변경하므로 같은 사유 헤더·검증과 기존 `AuditLog`를 적용한다. 승인·거절 API는 고객 개인정보를 응답으로 반환하지 않는 관리자 변경으로 설계하고 기존 `AuditLog`를 적용한다. 승인·거절 응답에 개인정보가 추가되면 조회 사유 적용 범위를 다시 검토한다.

### API 합의 체크리스트

- 기존 응답 래퍼·HTTP 상태·오류 코드 규약
- FE 이체 요청의 멱등키와 `flowId`를 포함한 요청 지문(`fingerprint`) 적용 확인
- `flowId` 소유권과 이벤트 마감 시점
- `HELD` 응답을 FE가 어떻게 표시할지
- 보류 요청에 원래 이체 의도를 안전하게 보존하는 방식
- 내부 API 서비스 인증 및 마스킹
- Agent 작업 발행·재시도·결과 저장의 멱등성
- 승인 후 실행 실패/응답 불명 시 처리 계약

## 10. 6인 팀 개발 공수 및 일정

### 10.1 추정 전제

- 기존 React·Spring Boot·MySQL 즉시이체를 최대한 재사용한다.
- FE/BE/AI가 API 계약 확정 후 **병렬 작업**한다.
- XGBoost는 합성 데이터로 학습하고 모델은 보조 신호로 사용한다.
- Agent는 LangGraph **단일 Agent, 핵심 Tool 2개**, 관리자 화면은 최소 범위다.
- 실제 운영 보안 심사, 외부 콜 시스템, 타행 연동, 부하 시험은 제외한다.
- **인일은 작업량**이고 **영업일은 달력상 소요 기간**이다. 둘을 혼동하지 않는다.

### 10.2 기능별 공수 (축소형 MVP)

| 작업 | 주 담당 | 예상 인일 | 병렬 가능성 |
|---|---|---:|---|
| API·인증·보류 계약 확정 | BE + AI + FE | 1.5~2 | 선행 필수 |
| FE 7종 이벤트 계측 | FE | 2~3 | 가능 |
| 이벤트 저장·피처 API | BE | 1.5~2 | 가능 |
| 합성 데이터·XGBoost | **AI** | 2~3 | 가능 |
| FastAPI·LangGraph | **AI** | 2~3 | 가능 |
| Agent Tool·내부 API 연동 | **AI + BE** | 2~3 | 계약 이후 |
| 서버 정책 A/B·동시성 기본 | BE | 1.5~2.5 | 가능 |

**지연 시 처리:** #772 PR-a가 11/2 목표보다 늦으면 해당 보류 통합만 목 계약으로 유지하고 Python Agent·FE·순수 정책 로직을 진행한다. P4의 원본·상태 조회 제공이 늦으면 Agent Tool을 목 조회로 검증하고 실제 연동은 미완료로 기록한다. `TransferSettled.flowId`가 늦으면 정책 B를 `RecentTransferQuery`만으로 검증하고, 과거 이체의 망설임까지 보는 정책 A는 완료로 표시하지 않는다. 필수 부품이 11/11까지 없으면 실제 보류→조사→승인 E2E도 완료로 표시하지 않고, 구현된 범위와 남은 의존성을 테스트 인계에 적는다. 기존 15~20영업일 추정에 비해 압축된 일정이므로 시각화·상세 모델 비교를 먼저 줄이고 인증·멱등·원장 검증은 생략하지 않는다.

### 10.5 핵심 의사결정 게이트

보류·토큰·재실행의 **문서 계약은 PR #780에 반영됐다.** 구현·통합 단계에서 아래 항목을 검증한다.

1. 기존 이체 서비스가 **원장 기표 전에** `HELD`로 분기 가능한가?
2. 보류 상태에서 잔액·원장·입금이 변경되지 않는가?
3. 판정 전 토큰 소비 뒤 보류 저장에 실패하면 `transfer` ERROR·실패 응답이 남고, 같은 멱등 키 재요청은 토큰 오류로 끝나는가? `EXECUTING` 보류 행만 **토큰 없이 `execute()`**할 수 있는가?
4. 중복 승인·재시도에 대한 멱등키를 설계할 수 있는가?
5. 서버 `HELD` 이후 Agent 조사 이벤트를 안전하게 전달할 수 있는가?

1~4가 구현에서 성립하지 않으면 Agent 통합보다 **이체 실행 경계 및 인증 구현**이 우선이다. 발표 시연을 위해 금융 정합성을 희생해서는 안 된다.

## 13. 발표 시연 시나리오

### 시나리오 A — 망설임 + 신규 수취인 반복 이체

1. 신규 수취인에게 50만 원씩 2회 이체 성공.
2. 세 번째 50만 원 이체에서 뒤로 가기 1회 + 금액 재수정 2회 발생.
3. 서버가 반복 묶음의 망설임·신규 수취인·3회·150만 원을 확인.
4. **세 번째 요청만 `HELD`**, 잔액·원장 불변 확인.
5. Agent 비동기 실행 → 거래 이력 Tool 호출 → 필요 시 수취인 맥락 Tool 호출.
6. 관리자 화면에서 **서버 A 보류 사유**와 Agent가 관찰한 **추가 금액 패턴**을 분리해 보여준다.
7. 관리자 콜 결과 기록과 권한 확인 후 `release()`가 보류 건을 `EXECUTING`으로 선점 → 토큰 없이 `execute()` 호출 → 보류 행 상태와 원본 출금계좌·수취계좌번호·금액 확인 → 최신 잔액·한도·계좌 상태 재검증 후 한 번 기표. 고객 재인증·OTP 재사용 없음.

### 시나리오 B — 망설임 없는 강한 반복 이체

1. 동일 수취인에게 100만 원씩 2회 성공.
2. 세 번째 100만 원 요청, 망설임 없음.
3. 서버가 정책 B(3회·300만 원)를 검증해 **즉시 `HELD`**.
4. Agent가 추가 맥락 조사, 관리자 화면에 보류 근거와 조사 결과를 분리 표시.
5. 관리자 거절 → 원장 불변.

### 시나리오 C — 정상 거래

1. 단건 또는 A/B 미충족 이체 요청.
2. 서버 정상 실행, `HELD` 및 Agent 조사 작업 생성 없음.
3. 망설임만 있는 경우 행동 신호는 기록하되 보류하지 않음.

### 시나리오 D — AI 장애

1. 정책 A/B 충족 → 서버 `HELD` 성공.
2. Python Agent 호출 실패 또는 응답 지연.
3. `HELD` 유지, 조사 상태 `FAILED` 또는 재시도 대기.
4. 관리자는 서버 정책 근거만으로 수동 검토 가능.
5. AI 장애로 거래가 자동 실행되거나 자동 거절되지 않음.

**시연 데이터:** 실제 10분을 기다리지 않도록 고정 시계·테스트 픽스처·관리자용 데모 데이터 시드를 사용한다. 운영 데이터 조작과 혼동되지 않도록 테스트 환경에서만 활성화한다.

### 15.1 채택 결론

**최종 채택:** `Spring Boot 실시간 탐지·보류 + LangGraph 비동기 보류 사건 추가 위험 신호 조사 Agent`.

- `PENDING_REVIEW`는 구현하지 않는다.
- 서버가 **AI 조사 전** 위험 이체를 `HELD`로 확정한다.

- AI 장애가 발생해도 보류는 유지된다.
