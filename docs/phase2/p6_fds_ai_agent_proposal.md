## 1. 검토 결론과 배경

**결론:** P6은 `transfer`의 당행 즉시이체에서 **서버의 실행 전 탐지·보류**와 **Agent의 보류 사건 추가 조사**를 연결하는 비교 평가 시연판으로 추진한다. AI가 계좌나 원장을 직접 조작하지 않으며, 보류 건의 최종 승인·거절은 관리자가 담당한다. 보류·토큰·재실행의 P4 계약은 [transfer_seam.md §9](transfer_seam.md#9-훅-c--이체-보류-771)에 정해졌고, P6은 행동 수집·A/B 정책·조사·관리자 연동의 세부 계약과 구현을 남겨 두고 있다.

□ **단건 거래 정보만으로는 반복 송금과 이체 전 행동을 설명하기 어렵다**

○ 한 건의 금액·수취인만 보는 판단은 같은 수취인에게 짧은 시간에 나누어 보내는 상황을 놓칠 수 있다.

○ 사회공학 사기 결제의 행동 신호를 분석한 [Lund University 연구](https://lup.lub.lu.se/student-papers/search/publication/9233794)는 조작된 세션이 주요 승인 단계에서 일반적으로 더 느린 경향을 보고했다. 이를 우리 즉시이체 화면의 **확인 단계 체류 시간**을 시험할 근거로 사용한다. 특정 시간 기준이나 실제 보이스피싱 탐지 성능을 입증한 자료로 해석하지 않는다.

○ [원격뱅킹 시퀀스 탐지 연구](https://www.icommercecentral.com/open-access/remote-banking-fraud-detection-framework-using-sequence-learners.php?aid=87545)는 로그인→수취인 추가→결제의 화면 흐름을 순서대로 표현하고, **화면별 체류 시간(dwell time)**과 **화면 간 이동 시간(flight time)**을 탐지 입력으로 사용했다. 이는 D-01·D-02의 단계 이동과 확인 화면 체류를 `flowId`별 행동 피처로 계측하는 설계에 참고할 수 있다.

○ [금융감독원 보이스피싱 피해 사례](https://eiec.kdi.re.kr/policy/materialView.do?num=215555)에는 피해자가 여러 차례 송금한 사례가 있다. **반복 송금**을 후보 시나리오로 채택하는 근거이며, 본 제안의 `10분·3회·150만 원` 기준을 검증한 자료는 아니다.

□ **AI가 발견한 위험과 실제 자금 이동의 책임을 분리해야 한다**

○ 정상 고객도 처음 송금하거나 꼼꼼히 확인할 때 오래 머무를 수 있다. 행동 망설임만으로 이체를 취소하거나 계좌를 정지시키지 않는다.

○ [카카오뱅크의 시퀀스 기반 FDS 사례](https://tech.kakaobank.com/posts/2606-sequence-based-fds-model/)처럼 거래 앞선 행동 흐름을 보되, 이번 프로젝트는 실제 피해 라벨이 없으므로 **합성 시나리오 기반 구현·비교 시연**으로 범위를 한정한다.

### 세 구현 수준 중 비교 평가·관리자 대응 시연판을 고른 이유

| 선택지 | 보여줄 수 있는 결과 | 이번 과제에서의 판단 |
| --- | --- | --- |
| 화면 목업 | 행동 점수와 경고 화면 | 실제 보류·원장 미기표와 관리자 승인 흐름을 검증할 수 없음 |
| **비교 평가·관리자 대응 시연판 — 선택** | 합성 행동 모델·규칙 비교, 실제 `HELD`, Agent 추가 조사, 관리자 승인·거절 | 기술 효과와 자금 정합성, Agent의 역할을 함께 보여줄 수 있음 |
| 카카오뱅크 ViT 구조 재현 | 복잡한 시퀀스 모델 구현 | 실제 행동 로그·피해 라벨이 없어 성능 일반화를 확인할 수 없고 11월 발표 일정에 맞지 않음 |

과거의 **7~10일** 추정은 FE 목 화면·합성 데이터 중심의 축약 데모였다. 이 제안은 실제 BE 보류·OTP·관리자 재실행과 비동기 Agent를 포함하므로 **15~20영업일의 팀 병렬 일정**으로 별도 산정한다.

**이번 범위의 제외 항목:** 실제 사기 탐지율 입증, 타행·예약·자동이체, AI의 계좌 정지·자동 거절·원장 기표, 자동 아웃바운드 콜, 외부 금융 데이터 조회, ViT·다중 Agent·RAG·MCP 서버, 관리자 승인 후 고객 재인증과 OTP 토큰 재사용. 발표 시나리오는 합성 데이터와 테스트 환경에서 재현한다.

## 3. 대상이 `transfer` 하나인 이유

즉시이체는 고객이 D-01 정보 입력에서 D-02 확인·인증으로 이동한 뒤 곧바로 실행을 요청하므로, 화면 행동과 특정 이체 요청을 `flowId`로 연결할 수 있다. 기존 BE에는 당행 즉시이체의 출금계좌·수취계좌·금액, 완료 이력, OTP 검증, 멱등 처리, 원장 기표 흐름이 있다. 따라서 **FE 행동 → 현재 이체 → 이전 성공 이체 → 보류 여부**를 하나의 경로로 검증할 수 있다.

`auto_transfer`와 `scheduled_transfer`는 고객이 등록할 때와 실제 이체가 실행될 때가 분리되어 동일한 망설임 시퀀스를 적용하기 어렵다. 타행이체는 별도 수취계좌·은행코드 및 대외 응답 불명 처리 계약이 있어 이번 범위에서 제외한다. 대상은 **고객 주도 당행 즉시이체 한 종류**로 고정한다.

## 4. FE 필수 이벤트 7개와 선정 이유

각 이벤트는 `flowId`, `seqNo`, `eventType`, 실제 시각 `occurredAt`, 화면 단계 `step`을 포함한다. 비밀번호·OTP·계좌번호·메모 원문은 행동 이벤트에 넣지 않는다. `occurredAt`은 실제 시각으로 기록하고, 활성 체류 시간은 `performance.now()`의 경과 시간으로 계산한다. 브라우저 비활성 시간은 확인 화면 체류에서 제외한다.

| 이벤트 | 수집 시점 | 파생 신호에 필요한 이유 |
| --- | --- | --- |
| `TRANSFER_ENTER` | 즉시이체 화면 첫 진입 | 흐름의 시작과 전체 소요 시간 |
| `RECIPIENT_CONFIRMED` | 수취계좌 확인 성공 | 수취인 확인까지 걸린 시간 |
| `AMOUNT_EDITED` | 최초 확정 금액을 다시 수정 완료 | 재수정 횟수·간격. 숫자 키마다 기록하지 않음 |
| `STEP_BACK` | D-02에서 D-01로 복귀 | 입력·확인 단계 왕복 횟수 |
| `CONFIRM_ENTER` | D-02 진입·재진입 | 확인 화면 체류 시작 |
| `CONFIRM_LEAVE` | D-02 이탈·인증 절차 이동 | 체류 종료. ‘이전’에서는 `STEP_BACK`과 함께 기록 |
| `SUBMIT_REQUESTED` | OTP 인증 후 실제 이체 요청 직전 | 행동 흐름과 실행 요청 연결 |

정상 이체에서도 대부분의 이벤트가 발생하므로 **7개 중 발생한 개수**를 위험도로 사용하지 않는다. 서버는 FE가 보낸 고객 ID·위험 점수를 신뢰하지 않고, 인증 고객의 `flowId` 소유권과 이벤트 순서·중복·허용 시간 범위를 검증한다.

서버가 계산·저장할 파생값은 `backCount`, `amountRevisionCount`, `confirmActiveSeconds`, `recipientConfirmSeconds`, `totalFlowSeconds`, `hesitationWarning`이다. Python 모델이 별도로 계산한 `behaviorRiskScore`에는 모델·피처 버전을 함께 남긴다. `(flowId, seqNo)` 중복을 막고 이벤트 수·크기·시간 범위를 제한한다. 브라우저에서 보낸 시각·체류값은 조작될 수 있으므로 서버 수신 시각과 비교해 비정상적 순서·범위를 걸러낸다. FE 이벤트가 누락돼도 §5의 정책 B는 거래 이력만으로 검사한다.

## 5. 탐지 판정과 관리자 검토 정책

□ **서비스 개요와 업무 흐름**

1. React 즉시이체 화면에서 §4의 **7종 이벤트**를 `flowId`로 묶는다.
2. Spring Boot가 이체 실행 직전 행동 망설임 규칙과 고객 전체의 성공 이체 이력을 조회한다. 현재 요청을 포함해 정책 A/B를 판정한다.
3. 계좌비밀번호 토큰과 OTP를 판정 전에 소비한다. 의심 조건이 성립하면 훅 C에서 기표 트랜잭션을 롤백하고 새 트랜잭션에 **원본 이체 요청을 `HELD`로 저장**한다. 출금·입금·원장 기표는 하지 않는다.
4. 보류 사건 생성과 함께 Python/FastAPI의 LangGraph Agent 조사 작업을 비동기로 등록한다. Agent는 허용된 읽기 Tool로 거래 이력과 수취인 맥락을 조사한다.
5. 관리자 화면에 **서버의 A/B 보류 사유**와 **Agent의 추가 관찰 사실·확인 질문**을 구분해 표시한다. 관리자가 직접 아웃바운드 콜을 하고 결과를 기록한다.
6. 관리자가 보류한 영업일 안에 원본 요청 그대로 승인하면 `release()`가 보류 건을 `EXECUTING`으로 선점하고 토큰 없이 `execute()`를 호출한다. `execute()`는 보류 행의 상태와 원본 계좌·수취인·금액을 확인한 뒤 최신 잔액·한도·계좌 상태를 재검증해 **한 번만 즉시 실행**한다. 지연이체 설정이 함께 해당해도 다시 지연하지 않는다. 거절하면 미기표 상태로 종료한다.

```text
React FE ──7종 이벤트·즉시이체 요청──▶ Spring Boot
                                        └─ 계좌비밀번호 토큰·OTP 소비 (A/B 판정 전)
                                           └─ 한도 적립 → 훅 C에서 A/B 판정
                                              ├─ 불성립 → 기존 이체 실행
                                              └─ 성립 → 기표 트랜잭션 롤백 → 새 트랜잭션에 HELD 저장(미기표)
                                                                  ├─ 비동기 조사 작업 → Python Agent → 조사 보고서
                                                                  └─ 관리자 콜·승인 → release() → execute() → 1회 기표
```

`PENDING_REVIEW` 상태는 만들지 않는다. **이체 보류 상태**는 `HELD → EXECUTING → EXECUTED / FAILED` 또는 `HELD → REJECTED / CANCELLED / EXPIRED`로, **AI 조사 상태**는 `QUEUED → RUNNING → COMPLETED / FAILED`로 각각 관리한다. 실행된 이체의 `transfer.status=SUCCESS / ERROR`는 보류 상태와 별개다. AI 조사 결과가 없어도 보류 상태는 유지된다.

□ **서버 1차 보류 정책과 Agent 역할**

| 구분 | 초기 시연 조건 또는 역할 |
| --- | --- |
| 망설임 경고 | 확인 단계 복귀 1회 이상, 확정 금액 재수정 2회 이상, 확인 화면 활성 체류 60초 이상 중 **2개 이상** |
| 정책 A | 반복 묶음에 망설임 경고가 있고, 묶음 시작 전 처음 보는 수취인에게 **10분 내 3회 이상·누적 150만 원 이상** 송금 시도 |
| 정책 B | 망설임·신규 수취인 여부와 관계없이 동일 수취인에게 **10분 내 3회 이상·누적 300만 원 이상** 송금 시도 |
| XGBoost | 합성 행동 데이터로 학습해 위험 점수를 산출한다. **초기 보류의 필수 조건은 아니며** 관리자 참고·규칙 대비 비교에 사용 |
| LangGraph Agent | **이미 `HELD`인 사건만** 추가 조사한다. 서버 A/B에 없는 관찰 사실과 관리자 확인 질문을 제시하며 보류·실행·거절을 직접 수행하지 않음 |

○ A/B의 건수와 누적액에는 **현재 미실행 요청**을 포함한다. 반복 묶음의 앞선 성공 이체는 되돌리지 않으며, 세 번째 요청을 실행 전에 보류한다.

10분 창은 `TransferHoldContext.requestedAt` 기준 **`[requestedAt - 10분, requestedAt)`**이다. 시작 시각의 성공 이체는 포함하고 요청 시각과 그 이후는 제외한다. 현재 요청은 조회 결과에 포함하지 않고 아래 계산에서 한 번만 더한다. T08은 시작 경계 포함·그 직전 제외·끝 경계 제외를 검증한다.

서버 집계는 **같은 고객의 전체 출금계좌 → 같은 수취계좌**를 기준으로 한다. P4의 `RecentTransferQuery`로 당행 즉시·예약·자동이체의 커밋된 `SUCCESS`를 출금계좌별로 조회하고, 정정 체인에서 무효화된 행(`invalidated_at`)은 제외한다. `count10m = 직전 10분 성공 이체 건수 + 현재 요청 1건`, `amount10m = 직전 10분 성공 이체 금액 합계 + 현재 요청 금액`으로 계산한다. 실패·취소·거절·기존 보류 건은 성공 이체 건수에 넣지 않는다. A를 먼저 검사하고 불성립할 때 B를 검사해, 한 요청에 보류 건이 두 개 생기지 않게 한다. 망설임은 **현재 요청 또는 같은 반복 묶음의 앞선 성공 이체 중 한 번 이상** 관측됐는지 본다.

○ 신규 수취인은 세 번째 이체 직전이 아니라 **반복 묶음 첫 이체 이전**의 성공 이력으로 판단한다. 과거 거래가 있다는 사실만으로 수취인을 안전하다고 확정하지 않는다.

○ 정책 A의 앞선 성공 이체와 `flowId` 연결은 P6이 별도 저장한다. P4가 `TransferSettled`에 nullable `flowId`를 추가한 PR이 **머지된 뒤** 성공 이벤트 리스너를 연결한다. `refId`(성공 이체 ID)를 키로 중복 저장을 막는다. 커밋 후 이벤트 처리 지연으로 앞선 연결이 잠시 보이지 않을 수 있으므로, 이 경우에도 정책 B는 `RecentTransferQuery`만으로 독립 판정한다. `transfer`에는 `flowId` 컬럼을 추가하지 않는다.

○ Agent는 서버가 통과시킨 거래를 다시 탐지하지 않는다. 본 제안의 차별점은 **보류 사건 안에서 추가 맥락을 조건부로 조회하고, 서버 보류 사유와 구별되는 근거를 관리자에게 제공**하는 데 있다.

□ **관리자에게 올리는 기준과 권한 경계**

○ 망설임 경고 또는 XGBoost 점수는 수취인 이력과 무관하게 기록한다. **망설임만으로 관리자 검토 건이나 보류 상태를 만들지 않는다.** A 또는 B가 성립할 때만 현재 요청을 `HELD`로 만들고 검토 건을 생성한다.

○ `HELD`와 조사 작업 상태(`QUEUED`·`RUNNING`·`COMPLETED`·`FAILED`)는 별도로 관리한다. AI가 늦거나 실패해도 보류는 유지되며, 관리자는 서버의 보류 근거와 직접 기록한 고객 콜 결과로 승인·거절할 수 있다.

○ FE 행동 이벤트나 Python 모델 결과가 누락되면 망설임 조건을 충족한 것으로 추정하지 않는다. **거래 이력만으로 판단 가능한 B는 계속 검사**한다. 훅 C에서 조회 예외가 나면 P4 계약대로 이체 `ERROR`로 확정하고, 판정을 건너뛰어 실행하지 않는다.

○ `ON_APPROVAL` 보류 건은 **보류한 영업일 안에 승인되지 않으면 `EXPIRED`**로 종료한다. P4 #772는 `AT_TIME`만 다루며, FDS 착수 때 승인 절차와 함께 이 만료 처리를 구현한다.

○ 관리자는 보류된 이체의 출금계좌·수취계좌·금액을 수정하지 않는다. AI는 거래 실행·보류 해제·계좌 정지·자동 거절 권한을 갖지 않는다.

○ 승인된 원본 요청이 실행될 때 **현재의** 잔액·한도·계좌 상태가 바뀌어 있다면 실행을 거부하고 실패 사유를 기록한다. 관리자 승인 클릭이나 네트워크 재시도가 반복돼도 원장 기표는 한 번만 허용한다. `HELD → EXECUTING`은 상태 조건부 갱신으로 전이하고, 실행 성공 후 응답이 유실되면 기존 멱등키와 결과 연결 정보를 조회해 이중 출금을 피한다.

## 6. 모델·Agent 선택과 실현 가능성

□ **ViT 대신 XGBoost, Java 추론 대신 Python 서비스**

카카오뱅크의 ViT 변형 모델은 대규모 앱·거래 시퀀스와 실제 피해 라벨을 전제로 한다. 우리 프로젝트에는 그 데이터가 없고, 이번 FE 이벤트는 왕복 횟수·재수정 횟수·확인 체류 초처럼 **소수의 표형 피처**로 표현된다. 따라서 Python에서 합성 정상·의심 시퀀스를 만들고 경량 XGBoost로 행동 위험 점수를 학습·평가한다. ‘3개 중 2개’ 규칙을 합성 라벨의 유일한 공식으로 사용하지 않고, 정상 망설임·망설임 없는 의심 사례를 별도 평가셋에 포함한다.

학습과 추론은 모두 Python에서 수행한다. FastAPI가 `model.json`과 버전이 붙은 피처 명세를 읽어 점수를 산출한다. 이 점수는 **사기 확률이 아니며** 초기 A/B 보류 조건의 필수 입력도 아니다. Python 장애 시 Spring Boot가 독립적으로 A/B를 판정한다. 일정이 부족하면 XGBoost의 상세 비교·시각화부터 줄이고 보류·승인 흐름을 우선한다.

모델 점수는 FE 이벤트 제출 후 미리 계산·저장하거나 `HELD` 이후 조사 중 계산한다. **언제 점수가 준비되는지**를 계약으로 고정하고, 점수가 아직 없으면 관리자 화면에 '분석 대기'로 표시한다. 발표에서 보이는 점수를 이체 전 보류 판단에 사용한 것처럼 설명하지 않는다.

합성 데이터는 빠른 정상 이체뿐 아니라 **신중한 첫 이체·금액 정정·수취인 확인 지연·화면 비활성화**를 정상 사례로 포함한다. 의심 사례에는 왕복·재수정·긴 체류의 여러 조합을 넣고, 망설임 없는 반복 이체를 정책 B 검증용으로 따로 둔다. 생성기 시드·시나리오 원형·라벨 이유를 저장하고 원형이 학습/검증/시험 양쪽에 섞이지 않게 분할한다. Python `pandas`·`scikit-learn`·`xgboost`로 학습하고 `model.json`, `feature_schema.json`, `training_config.json`, `evaluation.json`을 산출한다. 정밀도·재현율·F1·혼동행렬·오탐률을 보고하되 **합성 시나리오 구별 성능**으로만 설명한다.

□ **LangGraph를 사용하는 이유와 실제 Agent 동작**

LangGraph 단일 Agent는 `HELD` 사건을 입력받아 `get_transfer_history`로 최근 성공 이체를 조사하고, 정보가 부족할 때 `get_recipient_context`로 반복 묶음 이전 수취인 관계나 다른 출금계좌 맥락을 추가 조회한다. 두 Tool 모두 **서버가 부여한 `transferHoldId` 범위의 읽기 전용 API**다. Agent는 두 번째 Tool 사용 여부와 조사 초점을 선택하고, 서버 A/B 보류 사유와 구별되는 관찰 사실·근거 거래 ID·관리자 확인 질문을 구조화해 제출한다. 추가 발견이 없으면 빈 목록을 반환한다.

`보류 건 검증 → 거래 이력 조회 → 정보 부족 여부 판단 → 필요할 때만 수취인 맥락 추가 조회 → 추가 발견 작성 → JSON 검증·제출` 순서로 실행한다. 작업마다 Tool 호출 수·조회 기간·실행 시간·재시도를 제한한다. 조사 결과에는 `investigationId`, `transferHoldId`, 조사 상태, `secondaryFindings`의 코드·설명·`evidenceTransferIds`·항목별 `confidence`, `missingInformation`, `recommendedAction`, `suggestedQuestions`, `summary`, Agent·모델 버전을 포함한다. 추가 발견이 없다면 `secondaryFindings=[]`로 저장한다. 권고는 **관리자 고객 확인 제안** 수준이며 자동 실행 명령이 아니다.

추가 발견 후보는 **같은 금액으로 나눈 송금의 규칙성**, **여러 출금계좌에서 한 수취인으로 모인 흐름**, **묶음 이전의 수취인 친숙도**, **낮은 망설임 점수와 강한 반복 송금의 불일치**다. 서버의 건수·누적액·첫 수취인 판정에 이미 들어간 사실을 표현만 바꿔 새 발견으로 중복 보고하지 않는다. 관리자 확인 질문은 조회된 사실에 근거해 생성하며, 확인되지 않은 송금 목적·피해 여부를 단정하지 않는다. `secondaryFindings[].confidence`는 사기 확률이 아니라 증거 확인 상태로 사용한다. 허용 값과 JSON 예시는 개발 명세서 §7.5를 따른다.

서버는 Agent의 JSON 형식뿐 아니라 근거 거래 ID가 인증된 고객·허용된 조회 결과에 실제 포함되는지 확인한다. 보고서를 근거로 보류·실행 상태를 자동 변경하지 않는다. LLM 출력과 거래 메모 등의 외부 문자열은 권한 판단이나 지시문으로 취급하지 않는다.

P4는 보류 저장과 같은 커밋에 `TransferHeld`를 발행한다. P6 조사 작업은 `transferHoldId` 유니크 제약으로 보류 건당 한 행만 만들고, 최초 생성한 `investigationId`를 재전달·재시도에 재사용한다. 리스너는 작업 행 커밋 뒤에만 성공을 반환하고, 작업 큐 전달은 그 커밋 뒤에 한다. 저장 실패 시 이벤트 기록을 재전달해 같은 작업 행을 생성하거나 갱신한다. `QUEUED → RUNNING → COMPLETED / FAILED`로 상태를 관리한다. 제한 횟수·백오프로 재시도하되 최종 실패 시 관리자는 서버 근거만으로 처리한다. 내부 Tool은 임의 고객 ID가 아닌 서버 발급 `transferHoldId`로 조회 범위를 제한하고, 서비스 간 인증·최소 권한·계좌번호 마스킹·프롬프트 인젝션 방어·로그 보존 범위를 적용한다.

□ **보유 기반과 신규 구현 범위**

| 영역 | 기존 기반 | 이번에 필요한 작업 |
| --- | --- | --- |
| FE | React 즉시이체 화면 | 7종 행동 이벤트 수집, `flowId` 연결, 관리자 보류 화면 |
| 코어뱅킹 BE | Spring Boot의 당행 즉시이체·OTP·계좌·이체 이력 | 고객 소유권 검증, 10분 집계, A/B 판정, 원장 전 `HELD`, 승인 후 내부 실행 경로 |
| AI | Python 개발 환경 | 합성 데이터·XGBoost, FastAPI, LangGraph 단일 Agent, 읽기 전용 Tool 2개와 구조화 보고서 |
| 저장·비동기 | 기존 MySQL | P4 보류 요청·`TransferHeld`, P6 행동·조사·감사 기록과 내구성 있는 조사 작업·워커 |

○ Python은 XGBoost 학습·추론과 Agent 조사에 사용한다. Spring Boot는 **AI 서비스 응답을 기다리지 않고** A/B 정책으로 실행 또는 보류를 결정한다. AI 장애 시 이미 보류한 거래를 자동 실행하거나 거절하지 않으며, 관리자는 서버 근거와 고객 콜 결과만으로 검토할 수 있다.

○ 계좌비밀번호 토큰과 OTP는 판정 전에 소비한다. 보류 저장이 실패하면 기표 중 내부 오류와 같은 경로로 `transfer` ERROR 행을 남기고 실패 응답을 돌려준다. 이미 소비한 토큰 때문에 같은 멱등 키 재요청도 인증 토큰 오류로 끝나며, 고객은 다시 인증해 새 요청을 보낸다. OTP 원문·토큰은 보류 기록에 저장하거나 승인 때 재사용하지 않는다([transfer_seam.md §9-3](transfer_seam.md#9-3-hold일-때-p4가-보장하는-것)).

○ 일반 고객 즉시이체는 계좌비밀번호·OTP 토큰 둘 다 필수다. 승인 시 외부 이체 API를 다시 호출하거나 과거 토큰을 재사용하지 않는다. 관리자 권한·콜 결과는 P6이 확인하고, P4의 `release()`가 보류 건을 조건부로 `EXECUTING` 선점한 뒤 토큰 없이 내부 `execute()`를 부른다. `execute()`는 `sourceId`만으로 인증을 건너뛰지 않고 보류 행의 상태와 출금계좌·수취계좌번호·금액이 원본과 같은지 확인한다([transfer_seam.md §9-4](transfer_seam.md#9-4-실행거절취소)).

## 7. 구현 과정과 인일 추정

□ **구현 순서**

1. **계약 확인·잔여 계약 고정:** 훅 C, 판정 전 토큰 소비, `release() → execute()`는 P4 확정 계약을 따른다. P4·인증·FE·AI 담당자는 `flowId`, 이벤트 제출 시점, 보류 응답, P6의 내부 조회·조사 보고서·관리자 권한 계약을 구체화한다.
2. **행동 수집과 정책 판정:** FE가 7종 이벤트를 전송하고 BE가 소유권·순서·중복을 검사한다. 서버가 활성 체류·왕복·재수정을 계산하고 고객 전체 출금계좌의 성공 이체 이력에 현재 요청을 더해 A/B를 판정한다.
3. **보류와 인증:** 기존 검증 순서대로 토큰을 판정 전에 소비한다. A/B가 성립하면 훅 C가 HOLD를 결정하고 P4가 기표 트랜잭션을 롤백한 뒤 새 트랜잭션에 원본 보류 요청과 `TransferHeld`를 함께 남긴다. P6은 이벤트를 받아 조사 작업을 등록한다. 보류 중 원장은 기표하지 않는다. 정상 이체는 기존 실행 경로를 따른다.
4. **Python 모델·조사:** 합성 데이터 생성기와 XGBoost를 구축하고 FastAPI에 추론을 둔다. LangGraph Agent는 보류 사건의 읽기 Tool을 조건부로 호출해 추가 관찰 사실을 제출한다. P6은 기존 이벤트 발행 기록과 연결되는 내구성 있는 조사 작업·워커로 유실·중복을 막는다.
5. **관리자 업무:** 목록·상세에서 서버 사유와 Agent 결과를 분리하고 콜 결과·승인·거절을 제공한다. 승인 시 P4의 `release()`가 선점한 원본 보류 건만 `execute()`에서 재검증한 뒤 한 번 기표한다.
6. **통합 검증:** 정상/A/B/AI 장애/승인/거절, OTP 소비 실패·중복, 동시 세 번째 요청, 중복 승인, 응답 유실을 고정 시계와 합성 시나리오로 재현한다.

□ **연동 계약 초안**

| 호출 | API·메시지 예시 | 필수 계약 |
| --- | --- | --- |
| FE → BE | `POST /fds/behavior-flows/{flowId}/events` | 로그인 고객 소유권, 이벤트 순서·중복, 개인정보 제외 |
| FE → BE | `POST /transfers` + `flowId`·멱등키 | 요청 지문에 `flowId` 포함(훅 C 계약), 정상/`HELD` 응답 구분 |
| BE 내부 | `TransferHeld` → P6 조사 작업 | P4의 보류 저장·이벤트 발행은 같은 커밋, P6 작업 등록·재시도는 별도 설계 |
| Agent → BE | `GET /internal/fds/holds/{transferHoldId}/history` | 해당 보류 고객의 허용된 이체 이력만 조회 |
| Agent → BE | `GET /internal/fds/holds/{transferHoldId}/recipient-context` | 묶음 이전 수취인 관계·다른 출금계좌 맥락 조회 |
| Agent → BE | `PUT /internal/fds/investigations/{investigationId}/report` | 구조화 결과·근거 이체 ID 검증, 멱등 저장 |
| 관리자 → BE | `GET /admin/fds/holds`, `GET /admin/fds/holds/{transferHoldId}` | 보류 목록·상세와 서버 사유/AI 조사 결과 분리 표시 |
| 관리자 → BE | `POST /admin/fds/holds/{transferHoldId}/call-record` | 콜 결과·담당자·시각 감사 기록 |
| 관리자 → BE | `POST /admin/fds/holds/{transferHoldId}/approve`, `.../reject` | 권한·콜 기록 검증 후 P4 보류 해제·거절 호출 |

표의 URL은 **컨트롤러 매핑 기준 초안**이며 외부 호출에는 서버의 `/api/v1` 컨텍스트 경로가 앞에 붙는다(예: `/api/v1/transfers`). P4의 `TransferHeld`와 `flowId` 지문 포함은 확정 계약이고, P6 API의 경로·필드는 구현 전 확정한다. 정상·보류의 성공 응답은 프로젝트 공통 형식인 **HTTP 200·`code="0000"`**을 따른다. 보류를 기존 이체의 `SUCCESS`·`ERROR`·`TIMEOUT` 중 하나로 위장하지 않는다.

남은 세부 계약은 `flowId` 소유권·마감 시점, FE의 `HELD` 응답 표시, 내부 API 서비스 인증·마스킹, Agent 작업 재시도와 결과 저장의 멱등성, 관리자 승인 후 실행 실패·응답 불명 처리다. 기존 `TransferPreCheck`는 예외로 요청을 거부하는 훅이므로 **`HELD` 구현에 재사용하지 않는다.** 보류 자리는 한도 적립 뒤 훅 C로 확정됐다.

□ **저장·동시성 경계**

P4가 `transfer_hold`와 원본 요청 저장·보류 상태 전이·`TransferHeld`를 소유한다. P6은 행동 흐름·이벤트, 조사 결과, 조사 작업과 FDS 판정·관리자 감사 기록을 소유한다. 동일 보류 건의 조사 보고서와 관리자 조치는 멱등 처리한다. 훅 C는 고객 단위 한도 행 락을 쥔 채 조회하므로 앞선 요청의 커밋을 본다. P6 정책 구현체는 훅 안에서 외부 호출·DB 쓰기를 하지 않고, 스위치가 꺼져 있으면 DB도 읽지 않는다. 새 테이블을 만들면 Flyway 증분 파일과 `schema_reference.md`, `corebank_erd.md`를 함께 갱신한다.

P4는 `transfer.api`에 `transferHoldId`로 원본 요청·상태를 읽는 계약을 제공하고 조회 구현은 FDS 착수 때 만든다. P6은 판정 근거·행동 요약·Agent 읽기 Tool을 소유한다. FDS 훅 C는 지연이체보다 작은 `order`로 승인 보류를 우선 판정한다. 승인 실행은 `source_type=HELD`, `source_id=보류 ID`로 기존 즉시이체를 한 번 기표하고 기존 소스 유니크 제약으로 중복 실행을 막는다. 원장 거래유형과 GL 매핑은 유지한다.

| 저장 대상 | 핵심 필드·제약 |
| --- | --- |
| `transfer_hold` (P4) | 원본 요청·요청 지문·인증 완료 시각·정책 코드·해제 방식/시각·`flowId`·보류 상태. 상세 필드와 제약은 [transfer_seam.md §9](transfer_seam.md#9-훅-c--이체-보류-771) 및 #772 구현을 따른다 |

| P6 성공 이체·행동 연결 (테이블명 미정) | 성공 `TransferSettled`의 `refId`와 `flowId` 연결. `refId` 유니크로 중복 이벤트 저장 방지. 리스너는 P4 필드 추가 PR 머지 뒤 연결 |

## 8. 기대 효과와 성과 검증 계획

### 8.1 기대 효과

□ **의심 거래의 기표 전 확인 시간 확보**

○ A/B 조건이 겹친 현재 요청만 임시 보류해 관리자에게 고객 확인 시간을 제공한다. AI가 계좌를 정지하거나 이체를 영구 거절하지 않는다.

□ **관리자 검토 근거의 분리와 추적**

○ 서버가 확인한 보류 사유, Agent가 추가 조사한 관찰 사실, 관리자 콜 결과와 최종 조치를 각각 기록한다. Agent가 제시한 근거 거래 ID는 서버가 고객·허용된 조회 범위와 대조해 검증한다.

□ **발표 가능한 AI Agent성과 한계의 동시 제시**

○ Agent가 첫 조회 결과에 따라 두 번째 Tool 사용 여부와 조사 초점을 선택하는 장면을 시연한다. Agent의 추가 발견은 **보류 사건 안에서만** 유효하며, 서버를 통과한 사기 거래를 탐지하는 효과로 주장하지 않는다.

### 8.2 성과 검증 계획

| T16–T17 | 승인 시 잔액 부족·계좌 정지; 실행 성공 후 응답 유실 | 실행 거부 또는 멱등 결과 재조회, 이중 출금 없음 |
| T18–T19 | 비인가 내부 Tool 접근; Agent가 없는 거래 ID를 근거로 보고 | 접근 거부·근거 검증 실패 표시 |
| T20 | `HELD` 상태 조회 | 출금·입금·원장 기표 없음 |
| T21–T23 | OTP 대조 불일치; 소비 후 보류 저장 실패·동일 멱등 키 재요청; 보류 행 미선점·원본 불일치·토큰과 `sourceId` 동시 전달 | 저장 실패 시 `transfer` ERROR·실패 응답, 같은 키는 토큰 오류·새 인증 필요, 부적절한 내부 실행은 기표 없이 거부 |
| T24 | AI 조사 `RUNNING`·`FAILED`, 관리자 콜 기록 완료 | 서버 근거로 승인·거절 가능, AI 미완료 사유 감사 기록 |

□ **AI 조사와 모델 평가**

○ 합성 정상·의심 시나리오를 원형 단위로 분리해 학습·평가한다. XGBoost 점수와 3개 중 2개 규칙의 오탐·탐지 결과를 **합성 데이터 범위에서만** 비교한다. 실제 금융권 예방률이나 사기 확률로 발표하지 않는다.

○ 평가표에는 **단건 거래 속성 기준선**, **망설임 3개 중 2개 규칙**, **XGBoost 행동 점수**의 혼동행렬·정밀도·재현율·오탐률을 같은 합성 시험셋에서 나란히 표시한다. 학습에 사용한 시나리오 원형을 시험셋에 재사용하지 않고, 정상인데 오래 확인한 거래와 망설임 없는 반복 송금을 반례로 넣는다. 지표가 불리해도 결과를 그대로 보고한다.

○ Agent는 두 번째 Tool이 필요한 건과 필요 없는 건을 각각 실행하고, 서버 A/B 사유와 구별되는 `secondaryFindings`를 반환하는지 확인한다. 추가 발견이 없는 경우에는 빈 결과를 허용한다. 근거 거래 ID가 실제 조회 결과와 일치하지 않으면 보고서를 거부한다.

○ 관리자 화면에서 **서버 보류 사유 / Agent 추가 관찰 / 고객 콜 결과 / 최종 조치**를 나란히 보여준다. AI 장애 시에도 서버 근거만으로 업무가 진행되는 장면을 시연한다.

□ **발표 시연 A–D**

| 장면 | 화면과 서버에서 확인할 결과 |
| --- | --- |
| A: 망설임 + 신규 수취인 | 50만 원 두 번 성공 후 세 번째 요청에서 뒤로 가기 1회·금액 재수정 2회 → 서버 A로 `HELD`·미기표 → Agent 조건부 Tool 호출·추가 발견 → 관리자 콜·승인 → 재인증·OTP 재사용 없이 1회 실행 |
| B: 망설임 없는 반복 | 100만 원 두 번 성공 후 세 번째 요청 → 서버 B로 `HELD` → Agent 조사 → 관리자 거절·미기표 종료 |
| C: 정상 거래 | A/B 불성립 → 기존 실행 경로. 망설임만 있어도 보류·Agent 작업 없음 |
| D: AI 장애 | 서버 A/B로 `HELD` 후 Python 조사 실패 → 보류 유지·실패 표시 → 관리자 서버 근거와 콜로 수동 검토 |

시연에서는 고정 시계·테스트 픽스처로 거래 간격을 재현하고, 테스트 환경에서만 데모 시드를 사용한다. **서버 보류 근거, Agent의 추가 관찰, 콜 결과, 최종 실행 결과**를 각기 다른 영역에서 확인한다.

□ **완료 판단**

정상 이체·A/B 보류·미기표·OTP 1회 소비·보류/조사 상태 분리·Agent의 두 종류 조회 Tool과 조건부 분기·추가 발견 저장·AI 장애 수동 검토·관리자 콜 후 승인/거절·승인 후 고객 재인증 없는 1회 실행·거절/만료/중복·동시 요청 검증이 모두 통과해야 한다. 합성 XGBoost 점수를 실제 사기 확률로 표기하지 않고, 최초 인증을 지연 실행에 사용하는 계약이 팀 내 확정돼 있어야 한다.

**팀장님께 요청할 결정:** 확정된 P4 보류 계약을 구현할 담당·머지 일정과 P6 FE·BE·AI 담당 배정, `flowId`/Tool/API 계약, 11월 12일 기능 동결 목표의 수용 여부.

Python FastAPI 추론·LangGraph·내구성 있는 조사 작업이 새 범위다. 관리자 승인 후에는 소비한 OTP를 재사용하지 않고 P4의 `release() → execute()` 경로를 따른다. 초기안의 29.5인일과 이번 25~38인일은 포함한 작업이 달라 직접 비교할 수 없다. 병렬화는 인일 합계를 줄이지 않는다. P6 API 경로·상태명·테이블명·공수는 구현 계약에서 확정한다.
