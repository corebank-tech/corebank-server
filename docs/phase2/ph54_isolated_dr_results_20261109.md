# PH-54 — 격리 DR 리허설 결과 (2026-11-09)

> **판정: 격리 환경의 DB 복원·계정계 API·당행이체·원장·GL 정합성 검증 통과.**
>
> 실제 운영 Replica 승격, 원본 쓰기 차단, DNS 전환, Failback 및 RTO/RPO 측정은 수행하지 않았다. 이 문서는 운영 전환 결과가 아닌 사전 격리 검증 결과다.

- 수행일: 2026-11-09
- 담당: P2
- 관련 이슈: #886
- 검증 환경: 온프레미스 VM의 별도 Docker MySQL 및 계정계 API
- 정확한 리허설 시작·종료 시각: 미기록
- 관련 문서: [PH-54 DR Runbook](ph54_onprem_dr_runbook.md), [RDS → VM 복제 검증](ph70_rds_vm_replication_validation_20261103.md)

## 1. 검증 목적 및 범위

운영 AWS RDS의 데이터가 온프레미스 환경에 복원됐을 때, 계정계 API가 실제 금융 거래를 처리하고 거래·원장·GL 정합성을 유지하는지 확인한다.

운영 Replica의 복제를 유지하기 위해 별도 MySQL을 구성했다. 따라서 이번 검증에서는 실제 운영 Replica를 승격하지 않았으며, 운영 DNS도 변경하지 않았다.

검증 범위:

1. Replica 데이터의 격리 DB 복원
2. 격리 DB에 연결한 계정계 API 기동
3. 고객 로그인 및 계좌 조회
4. 계좌비밀번호·OTP 인증
5. 1,000원 당행이체
6. 거래·계좌 잔액·원장·GL 정합성

| 구분 | 구성 |
|---|---|
| 데이터 원본 | `info-replica-mysql` — RDS 복제 수신 중 |
| 격리 MySQL | `corebank-drtest-mysql` |
| 격리 MySQL 접근 | `127.0.0.1:3310` |
| 격리 Docker 네트워크 | `corebank-drtest-net` |
| 격리 계정계 API | `corebank-drtest-api` |
| API 접근 | `http://127.0.0.1:8080/api/v1` |
| API 이미지 | `corebank/corebank-server:f72982e00e5c3d5ee2c954aa47e7e5768523d310` |
| 애플리케이션 버전 | 11/3 릴리스 3 |
| Spring Profile | `prod,phase2-seed` |
| 업무 DB | `minicore` |

격리 API는 운영 DB가 아닌 `corebank-drtest-mysql`에 연결했다.

로컬 HTTP에서 세션을 검증하기 위해 격리 API의 쿠키 설정을 별도로 적용했다.

- `SERVER_SERVLET_SESSION_COOKIE_SECURE=false`
- `APP_SECURITY_CSRF_COOKIE_DOMAIN=`

이 설정은 루프백 HTTP 검증용이며, 실제 운영 HTTPS 환경의 검증 결과로 간주하지 않는다.

운영 Replica(`info-replica-mysql`), 정보계 마트(`info-mart-mysql`), 정보계 API(`info-api`)의 기존 실행 상태를 변경하지 않았다.

## 3. 격리 DB 복원 결과

### 3-1. 데이터 준비

2026-11-09 운영 Replica 데이터를 SQL 덤프로 백업하고, 별도 MySQL 인스턴스에 복원했다.

- 백업 파일: `~/corebank-dr-backup/minicore-20261109-110201.sql.gz`
- 압축 파일 크기: 약 362MB
- 복원 후 DB 크기: 약 3.87GB
- 복원 테이블: 52개
- Flyway 이력: 실패 항목 없음, 최신 버전 `202611030100` 확인

주요 데이터 표본:

| 테이블 | 복원본 행 수 |
|---|---:|
| `account` | 180,023 |
| `customer` | 60,010 |

복원본의 테이블 구조와 주요 데이터가 조회 가능한 상태임을 확인했다.

다만 전체 행·컬럼 체크섬 비교 및 공통 GTID 기준의 복원 정합성 검증은 수행하지 않았다.

### 3-2. API 기동

격리 DB를 연결 대상으로 지정한 계정계 API 컨테이너를 기동했다.

확인 결과:

- Spring Boot 애플리케이션 기동 정상
- API 헬스체크 HTTP 200
- Flyway 마이그레이션 오류 없음
- 고객 인증 및 계좌 조회 가능

## 4. 업무 API 검증

### 4-1. 인증 및 조회

| 순서 | 검증 | 결과 |
|---|---|---|
| 1 | 고객 로그인 | HTTP 200 |
| 2 | JSESSIONID 발급 | 확인 |
| 3 | `GET /customers/me` | HTTP 200 |
| 4 | `GET /accounts` | HTTP 200 |
| 5 | 이체 수취인 계좌 조회 | HTTP 200 |
| 6 | 출금계좌 비밀번호 인증 | HTTP 200 |
| 7 | Mock OTP 발급 | HTTP 200 |
| 8 | OTP 검증 | HTTP 200 |

로그인 후 세션 쿠키를 사용해 고객정보 및 계좌 조회를 수행했다.

검증 도중 `curl`이 저장한 세션 쿠키의 만료값 `0`을 Python `MozillaCookieJar`가 만료된 쿠키로 처리하는 문제가 있었다.

쿠키를 로드할 때 `0`을 세션 쿠키로 정규화한 뒤 고객 세션 검증과 이체 요청에 성공했다.

해당 문제는 격리 테스트 스크립트의 쿠키 처리 문제이며, 계정계 API 결함으로 판단하지 않는다.

출금계좌 비밀번호 인증 및 OTP 인증 후 멱등키를 생성해 이체를 1회 요청했다.

## 5. DB 정합성 검증

이체 API의 성공 응답만으로 완료 판정하지 않고, 격리 DB에서 거래번호 기준으로 관련 테이블을 조회했다.

### 5-1. 이체 거래

`transfer` 테이블 조회 결과:

| 항목 | 결과 |
|---|---|
| 거래번호 | `20261109WB0000000001` |
| 상태 | `SUCCESS` |
| 출금계좌 ID | `60029998` |
| 입금계좌 ID | `60000001` |
| 금액 | 1,000원 |
| 수수료 | 0원 |
| 출금 후 잔액 | 50,648,000원 |

### 5-2. 계좌 잔액

| 계좌 | 이체 전 | 이체 후 | 변화 |
|---|---:|---:|---:|
| 출금계좌 `60029998` | 50,649,000원 | 50,648,000원 | -1,000원 |

두 계좌 모두 `ACTIVE` 상태이며, 이체 후 잔액이 예상값과 일치했다.

### 5-3. 원장 정합성

`ledger_entry`를 거래번호로 조회한 결과:

| 계좌 ID | 방향 | 금액 | 기표 후 잔액 |

| `60029998` | `WITHDRAWAL` | 1,000원 | 50,648,000원 |
| `60000001` | `DEPOSIT` | 1,000원 | 33,091,920원 |

집계 결과:

- 원장 행 수: 2건
- 출금 합계: 1,000원
- 입금 합계: 1,000원

동일 거래번호의 출금·입금 원장 쌍이 정상 생성됐다.

당행이체의 GL 전표 1건과 균형을 이루는 분개 2건을 확인했다.

### 5-5. 검증 판정

다음 연결 관계가 동일 거래번호를 기준으로 확인됐다.

`transfer` → `account` 잔액 변경 → `ledger_entry` 2건 → `gl_voucher` 1건 → `gl_journal_entry` 2건

**결론: 격리 환경에서 당행이체 1건의 거래·원장·GL 정합성 검증 통과.**

이 결과는 해당 시험 거래의 정합성을 의미하며, 전체 데이터에 대한 전수 대사 결과는 아니다.

## 6. 미실시 항목 및 한계

| 항목 | 상태 | 사유 |
|---|---|---|
| 운영 Replica 승격 | 미실시 | 격리 환경의 데이터 복원·쓰기 검증만 수행 |
| AWS 원본 쓰기 차단 | 미실시 | 실제 전환 단계 아님 |
| 최종 원본·Replica GTID 일치 | 미검증 | 전환 기준점 미확정 |
| 만기해지 | 미실시 | 릴리스 3의 계좌 버전 충돌 결함 수정 전 이미지 |
| 중도해지 | 미실시 | 동일한 버전 충돌 가능성이 있는 이미지 |
| 실제 FE 경유 업무 | 미실시 | API 직접 호출만 검증 |
| 외부 HTTPS·DNS | 미실시 | 루프백 HTTP만 검증 |
| 정보계 API 연동 | 미실시 | 계정계 업무 중심 검증 |
| 실제 외부 연동 | 미실시 | 격리 환경 검증 범위 밖 |
| Failback | 미실시 | AWS 재동기화·복귀 미검증 |
| RTO/RPO | 미측정 | 실제 장애·전환 시작 및 복구 시각 미계측 |

UAT U-C09의 `409 CMN0303` 계좌 버전 충돌 문제는 PR #935에서 수정됐다.

해당 수정은 2026-11-09 릴리스 4에 포함됐으나, 이번 격리 리허설에는 릴리스 3 이미지가 사용됐다. 따라서 이번 결과로 만기·중도해지 결함이 해결됐다고 판정하지 않는다.

또한 실제 금융 거래 처리는 Mock OTP 등 시험 구성을 사용했으므로, 운영 수준의 외부 인증·보안 통제를 검증했다고 판단하지 않는다.

1. 릴리스 4 계정계 API 이미지 및 환경변수 준비 상태 확인

6. 실제 전환 시각과 관측값을 바탕으로 전환 소요 시간과 RPO 평가 결과 기록
7. AWS 철거 계획에 따른 Failback 미실시 사유와 데이터 보존·복구 대책 기록

## 8. 최종 결론

2026-11-09 격리 리허설에서 복원된 MySQL 데이터를 기반으로 계정계 API가 기동했고, 로그인·계좌조회·당행이체 및 원장·GL 기표까지 정상 동작했다.

1,000원 당행이체에 대해 출금·입금 계좌 잔액, 원장 2건, GL 전표 1건, 분개 2건 및 차대변 차이 0원을 확인했다.

따라서 **격리 환경에서의 핵심 거래 복구 가능성 검증은 통과**했다.

다만 운영 Replica 승격과 서비스 전환은 아직 수행하지 않았으므로, 실제 Failover 성공 및 RTO/RPO 목표 달성을 입증하는 결과는 아니다.
