## 1. 검증 목적 및 범위

운영 AWS RDS의 데이터가 온프레미스 환경에 복원됐을 때, 계정계 API가 실제 금융 거래를 처리하고 거래·원장·GL 정합성을 유지하는지 확인한다.

운영 Replica의 복제를 유지하기 위해 별도 MySQL을 구성했다. 따라서 이번 검증에서는 실제 운영 Replica를 승격하지 않았으며, 운영 DNS도 변경하지 않았다.

검증 범위:

1. Replica 데이터의 격리 DB 복원
2. 격리 DB에 연결한 계정계 API 기동
3. 고객 로그인 및 계좌 조회
4. 계좌비밀번호·OTP 인증
5. 1,000원 당행이체
6. 거래·계좌 잔액·원장·GL 정합성

### 2-1. 스케줄러 및 외부 적재 격리

격리 계정계 API는 릴리스 3 이미지에서 `prod,phase2-seed` 프로필로 기동했다.

- `SchedulingConfig`는 `@Profile("!phase2-seed")` 조건으로 선언돼 있어 정기 `@Scheduled` 작업이 등록되지 않는다.
- `BusinessDateCatchUpScheduler`도 동일한 프로필 조건으로 제외돼 기동 직후 영업일 보정이 실행되지 않는다.
- 따라서 00:30 감사 로그 S3 적재를 포함한 정기 스케줄은 이번 격리 실행에서 활성화되지 않는 구성이다.

단, `application-prod.yml`의 감사 로그 저장소 설정은 여전히 `s3`이므로 외부 S3 접근 가능성이 설정 차원에서 완전히 차단됐다고 판단하지 않는다.

P5의 감사 버킷 확인 결과, 검토 시점까지 격리 API가 적재한 흔적은 발견되지 않았다.

격리 API 및 MySQL 컨테이너의 종료·보존 상태는 리허설 종료 후 실제 상태를 확인해 기록한다.

해당 파일에는 시험 데이터와 인증 관련 정보가 포함될 수 있으므로 저장소에 커밋하지 않고 VM 내부에서 관리한다.

추가 검증 완료 후 격리 MySQL과 임시 파일의 보존 필요성을 재검토하고 정리한다.

### 3-1. 데이터 준비

2026-11-09 운영 Replica 데이터를 SQL 덤프로 백업하고, 별도 MySQL 인스턴스에 복원했다.

- 백업 파일: `~/corebank-dr-backup/minicore-20261109-110201.sql.gz`
- 압축 파일 크기: 약 362MB
- 복원 후 DB 크기: 약 3.87GB
- 복원 테이블: 52개
- Flyway 이력: 실패 항목 없음, 최신 버전 `202611030100` 확인

주요 데이터 표본:

| 테이블 | 복원본 행 수 |
|---|---:|
| `account` | 180,023 |
| `customer` | 60,010 |

복원본의 테이블 구조와 주요 데이터가 조회 가능한 상태임을 확인했다.

다만 전체 행·컬럼 체크섬 비교 및 공통 GTID 기준의 복원 정합성 검증은 수행하지 않았다.

### 3-1-1. 덤프 옵션 및 데이터 일관성

2026-11-09 운영 Replica(`info-replica-mysql`)에서 `mysqldump`로 `minicore` 데이터를 추출했다.

사용한 옵션:

- `--single-transaction`
- `--quick`
- `--set-gtid-purged=OFF`
- `--no-tablespaces`
- `--hex-blob`
- `--routines`
- `--events`
- `--triggers`
- `--databases minicore`

`--single-transaction`으로 InnoDB 데이터의 일관된 스냅샷을 생성하는 방식을 사용했으며, 덤프 중 운영 Replica의 복제 스레드는 중지하지 않았다.

`--set-gtid-purged=OFF`로 덤프 파일에 GTID_PURGED 설정문을 포함하지 않았다.

다만 다음 항목은 덤프 시점의 관측값을 확보하지 못했다.

- 원본 RDS의 최종 적용 GTID
- Replica의 수신·적용 GTID 및 복제 지연
- 원본 RDS와 복원본의 동일 기준점 행 수 비교
- 전체 데이터 체크섬 및 전수 정합성

따라서 덤프의 트랜잭션 일관성을 위한 옵션을 사용했다는 사실만으로 원본 RDS와 복원본의 완전한 동등성이 검증됐다고 판단하지 않는다.

또한 이번 방식은 SQL 덤프 복원이므로 실제 DR에서 수행할 Replica 승격과는 구분한다.

## 6. 미실시 항목 및 한계

| 항목 | 상태 | 사유 |
|---|---|---|
| 운영 Replica 승격 | 미실시 | 격리 환경의 데이터 복원·쓰기 검증만 수행 |

또한 실제 금융 거래 처리는 Mock OTP 등 시험 구성을 사용했으므로, 운영 수준의 외부 인증·보안 통제를 검증했다고 판단하지 않는다.
