# PH-15 — COB 만기 감지 운영 관측 결과 (2026-11-09 정리)

> 담당: P2  
> 관측 데이터: 2026-10-26 ~ 2026-11-06 COB 실행 이력  
> 조회일: 2026-11-09 (KST)  
> 상태: **릴리스 4 배포 전 이력 정리 완료 / 릴리스 4 배포 후 관측 대기**  
> 관련 작업: [PH-15](tasks.md#ph-15-만기--감지--matured-전이--원리금--만기해지-api), [PH-43 측정 결과](ph43_baseline_results.md)

## 1. 목적과 범위

- COB의 `account-maturity` 스텝에서 만기 대상 계좌를 조회하고 `ACTIVE → MATURED`로 전이하는 **전체 단계 실행시간**과 **관측된 상태 전이 건수**를 기록한다.
- 전체 실행시간을 실제 전이 건수로 나눠 **전이 1건당 관측 평균 비용**을 산출한다. 이 값은 후보 조회·잠금·상태 저장·이력 저장·이벤트 발행 등 공통 비용을 포함하므로 계좌 한 건의 순수 처리시간이나 계좌 수에 비례하는 상수로 해석하지 않는다.
- `MATURED → CLOSED` 고객 만기해지 API의 응답시간, 이자·세금·원리금 **0원 오차 검증**, 정정 거래 후 만기해지 E2E 검증은 본 결과의 측정 범위가 아니다.
- 실제 운영 DB에서 기존 기록을 **읽기 전용 `SELECT`**로 확인했다. COB를 별도로 실행하거나 계좌·영업일·테이블을 수정하지 않았다.

## 2. 관측 환경 및 버전 구분

- 조회 경로: 신규 AWS 계정 EC2 → SSM 세션 → MySQL 클라이언트(TLS) → 신규 RDS `minicore`.
- 원천: `batch_execution_history` (`COB` / `account-maturity`), `account_status_history` (`COB`, `ACTIVE → MATURED`).
- 신규 RDS는 **2026-10-28 기존 계정 DB 스냅샷 복원본**이다. 따라서 신규 RDS에서 조회되더라도 10/26~10/27 이력은 **기존 환경에서 생성된 기록**이다.
- 10/28~11/06 스텝 이력은 복원 시각 이후 기록이므로 신규 RDS 운영 기록으로 분리한다. 인스턴스별 정확한 애플리케이션 이미지/코드 버전은 이 쿼리만으로 알 수 없다.
- **릴리스 4는 2026-11-09 오후 배포**되었다(팀 배포 안내). 아래 10개 기록은 모두 그보다 이전이므로 **릴리스 4 실측치가 아니다**. 배포 완료 시각·이미지 식별자는 별도 확인 필요.
- 영업일(`business_date`)과 실제 실행 시각(`started_at`)은 COB 재시도에 따라 달라질 수 있다. 환경/릴리스 구분은 영업일만이 아닌 실제 실행 시각을 우선 사용한다.

## 4. 신규 RDS 운영 기록 요약 (2026-10-28 ~ 11-06)

| 지표 | 결과 |
| --- | ---: |
| 관측된 `account-maturity` 성공 스텝 | 8회 / 조회된 8회 |
| 관측된 `ACTIVE → MATURED` 상태 이력 | 424건 |
| 전체 실행시간 합계 | 11,559.77ms |
| 회당 평균 실행시간 | 1,444.97ms (약 1.445초) |
| 회당 중앙값 실행시간 | 1,366.87ms (약 1.367초) |
| 최솟값 ~ 최댓값 | 1,192.39 ~ 2,147.59ms |
| 전체 시간 합계 ÷ 전체 전이 건수 | **27.26ms/건 (관측 평균 비용)** |

계산식:

```text
회당 평균 실행시간 = 11,559.77ms / 8회 = 1,444.97ms
회당 중앙값 = (1,309.32ms + 1,424.42ms) / 2 = 1,366.87ms
관측 평균 비용 = 11,559.77ms / 424건 = 27.26ms/건
```

**해석**

1. 신규 RDS의 조회된 8회 모두 `account-maturity` 스텝 `SUCCESS`였다. 단, 이것만으로 모든 만기 후보가 성공 처리됐거나 실패 후보가 0건이라는 사실까지 증명되지는 않는다. 별도 애플리케이션 로그의 `failedCandidates`·`failedChunks` 대조가 필요하다.
2. 만기 감지는 38~112건 전이 구간에서 회당 약 1.19~2.15초를 기록했다. 38건인 날에도 시간이 약 1.2~1.56초이므로 계좌당 비용을 순수 선형 비용으로 간주할 수 없다.
3. `27.26ms/건`은 회차별 비율의 단순 평균이 아니라, **총 실행시간 ÷ 총 전이 건수**로 계산한 전체 관측 평균이다. 이를 전체 계좌 15만 건에 곱해 처리시간을 추정해서는 안 된다. 전체 계좌는 스캔 대상이고 전이 대상은 일부일 수 있으며, 고정 오버헤드도 포함되어 있기 때문이다.
4. 기존 환경 10/26~10/27 2건의 기록과 신규 RDS 8건은 인스턴스 사양·실제 데이터·실행 여건이 달라 직접적인 개선 전후 비교로 사용할 수 없다.
5. 현재 값은 **릴리스 4 이전 운영 관측값**이지, 릴리스 4의 성능 개선 효과를 검증하는 전후 실험 결과가 아니다.

### P5 COB 전체 소요시간 반영 기준

- P5가 측정한 COB 총 실행시간에 `account-maturity`가 이미 포함되어 있다면 **추가 합산하지 않고 단계별 기여시간**으로 표시한다(이중 집계 방지).
- 별도 단계 합산식으로 구성한다면 **동일 COB 회차의** 영업일 전환·원장 대사·만기 감지 스텝 값을 사용한다. `account-maturity`의 평균 1.445초를 다른 날의 COB 시간에 기계적으로 더하지 않는다.
- 이 문서의 수치는 신규 RDS 운영 기록 8회의 **만기 감지 스텝 시간만** 설명한다.

## 5. 재현 SQL (운영 DB 읽기 전용)

### 5-1. 전체 실행시간

```sql
SELECT
    business_date,
    started_at,
    ended_at,
    ROUND(TIMESTAMPDIFF(MICROSECOND, started_at, ended_at) / 1000, 2) AS elapsed_ms,
    status
FROM batch_execution_history
WHERE job_name = 'COB'
  AND step_name = 'account-maturity'
ORDER BY started_at DESC
LIMIT 20;
```

### 5-2. 실제 상태 전이 이력과 연결

```sql
SELECT
    b.business_date,
    b.started_at,
    b.status,
    ROUND(TIMESTAMPDIFF(MICROSECOND, b.started_at, b.ended_at) / 1000, 2) AS elapsed_ms,
    COUNT(h.history_id) AS transitioned_count,
    ROUND(
        TIMESTAMPDIFF(MICROSECOND, b.started_at, b.ended_at)
        / 1000 / NULLIF(COUNT(h.history_id), 0),
        2
    ) AS observed_ms_per_account
FROM (
    SELECT *
    FROM batch_execution_history
    WHERE job_name = 'COB'
      AND step_name = 'account-maturity'
    ORDER BY started_at DESC
    LIMIT 20
) b
LEFT JOIN account_status_history h
    ON h.changed_at >= b.started_at
   AND h.changed_at <= b.ended_at
   AND h.trigger_type = 'COB'
   AND h.previous_status = 'ACTIVE'
   AND h.new_status = 'MATURED'
GROUP BY
    b.batch_execution_history_id,
    b.business_date,
    b.started_at,
    b.ended_at,
    b.status
ORDER BY b.started_at DESC;
```

동일 시간대에 여러 실행이 겹치거나 이력 기록 시각과 커밋 시각이 차이 나면 이 방식의 연결이 부정확할 수 있다. 스텝이 겹치지 않았는지와 각 회차 로그의 실제 전이 수를 확인해야 정확한 단건 비용으로 확정할 수 있다. `effective_business_date`는 COB 날짜가 아니라 만기 판정 기준인 다음 영업일이므로 같은 날짜끼리 단순 조인하지 않는다.
