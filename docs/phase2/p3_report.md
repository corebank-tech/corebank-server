# P3 회계 통제와 정보계 리포트 (P3-RPT)

> S1부터 S4까지 P3가 맡은 회계 통제(GL)와 정보계 마트 설계의 결과를 한 장으로 묶는다. PH-48 발표 자료의 입력이다.
> 새로 잰 값은 없고, 수치마다 원 문서를 단다. **확정**은 원 문서에 측정 조건과 함께 기록된 값이고, **로컬**은 운영이 아닌 로컬 DB에서 잰 값이다.
> 정보계 ETL 적재와 조회 API(P5)는 결과를 옮기지 않고 링크만 건다(P5-RPT #857).

## 2. 회계 통제 구조

### 2-1. 계정과목과 GL 테이블 (PH-20, PR #478)

- 계정과목 15개를 5분류(자산, 부채, 자본, 수익, 비용)로 둔다. 시드는 `R__seed_gl_account.sql`이다.
- 테이블은 `gl_account`, `gl_voucher`(전표), `gl_journal_entry`(분개) 셋이다. 금액은 원 단위 `BIGINT`다.

### 2-2. 분개 패턴 (PH-21, PR #491, PR #526)

- 정본은 [gl_journal_patterns.md](gl_journal_patterns.md)다. 원장 이벤트를 전표로 옮기는 규칙을 코드가 아니라 이 표에 두고, 새 유형은 소유 트랙이 표를 먼저 고친다.
- 전표 유형은 9종이다. P3가 개시(`OPN`), 당행 이체(`TRF`), 상품가입 초입금(`SUB`), 취소정정(`REV`)을 정했고, 이자(`INT`), 만기와 해지(`MAT`, `TRM`)는 P2, 타행 미결제 2패턴(`IBT`, `IBS`)은 P4가 같은 표에 더했다.
- 전표번호는 `yyyyMMdd-TTT-NNNNNN`(거래일, 유형, 일련번호 6자리)이다. 4자리로는 PH-60b 첫날부터 넘쳐 6자리로 정했다.

### 2-3. 기표 경로 (PH-24, PR #585)

- 다른 도메인은 `gl.api.JournalPostingUseCase` 하나로 기표한다. 이 호출은 호출자 트랜잭션 안에서만 돌아(`MANDATORY`) 원장과 전표가 같은 커밋에 들어간다.
- 이체 기표 훅 B(`GlLedgerPostingHook`)는 즉시이체, 예약이체, 자동이체, 상품가입 초입금, 취소정정에서 불린다. 기표가 실패하면 예외를 던져 이체를 롤백한다.
- 전표에 원 거래번호(`reference_key`)를 두고 `UNIQUE (tx_type, reference_key)`를 건다. 같은 거래를 두 번 기표하면 예외다. 이 키가 원장과 전표를 잇는 사후 대사의 기준이 된다.
- 전표번호 채번은 전용 커넥션 풀(3개)로 한다. 메인 풀에서 커넥션을 하나 더 꺼내면 동시 이체가 풀 크기에 닿을 때 순환 대기로 멈추는 것을 재현해 분리했다.

### 2-4. 통제의 층 (ADR-0009)

| 시점 | 장치 | 막거나 찾는 결함 |
|---|---|---|
| 기표할 때 | 원장과 전표를 같은 트랜잭션에서 쓴다 | 전표 없는 원장 |
| 기표할 때 | `Voucher.validateBalanced` | 차대변이 다른 전표 |
| 기표할 때 | `uk_gl_voucher_tx_type_reference_key` | 같은 거래의 같은 유형 중복 기표 |
| 저장한 뒤 | 시산표(PH-28), 전표 차대변 점검 | 차대변이 깨진 GL 결함 |
| 저장한 뒤 | 원장 전표 대사, 고아 전표 수(PH-28b) | 차대변이 맞는 GL 결함(분개누락, 다른 키 중복), 원장 누락 |
| 저장한 뒤 | P4 원장 잔액 대사(PH-38) | 원장 결함 |

차대변 일치는 DB 제약으로 걸지 않았다. MySQL CHECK는 한 행만 보고 지연 제약이 없어 여러 줄의 합을 막을 수 없기 때문이다. 그래서 저장 뒤 결함은 사후 점검(`GET /admin/gl/integrity-check`)으로 찾는다.

## 3. 시산표 성능 (PH-28, GL-IDX)

**문제.** 시산표 집계가 기간과 무관하게 분개 655만 행을 모두 읽었다. FK 인덱스 `fk_gl_journal_entry_account` 전체를 훑고 본 테이블에서 거래일을 거르는 실행계획이었다. 하루를 조회해도 22.7초였다.

**결정.** 로컬에서 인덱스 후보 3개를 같은 SQL로 비교해 `(trade_date, account_code, dr_cr, amount)`를 골랐다. 조회 기간 범위만 읽고 본 테이블을 읽지 않는다(커버링 범위 스캔). `(account_code, trade_date)`는 인덱스가 없을 때보다 2배 넘게 느렸고, `account_code`로 시작하는 후보는 FK 인덱스를 MySQL이 조용히 지우는 문제가 있었다. 쿼리 타임아웃은 30초로 두고 넘기면 `GLA9010`으로 응답한다.

**결과.** 같은 기존 EC2와 RDS, 같은 측정 SQL로 10/28과 11/5에 쟀다(기간마다 예열 1 + 20회).

| 기간 | 개선 전 평균(ms) | 개선 후 평균(ms) | 배수 | 개선 후 p95(ms) |
|---|---:|---:|---:|---:|
| 하루 10/1 | 22,674.5 | 1,077.8 | 21.0배 | 1,158 |
| 한 달 9/1~9/30 | 25,322.3 | 14,915.4 | 1.70배 | 15,314 |
| 전 구간 9/1~10/5 | 26,820.0 | 19,770.7 | 1.36배 | 20,686 |

- 집계 결과는 개선 전과 같다. 기간별 대상 분개 행 수, 전 구간 차대변 checksum, API 응답 18개, 교차 측정 결과를 대조했다.
- DB 측정 중 RDS 읽기 IOPS와 처리량이 개선 전의 약 40%로 줄었다.
- 출처: [ph28_baseline_results.md](ph28_baseline_results.md) §2(개선 전), §3(후보 비교, 결정, 개선 후). 이슈 #773, PR #774, PR #910.

## 4. 결함 탐지율 (PH-28b)

결함 11가지를 GL과 원장에 하나씩 넣고 탐지 수단 4개를 모두 돌리는 행렬 테스트 `GlIntegrityCheckFaultDetectionTest`가 탐지율의 정본이다. 기대값이 테스트에 단언으로 들어 있어 탐지 쿼리가 바뀌면 CI가 깨진다.

| 탐지 수단 | 잡은 결함 |
|---|---|
| 기존 3개(P4 원장 잔액 대사, 전표 차대변 점검, 시산표) | 10건 중 7건 |
| 원장 전표 대사 추가 후 | 10건 중 10건 |
| DB가 주입 자체를 막음(`uk_gl_voucher_tx_type_reference_key`) | 1건, 분모에서 뺌 |

- 기존 수단이 놓친 3건은 GL 분개누락, 다른 참조 키로 복제한 전표, 같은 전표에 붙은 분개 쌍이다. 모두 차대변이 맞은 채 남아 시산표와 전표 차대변 점검에 걸리지 않는다.
- GL 결함은 원장 전표 대사가, 원장 결함은 P4 대사가 빠짐없이 잡는다. 둘 중 하나만으로는 10건을 채우지 못한다.
- Apache Fineract(`b94b2dd`)는 기표 시점 검사까지만 있고 저장 뒤 원장과 GL을 대조하는 통제가 없다. 우리는 그 위에 사후 대조를 하나 더 둔다.
- 출처: [ph28b_fault_injection_results.md](ph28b_fault_injection_results.md), [ADR-0009](../adr/0009-gl-integrity-controls.md). 이슈 #681, #684.

## 5. 정보계 마트 설계 (PH-75)

정본은 [info_mart.md](info_mart.md)다. P3는 설계를 10/16에 P5에 넘겼고, 적재(PH-76)와 조회 API(PH-77)는 P5가 구현했다.

- **마트 2종.** `mart_daily_account_balance`(계좌 × 거래일 일별 잔액 스냅샷)와 `mart_product_subscription_event`(가입과 해지 이벤트 1건 1행)다. 기준일은 GL과 같은 거래일이다.
- **정합성 대조 2개.** 마트 합계와 원장 합계가 원 단위로 같아야 적재를 확정한다(다르면 실패로 롤백). 마트 잔액 증감과 GL `20100` 증감은 차이가 있어도 커밋하고 차이를 남긴다. GL은 누적이 아니라 증감으로 비교한다. 훅 B가 나가기 전 이체는 원장에만 있어, 누적으로 비교하면 그 공백이 이후 모든 날짜에 남기 때문이다.
- **개인정보.** 마트에 PII 컬럼을 두지 않고, 고객과 계좌는 HMAC-SHA256 가명 키로만 남긴다. 키는 온프레미스 ETL에만 둔다.
- **기준 시점.** 응답의 `asOf`는 첫 적재일부터 빠짐없이 적재가 끝난 마지막 기준일이다.
- P5 결과: [ph76_etl_first_load.md](ph76_etl_first_load.md)(첫 적재, 대조, PII 검증), [ph77_info_api_measurement.md](ph77_info_api_measurement.md)(조회 API), [ph76_etl_ops_runbook.md](ph76_etl_ops_runbook.md)(운영).

### 5-1. 운영 확인 (11/5~11/6, UAT)

운영 3-Tier 관리자 정보계 대시보드(`/admin/info-dashboard`)에서 두 날짜를 비교했다. 브라우저는 WAS(`api.corebank.cloud`)의 `/admin/info/deposit-balances`, `/admin/info/product-subscriptions`만 부르고 정보계 VM은 WAS 뒤에서 호출된다.

| 기준시점 | 총 예수금 잔액 | 11월 신규 가입 | 11월 해지 |
|---|---|---|---|
| 2026-11-04 마감 (11/5 조회) | 1,060,000,760,000원 | 0건 | 0건 |
| 2026-11-05 마감 (11/6 조회) | 1,060,000,700,000원 | 6건 | 0건 |

- 11/5 UAT에서 은행 밖으로 나간 돈은 타행이체 6건 × 10,000원뿐이다. 시드 계좌의 입금, 당행이체, 정기예금 가입은 수신 안의 이동이라 총액이 그대로다. 총 예수금 차이 −60,000원이 이와 같다.
- 신규 가입 6건은 UAT 정기예금 가입(U-C07) 6건, 해지 0건은 실패한 만기해지와 중도해지(U-C09, U-C10, 롤백 확인)와 맞는다.
- 같은 날 원장 대사 불일치 화면(영업일 11/5)도 0건이다. 다만 이 화면은 대사가 돌지 않은 날도 0건이고, 정보계 기준시점은 대사보다 먼저 커밋되는 마감 신호라 대사 완료 근거가 아니다. 대사 스텝 완료는 운영 3-Tier `batch_execution_history`로 확인해야 한다(P5, PR #924).
- WAS 설정 `APP_INFO_API_BASE_URL`이 비어 있으면 서버가 정보계를 부르지 않고 `200`과 `asOf: null`을 돌려준다. 그래서 연결 여부는 응답 코드가 아니라 기준시점과 수치로 판정했다.
- 마트 증감과 GL `20100` 증감 대조가 이날 0이 아닌 증감에서도 일치했는지는 ETL 대조 로그로 확인해야 한다(P5). 아래 §6 "정보계 GL 대조" 항목은 그 확인 전까지 그대로 둔다.
