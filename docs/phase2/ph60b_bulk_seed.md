# PH-60b 대량 시드 설계·실행 가이드

## 1. 목적

PH-60b는 PH-60이 적재된 데이터베이스에 성능·대사·시산표·COB 검증용 데이터를 추가하는 작업이다. PH-60 데이터를 삭제하거나 다시 생성하지 않는다.

이 문서는 PH-60b 설계·실행 계약이다. 생성기, 실행 플래그, 단계별 파생 체크포인트와 스케줄러 격리 구현은 이 계약을 따른다.

전표와 분개 규칙의 정본은 [gl_journal_patterns.md](gl_journal_patterns.md)다.

## 2. PH-60과 PH-60b의 경계

| 구분 | PH-60 기존 데이터 | PH-60b 작업 |
|---|---:|---:|
| 고객 | 10,000명 | 50,000명 추가 |
| 계좌 | 30,000개 | 150,000개 추가 |
| 신규 거래 | 이체 235,000건 | TRF 2,900,000건 + SUB 100,000건 |
| 신규 `ledger_entry` | 500,000행 | 6,000,000행 |
| 신규 전표 | 개시 전표 1건 | 거래 전표 3,000,000건 |
| 신규 분개 | 개시 분개 2행 | 거래 분개 6,000,000행 |
| PH-60 보완 | 이체 전표 없음 | TRF 전표 235,000건 + 분개 470,000행 추가 |

PH-60b의 고객 5만 명·계좌 15만 개·거래 300만 건은 PH-60을 포함한 누적 최종 건수가 아니라 **추가 건수**다.

PH-60 보완분은 PH-60b 신규 거래 300만 건과 별도다. 따라서 **PH-60b 신규분의 목표 건수**는 거래 300만 건·`ledger_entry` 600만 행·전표 300만 건·분개 600만 행으로 고정한다. 같은 실행에서 만드는 PH-60 보완분까지 합산하면 전표는 323만 5천 건, 분개는 647만 행이지만, 이 합산값을 PH-60b 신규분 목표로 표현하지 않는다.

## 3. 신규 계좌 구성

고객 50,000명마다 요구불·정기예금·적금 계좌를 하나씩 추가한다.

| 계좌 유형 | 건수 | 자금 형성 방식 |
|---|---:|---|
| 요구불 | 50,000개 | TRF 입금 |
| 정기예금 | 50,000개 | SUB 초입금 |
| 적금 | 50,000개 | SUB 초입금 |

계좌번호는 실제 당행 코드 `088`과 상품 마스터의 prefix를 사용한다. PH-60의 `860` 계좌번호 규칙을 이어받지 않는다.

| 계좌·상품 | 은행코드 | prefix | 수량 | 예약 sequence |
|---|---:|---:|---:|---:|
| 요구불계좌 | `088` | `10` | 50,000개 | 6,000,001~6,050,000 |
| `PRD_BASIC_DEP` | `088` | `20` | 48,000개 | 6,000,001~6,048,000 |
| `PRD_SHORT_DEP` | `088` | `23` | 2,000개 | 6,000,001~6,002,000 |
| `PRD_REGULAR_SAVE` | `088` | `32` | 50,000개 | 6,000,001~6,050,000 |

QA 시드의 `V202609161800`과 같은 방식으로 계좌 INSERT와 같은 트랜잭션에서 `account_number_sequence`를 예약 대역의 마지막 번호까지 이동한 뒤 생성한다. 실행 전 실제 운영 채번값과 QA 대역이 예약 범위보다 작은지 확인하고, 완료 후에는 각 규칙의 `last_sequence`가 생성된 마지막 번호 이상인지 검증한다. 이미 더 큰 값이 사용된 규칙은 낮추지 않고 충돌하지 않는 상위 연속 대역을 다시 산정한다.

신규 계좌는 잔액 0원으로 생성한다. `account.balance`에 초기잔액만 직접 넣지 않는다. 계좌 컬럼을 변경해도 DB가 `ledger_entry`, `gl_voucher`, `gl_journal_entry`를 자동 생성하지 않기 때문에 잔액-원장 대사와 시산표가 어긋난다.

예·적금 계좌 100,000개에는 `product_subscription`과 SUB를 각 1건 생성한다. SUB 출금계좌는 같은 고객의 신규 요구불계좌다. 신규 요구불계좌의 최초 자금은 PH-60의 2026-09-01 개시 입금 뒤, 같은 날의 다른 거래보다 먼저 실행하는 TRF 50,000건으로 공급한다. 공급액은 건당 950만 원이며 PH-60 요구불계좌 하나가 5건(하루 4,750만 원)을 보낸다. 같은 거래일의 PH-60 이체 출금까지 합산해 5,000만 원 일 한도를 지키고, 실행 시점의 PH-60 계좌에서 출금 후에도 음수가 되지 않아야 한다. PH-60의 최초 고정 잔액은 가정하지 않는다. 운영에서는 정상 쓰기를 중단한 유지보수 시간에 실행하고, 각 구간에서 실제 입출금이 발생하는 계좌만 ID 오름차순으로 1,000개씩 `SELECT ... FOR UPDATE` 잠금한 뒤 50,000건 단위로 현재 잔액을 다시 조회한다. SUB 100,000건은 TRF 2,900,000건에 포함하지 않는 독립 거래다.

가입 기록은 상품 마스터를 정본으로 생성한다. 계좌 개설일과 가입일은 상품 판매 시작일보다 빠를 수 없고, 가입 기간·가입금액·금액 단위·`base_rate`·`applied_rate`는 가입 시점의 상품 및 금리 구간을 따라야 한다. 우대금리는 0이며 앱 가입 규칙과 같이 `base_rate + preferential_rate = applied_rate`를 만족한다. `expected_maturity_amount`도 앱과 같은 원 단위 버림 계산으로 채운다.

| 상품 | 수량 | 가입 가능일 | 가입 기간 |
|---|---:|---|---|
| `PRD_BASIC_DEP` | 48,000건 | 2026-08-01 이후 | 6~36개월 및 등록된 금리 구간 |
| `PRD_SHORT_DEP` | 2,000건 | 2026-07-15 이후 | 1개월 또는 2개월 |
| `PRD_REGULAR_SAVE` | 50,000건 | 2026-07-22 이후 | 6~24개월 및 등록된 금리 구간 |

거래 금액은 고정 시드값으로 재현 가능하게 만들되 원 단위 정수로 저장한다. 상품별 최소·최대 가입금액과 금액 단위를 지키고, 공급 계좌의 현재 출금 가능 잔액을 초과하거나 음수 잔액을 만들 수 없다.

PH-60의 개시 전표 `20260901-OPN-000001`은 그대로 유지한다. PH-60b에서는 개시 전표를 추가하지 않는다.

PH-60b 고객의 로그인 아이디는 `^[a-z][a-z0-9]{5,15}$`를 만족하는 `ph60b00001~ph60b50000` 형식을 사용한다. 밑줄이 있는 PH-60의 `ph60_user_00001` 형식을 복사하지 않는다.

## 4. 거래·원장·전표·분개 규격

### 4-1. PH-60b 신규분

| 거래 유형 | 거래 | `ledger_entry` | 전표 | 분개 |
|---|---:|---:|---:|---:|
| TRF | 2,900,000건 | 5,800,000행 | 2,900,000건 | 5,800,000행 |
| SUB | 100,000건 | 200,000행 | 100,000건 | 200,000행 |
| 합계 | 3,000,000건 | 6,000,000행 | 3,000,000건 | 6,000,000행 |

거래 1건마다 출금·입금 `ledger_entry` 2행, 전표 1건, 분개 2행을 만든다.

SUB 100,000건에는 이미 `MATURED`인 정기예금 1,000건과 `ACTIVE` 만기 임박 정기예금 1,000건을 포함한다. 상태 검증용 SUB를 100,000건 밖에 추가하지 않으므로 위 네 가지 신규분 합계는 각각 3,000,000건·6,000,000행·3,000,000건·6,000,000행을 유지한다.

### 4-2. PH-60 보완분

PH-60 이체 235,000건은 출금·입금 `ledger_entry` 470,000행이 있지만 대응하는 TRF 전표가 없다. PH-60b 실행 시 TRF 전표 235,000건과 분개 470,000행을 별도로 보완한다.

TRF와 SUB 전표의 `description`에는 해당 거래 원장 두 행이 공유하는 `transaction_number`를 넣는다. PH-24에서 `reference_key`가 추가되면 P3가 이 값을 옮긴다.

PH-60 이체일은 모두 2026-09-01이므로 보완 전표는 `20260901-TRF-000001~235000`을 사용한다. PH-60b의 2026-09-01 TRF 전표는 `20260901-TRF-235001`부터 이어서 채번한다.

PH-60b 신규 SUB도 TRF와 같은 거래번호 연결 규칙을 사용한다.

## 5. 거래 기간과 분포

거래 3,000,000건은 2026-09-01~10-05에 모두 배치한다. 9월 2,000,000건·10월 1~5일 1,000,000건이며, 9월 25일에 9월 거래의 20%인 400,000건을 배치한다. 운영 DB를 데모에 사용하므로 미래 거래가 현재 잔액에 미리 반영되지 않도록 기간을 제한한다.

| 패턴 | 고정 규칙 |
|---|---|
| 일반 구간 | 계좌에 균등 분포 |
| 핫스팟 | 상위 100계좌에 전체 거래의 30% 집중 |
| 급여일 | 9월 25일에 9월 거래의 20% 집중 |
| 주말 | 주말 일평균 건수를 평일 일평균의 20%로 설정 |

핫스팟 100계좌는 부하·이상거래 탐지 검증을 위해 급여일 등에 1일 5,000만 원을 의도적으로 초과한다. 이는 정상 고객 한도 준수 표본이 아니라 탐지 대상 데이터이며, PH-60 자금 공급 계좌의 일 한도 검증과 구분한다.

분포 계산 순서는 9월·10월 거래량 배분 → 9월 25일에 9월 거래의 20% 배정 → 나머지를 평일·주말 5:1 비율로 배분 → 각 날짜 거래의 30%를 핫스팟 계좌에 배정 → 나머지 70%를 일반 계좌에 균등 배정 순서로 고정한다. 여러 조건이 겹쳐도 전체 거래 건수 300만 건과 계좌별 잔액 불변식을 유지한다. 생성에는 고정 시드값을 사용해 같은 버전에서 동일한 데이터가 나오게 한다.

## 6. 자동이체·예약이체와 상태 데이터

자동이체와 예약이체를 각각 10,000건, 합계 20,000건 생성한다.

자동이체 시작일은 실제 적재일의 다음 날로 두고, 최초 실행일은 시작일 당일을 포함해 처음 도래하는 `transfer_day`로 계산한다. 예약이체 실행일도 적재 다음 날 이후로 분산한다. 적재 시점에 이미 지난 실행일을 가진 `NORMAL`·`WAITING` 행은 만들지 않는다.

| 대상 | 건수 | 상태·용도 |
|---|---:|---|
| 만기 계좌 | 정기예금 1,000개 | 이미 `MATURED`, 상태 조회·거래 제한 검증 |
| 만기 임박 후보 | 정기예금 1,000개 | `ACTIVE`, COB의 `ACTIVE → MATURED` 전이 검증 |
| 휴면 후보 | 요구불 1,000개 | `ACTIVE`, COB의 `ACTIVE → DORMANT` 전이 검증 |

이미 `MATURED`인 1,000개는 SUB 100,000건과 9월 거래 2,000,000건 안에 포함한다. 1개월 가입이 가능한 `PRD_SHORT_DEP`을 사용하고 2026-09-01에 가입해 2026-10-01에 만기되도록 한다. 이 고객들이 휴면 후보와 겹치므로 두 SUB 출금을 9/1에 마쳐 마지막 거래일을 고정한다. 기준일 2026-10-05의 최종 상태는 `MATURED`다. 만기 도래를 별도의 거래로 추가하거나 신규분 목표 건수를 늘리지 않는다.

`ACTIVE` 만기 임박 1,000개도 SUB 100,000건 안에 포함한다. 10/24~10/30 만기는 9/24~9/30 가입·1개월 기간으로, 11/1~11/22 만기는 9/1~9/22 가입·2개월 기간으로 만든다. 10/31은 9월 가입일에 1·2개월을 더해 만들 수 없어 비우되, 전체 최소·최대 만기일 2026-10-24~11-22는 유지한다. 2개월 금리 구간은 상품 마스터에 추가한다. 나머지는 `PRD_BASIC_DEP` 일반 `ACTIVE` 정기예금 48,000건과 `PRD_REGULAR_SAVE` 일반 `ACTIVE` 적금 50,000건으로 구성한다.

PH-60b의 휴면 판정 기준은 `ACTIVE` 요구불계좌에서 `COALESCE(last_transaction_at, created_at)` 기준 365일 동안 거래가 없는 경우로 고정한다. 휴면 후보 1,000개는 2026-09-01에 같은 고객의 SUB 초입금을 보낸 뒤 이후 TRF·자동이체·예약이체 대상에서 제외한다. 따라서 마지막 거래일은 2026-09-01이고, 영업일이 2027-09-01에 도달하면 `ACTIVE → DORMANT` 전이 대상이 된다. 원장과 다른 과거 `last_transaction_at`을 임의로 넣지 않는다.

| 식별자 | 시작 | 종료 | 건수 |
|---|---:|---:|---:|

| `account_id` | 100,000,001 | 100,150,000 | 150,000 |

| `subscription_id` | 100,000,001 | 100,100,000 | 100,000 |
| `ledger_entry_id` | 100,000,001 | 106,000,000 | 6,000,000 |

`journal_entry_id` 대역은 PH-60b 신규 분개 600만 행과 PH-60 보완 분개 47만 행을 합한 범위다. 전용 대역을 사용하기 전에 QA 시드 대역과 운영 DB의 실제 자동 채번 값을 다시 확인하고, 적재 후 일반 서비스가 이 대역을 사용하지 않도록 각 테이블의 자동 채번을 종료값 다음으로 이동한다.

## 8. 실행 플래그

PH-60b 구현 시 최소 시드와 대량 시드의 실행 플래그를 분리한다.

```properties
app.phase2-seed.minimum.execute=true
app.phase2-seed.bulk.execute=true
```

두 플래그를 동시에 `true`로 실행하면 기동을 거부해야 한다.

PH-60 최소 시드와 PH-60b 대량 시드는 서로 다른 로더를 사용하며 두 플래그를 동시에 `true`로 실행하면 기동을 거부한다.

## 9. 시드 전용 프로세스와 스케줄러 격리

PH-60b는 HTTP API나 Swagger UI로 노출하지 않는다. 정상 서비스 컨테이너와 별개의 일회성 프로세스로 실행한다.

운영에서는 PH-60 선행 데이터와 스냅샷을 확인하고 정상 쓰기를 중단한 뒤 다음 명령을 실행한다. 전표 번호 충돌을 피하려면 PH-24 런타임 기표 배포 전에 실행한다.

```bash
cd /home/ubuntu/corebank
docker compose run --rm --no-deps corebank-server \
  --spring.profiles.active=prod,phase2-seed \
  --app.phase2-seed.bulk.execute=true \
  --spring.main.web-application-type=none

echo $?
```

성공 로그의 `PH-60b bulk seed ready`와 종료 코드 `0`을 확인한다. 최소 시드 플래그는 함께 지정하지 않는다.

`--spring.task.scheduling.enabled=false`는 현재 프로젝트의 스케줄러 빈 등록을 막지 못한다. 따라서 `phase2-seed` 프로필에서는 `SchedulingConfig`를 제외해 정각, 00:10, 02:00 배치가 등록되지 않게 한다.

## 10. 단계별 트랜잭션과 체크포인트

PH-60b 전체를 하나의 트랜잭션으로 적재하지 않는다.

| 단계 | 작업 | 완료 확인 |
|---:|---|---|
| 1 | 고객·계좌 생성 | 고정 ID 대역 건수와 FK |
| 2 | PH-60 GL 보완 | TRF 전표 235,000건·분개 470,000행 |
| 3 | PH-60b TRF 구간 생성 | 거래·원장·전표·분개와 원장 쌍·차대변 |
| 4 | PH-60b SUB 구간 생성 | 가입·원장·전표·분개와 원장 쌍·차대변 |
| 5 | 시간순 잔액 정규화 | `occurred_at, ledger_entry_id` 누계와 원장·이체·계좌 잔액 일치 |
| 6 | 자동이체·예약이체 생성 | 각 10,000건과 참조 무결성 |
| 7 | 전체 정합성 검증 | §11 전 항목 통과 |

별도 체크포인트 테이블은 추가하지 않는다. 고정 ID 대역을 거래 50,000건 단위로 나누고, 각 구간의 예상 건수와 참조 무결성을 조회해 완료 여부를 판정하는 **파생 체크포인트**를 사용한다. 시작 ID부터 연속해서 완전한 구간만 완료로 인정한다. 중간 구간 누락, 예상보다 많은 행, 거래·원장·전표·분개 중 일부만 존재하는 구간은 자동 보정하지 않고 실패한다.

JDBC 배치는 2,000행, 트랜잭션은 거래 50,000건 단위로 시작하고 로컬·복원 RDS 실측 후 조정한다. 신규 거래 구간은 해당 거래의 `transfer` 또는 `product_subscription`, `ledger_entry`, `gl_voucher`, `gl_journal_entry`를 같은 구간 트랜잭션에서 커밋한다. 단계 체크포인트는 마지막으로 검증된 연속 ID 구간이다.

각 구간은 실제 입출금 대상 계좌만 ID 오름차순으로 1,000개씩 잠그고, `account`도 실제 출금·입금이 발생한 계좌만 갱신한다. TRF와 SUB 적재가 모두 끝나면 5,000계좌 단위 독립 트랜잭션으로 발생시각 순 누계를 계산해 `ledger_entry.balance_after`, `transfer.withdrawal_balance_after`, `account.balance`를 정규화한다. 계좌 단위 윈도 함수 결과는 다른 구간과 독립이므로 실패 후 같은 범위를 다시 실행해도 안전하다.

JDBC `batchSize`는 한 번에 전송하는 SQL 묶음의 크기만 조절한다. 서비스 메서드 전체가 하나의 트랜잭션이면 배치 크기를 100만으로 나눠도 DB의 undo, 락 유지 시간, 전체 롤백 범위와 재시작 지점은 바뀌지 않는다. 단계별 트랜잭션과 파생 체크포인트는 실패한 구간만 복구하고 이미 검증한 수백만 행을 다시 적재하지 않기 위해 필요하다.

재실행 정책은 다음과 같다.

- 전용 대역이 비어 있으면 첫 단계부터 실행한다.
- 완료 단계와 완료 구간은 건수·정합성을 다시 확인한 뒤 건너뛴다.
- 부분 적재는 마지막으로 검증된 연속 구간 다음부터 재개한다.
- 불완전하거나 구멍이 있는 구간은 실패시키고 운영자가 상태를 확인한다.
- 전체 완료 후 재실행은 거부한다.
- 자동·예약이체 생성 뒤 `advanceSequences()` 또는 최종 `validate()`에서 실패해 업무 건수가 모두 찬 경우에는 재실행이 `already complete`로 거부된다. 서비스를 다시 열기 전에 `advanceSequences()`의 채번 이동 SQL과 §11의 검증 SQL을 수동 실행한다. `ALTER TABLE`은 암묵적으로 커밋되므로 실패 시 일부 테이블의 자동 채번만 반영됐을 수 있으며, `ledger_entry_id_sequence`, 각 테이블 `AUTO_INCREMENT`, `account_number_sequence`, `last_transaction_at`을 모두 확인한다.
- `INSERT IGNORE`로 불일치를 숨기거나 완료로 판정하지 않는다.

## 11. 완료 기준

- PH-60b 신규 거래 3,000,000건
- PH-60b 신규 `ledger_entry` 6,000,000행
- PH-60b 신규 전표 3,000,000건
- PH-60b 신규 분개 6,000,000행
- PH-60 보완 TRF 전표 235,000건
- PH-60 보완 분개 470,000행
- PH-60 보완분까지 합산한 전표 3,235,000건·분개 6,470,000행(신규분 완료 기준과 구분)
- 계좌번호 150,000개가 `088`과 상품별 prefix·예약 sequence 규칙을 만족
- 고객 아이디 50,000개가 `^[a-z][a-z0-9]{5,15}$`를 만족
- 예·적금 계좌 100,000개에 `product_subscription`이 각 1행 존재
- 상품 가입일·기간·가입금액·금액 단위·기간별 `base_rate`·`applied_rate` 위반 0건
- 상품 가입의 `expected_maturity_amount` 누락 0건
- 거래마다 출금·입금 원장 각 1행
- 거래별 출금·입금 원장 금액 차이 0원
- `occurred_at, ledger_entry_id` 순 누계와 모든 `balance_after` 일치
- 모든 시간순 `balance_after`가 0 이상
- `transfer.withdrawal_balance_after`와 출금 원장의 `balance_after` 일치
- 거래마다 전표 1건과 분개 2행
- 장부 전체 개시 전표가 `20260901-OPN-000001` 1건
- `OPENING` 원장 합계와 예수금 `20100` 대변 합계 일치
- 계좌별 원장 합계와 `account.balance` 일치
- 전표별 차변 합계와 대변 합계 일치
- 음수 잔액 계좌 0건
- PH-60 자금 공급 계좌의 2026-09-01 총출금이 고객별 일 한도 이하
- 자동이체 `next_execution_date`의 일자가 `transfer_day`와 일치
- ID 대역 밖 침범 0건
- 실행 결과 기록에 전체 소요 시간과 마지막으로 검증된 연속 체크포인트를 남김
- P4 정합성 검수 통과

실제 MySQL 통합 테스트에서는 테스트 메서드 전체를 `@Transactional`로 감싸지 않는다. 첫 거래 구간 커밋 후 다음 구간에서 실패를 발생시켜 첫 구간의 거래·원장·분개가 남는지 확인하고, 재실행 시 연속 체크포인트 다음 구간부터 완료되는지 검증한다. PH-60 GL 보완도 운영과 같은 `INSERT ... SELECT`를 축소 ID 대역에 실행해 전표와 분개 건수를 확인한다.

## 12. 실행 플래그·스케줄러 격리 이슈 범위

코드 구현 전에 별도 이슈를 만들고 다음 인수기준을 포함한다.

- PH-60 최소 시드 `app.phase2-seed.minimum.execute=true`와 PH-60b 대량 시드 `app.phase2-seed.bulk.execute=true`로 분리
- 두 실행 플래그가 동시에 `true`이면 기동 거부
- PH-60 기존 실행 명령과 문서를 새 최소 시드 플래그로 변경
- PH-60b 시드 전용 애플리케이션 컨텍스트에서 스케줄러 빈 제외
- 일반 서버 기동과 기존 스케줄러 동작에 영향이 없는지 테스트
- 시드 성공 후 프로세스 종료 코드 `0` 검증
- 적재 또는 자체 검증 실패 시 0이 아닌 종료 코드 검증
- Docker Compose 일회성 컨테이너 실행과 정상 서비스 컨테이너 무영향 검증

## 13. 상품 조회 실패 정책

상품 코드 조회는 `JdbcTemplate.queryForObject()`가 행이 없을 때 `null`을 반환한다고 가정하지 않는다. `EmptyResultDataAccessException`을 명시적으로 변환하거나 선택 조회 결과를 검사해, 필요한 상품이 없으면 데이터 적재 전에 원인을 포함한 명확한 오류로 실패시킨다. 존재하지 않는 상품, 판매 시작일 이전 가입, 지원하지 않는 기간에 대한 테스트를 둔다.
