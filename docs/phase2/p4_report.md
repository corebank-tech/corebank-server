# P4 이체 정합성과 성능 리포트 (P4-RPT)

> S1부터 S4까지 P4가 맡은 이체 코어, 확장점, 타행 이체, 대사의 결과를 한 장으로 묶는다. 측정값은 2 ~ 5절, 구조 결과는 6절이다. PH-48 발표 자료의 입력이다.
> 수치마다 원 문서를 단다. **확정**은 원 문서에 측정 조건과 함께 기록된 운영 측정값이고, **로컬**은 맥북 Docker MySQL에서 잰 값, **테스트**는 자동 테스트로 보장하는 값이다.
> 이체 TPS · p95 · p99는 P1이 재고(PH-30) P4가 리포트한다([README 측정 지표](README.md)). 수치는 P1이 넘긴 원자료(#898, 11/6)의 4회 중앙값을 다시 집계하지 않고 그대로 옮긴다.

## 2. 이체 성능 (PH-30 S4)

### 2-1. 무엇을 바꿨나

| 변경 | 내용 | 릴리스 |
|---|---|---|
| LOCK-TUNE (#786, PR #837) | 거래번호를 100개씩 묶어 예약해 채번 행 락 대기를 없앴다 | 3 |
| OTP 해시 교체 (#834, PR #835, P1) | 이체 1건당 BCrypt 3회 중 OTP 2회를 HMAC-SHA256으로 바꿨다 | 3 |

E′1과 E′2는 같은 릴리스 3 이미지(`f72982e0`)에서 `APP_OTP_CODE_HASH_ALGORITHM`만 `bcrypt` · `hmac`으로 바꿔 잰 것이다. 그래서 E′1 ↔ E′2 차이는 OTP 해시 교체만의 효과다. C(릴리스 2) ↔ E′1에는 LOCK-TUNE 말고도 릴리스 3의 다른 변경(PR 65개, #877)이 섞여 있다.

### 2-2. 결과 (10/s, 4회 중앙값, 괄호는 최소 ~ 최대)

| 지표 | C 기준선 (10/26, 릴리스 2) | E′1 `bcrypt` (11/4) | E′2 `hmac` (11/4) |
|---|---|---|---|
| 성공 처리량 | 3.27건/s | 3.45 (2.88 ~ 3.52) | **10.00** (9.98 ~ 10.01) |
| 이체 p95 | 9,469.9ms | 9,585 (8,500 ~ 10,790) | **135** (118 ~ 2,378) |
| 이체 p99 | - | 12,900 (12,224 ~ 16,473) | **308** (177 ~ 3,523) |
| HTTP 실패율 | 21.96% | 회차별 20.9 ~ 24.2% | 회차별 0 ~ 0.014% |

- 인프라와 하네스 조건은 셋 다 같다. 기존 ALB → 단일 EC2(`t3.small`) → 기존 RDS(`db.t4g.micro`, 버퍼 풀 128MB), Hikari 풀 10, `perf/k6/load.js` 고정 도착률 수준당 180초, `SESSION_POOL = MAX_VUS = 200`, 성공 처리량은 `transfer_success` ÷ 180초다. 부하 생성 기기는 E′가 리눅스 4코어이고, C는 기록에 없다.
- **E′1 ≈ C다.** LOCK-TUNE이 들어간 릴리스 3에서도 `bcrypt`면 10/s에서 똑같이 포화된다. 병목이 행 락이 아니라 앱 EC2의 CPU(BCrypt)라는 10/6 분석([harness_results.md](harness_results.md) §3-3)과 맞는다. LOCK-TUNE의 효과는 운영 10/s 수치에 드러나지 않고, 로컬 마이크로벤치마크(2-4)로만 보인다.
- **E′2는 10/s를 견딘다.** BCrypt 2회를 걷어내자 처리량이 목표 도착률과 같아지고 p95가 70분의 1로 줄었다. E′2 최댓값은 1회차(11/4 16:07) 한 번이고 2 ~ 4회 p95는 118 ~ 146ms다.
- 한계 쪽은 1회씩만 쟀다(11/5). HMAC 15/s는 14.44건/s, p95 3,819ms로 한계 근처, 20/s는 4.44건/s로 포화다.
- 성공률은 분모가 셋이라(이체 호출 도달 중 성공, 목표 대비 성공, HTTP 실패율) 같은 회차도 값이 갈린다. 포화 구간에서는 반복이 이체 호출에 닿기 전 BCrypt 단계에서 끊기기 때문이다. 이 리포트는 처리량과 HTTP 실패율로 비교한다.

### 2-3. 단일 EC2 → 3-Tier (11/6, 1회)

| 10/s | 단일 EC2 C (릴리스 2 · `bcrypt`) | 단일 EC2 E′2 (릴리스 3 · `hmac`) | 3-Tier WAS 2대 (릴리스 3) |
|---|---|---|---|
| 성공 처리량 | 3.27건/s | 10.00건/s | 10.00건/s (1,800 / 1,800) |
| 이체 p95 | 9,469.9ms | 135ms | 448.2ms |
| 이체 p99 | - | 308ms | 779.3ms |
| HTTP 실패 | 21.96% | 0 ~ 0.014% | 0 / 7,400 |

- 3-Tier는 ALB → WAS `t3.small` 2대 → RDS `db.t3.small` Multi-AZ다. 5/s는 901건 모두 성공, p95 338.4ms였다.
- 같은 릴리스 3 · `hmac`끼리 보면 10/s 처리량은 같고 3-Tier가 p95 약 3배 길다. C → 3-Tier의 3.27 → 10.00건/s는 대부분 OTP 해시 교체 효과이고, 10/s로는 환경 전환이 처리량을 늘렸는지 판단할 수 없다. RDS Multi-AZ 동기 복제, ALB → 사설 서브넷 구간, 부하 생성 기기(3-Tier는 맥북) 차이가 섞여 있어 나누지 않았다.
- 10/s까지만 재서 3-Tier의 포화 도착률은 모른다. WAS 대수에 따른 확장 효율은 P5 PH-56 범위다.

| 동시 스레드 | 처리량 전 → 후 | 행 락 대기(5,000건 회차) 전 → 후 |
|---|---|---|
| 8 | 420 → 10,363건/초 | 4,999 → 0 |
| 32 | 446 → 21,545건/초 | 4,999 → 0 |
| 64 | 435 → 22,090건/초 | 4,999 → 0 |

## 4. 타행 장애 격리 (PH-33-② · PH-36 · PH-36b)

모의 대외기관을 `NONE` · `NO_RESPONSE`로 바꿔 당행 5/s와 타행 1/s를 같은 3분 동안 흘렸다(`perf/k6/interbankFault.js`).

| 당행 이체 | 1회차 NONE → NO_RESPONSE (11/5) | 2회차 NONE → NO_RESPONSE (11/6) |
|---|---|---|
| p95 | 132.5 → 138.8ms | 197.3 → 165.7ms |
| p99 | 272.9 → 220.4ms | 429.6 → 312.5ms |
| 성공 · 처리량 | 100%, 5.01 → 5.00건/s | 100%, 5.01 → 5.01건/s |
| 타행 | 성공 180 → TIMEOUT 52 · 서킷 거절 129 | 성공 181 → TIMEOUT 53 · 서킷 거절 128 |

- 상대 은행이 3초씩 답하지 않아도 당행 이체는 느려지지 않았다. 서킷이 열려 뒤따르는 타행 요청을 채번 전에 끊었고, 커넥션 풀 10도 바닥나지 않았다(`HikariPool` 타임아웃 로그 0건).
- 11/6 첫 NONE은 쉬던 서버에 처음 건 부하라 p95 605.9ms로 튀어 비교에서 뺐다. 같은 조건을 4분 뒤 다시 잰 값이 위 197.3ms다.
- TIMEOUT은 조회거래가 1분 주기로 모두 SUCCESS로 확정했다. 모의 대외기관이 송금은 처리하고 응답만 보내지 않았으니 맞는 결과다.
