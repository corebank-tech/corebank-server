## 2. PH-13 대량 배치 성능 비교 (2026-11-10)

### 측정 조건

| 항목 | 내용 |
| --- | --- |
| 환경 | 신규 AWS 3-Tier EC2 + 운영 RDS (MySQL 8.4.10) |
| Docker 이미지 | `corebank/corebank-server:e6dfafe4dfe64bb3fb94a82382e7a93d72ed3284` |
| 데이터 | PH-60b, 150,000계좌 (`100000001~100150000`) |
| 계산 기간 | `[2026-09-01, 2026-10-01)` |
| Java | PH-11 기준선 측정기, `app.ph13.sql-enabled=false` |
| SQL | PH-13 측정기, `batchSize=1000` |
| 측정 횟수 | 방식별 3회 |

동일 EC2·RDS·이미지·계좌 범위에서 순차 실행했다. 운영 WAS는 변경하지 않았으며, 일회성 측정 컨테이너에서 `prod,phase2-seed` 및 측정 전용 프로필을 사용했다.

측정 컨테이너는 `server.port=0`, `spring.flyway.enabled=false`, `spring.datasource.hikari.read-only=true`로 실행했다.

전체 실행시간 중앙값:

- SQL: **44.069초**
- 실행시간 감소율: **92.66%**
- 처리 속도: **약 13.62배**

Java 지연시간은 계좌 1건, SQL 지연시간은 1,000계좌 배치 1회의 측정값이므로 평균·p95·p99를 직접 비교하지 않는다.

SQL 1·3회차에서 평균이 p95보다 높은 것은 통계적으로 가능한 결과다. 측정기는 150개 배치를 정렬해 143번째를 p95, 149번째를 p99로 사용한다. 가장 느린 150번째 배치는 평균에 포함되지만 두 백분위 지표에서는 제외된다. 개별 배치 기록이 없어 지연 원인은 확인하지 못했다.

### 계산 결과 정합성

| 항목 | Java 3회 | SQL 3회 |
| --- | ---: | ---: |
| 처리 계좌 수 | 150,000 | 150,000 |
| Checksum | `14,250,000,000,000` | `14,250,000,000,000` |
| 0원 적수 건수 | 13,855 | 13,855 |
| Fingerprint SHA-256 | 일치 | 일치 |

Fingerprint:

`186efb0a229c07976090b7818e9dddee48c01659d692551839b8567aaa66a01c`

6회 모두 Checksum·Fingerprint·0원 적수 건수가 일치했다. Fingerprint는 계좌 ID와 계산 결과를 순서대로 반영하므로 계좌별 정합성을 뒷받침한다. 단, 계좌별 결과 파일을 별도 추출해 직접 비교한 것은 아니다.

### 제한사항

- 최초 Java 측정 중 Spring Session 만료 세션 정리 작업이 읽기 전용 DB 연결에서 DELETE를 시도해 오류가 발생했다. DELETE는 차단됐고 적수 계산은 완료됐다. 오류 확인을 위해 중단한 별도 실행은 결과에서 제외했다.
- 운영 WAS의 읽기 부하와 RDS 내부 작업을 완전히 격리하지 못했다.
- Java·SQL 각 2·3회차는 종료 코드 0을 확인했다. 각 1회차는 측정 완료 로그만 확인했고 종료 코드는 보존하지 않았다.
- SQL 2회차의 배치 p99는 882.921ms로 다른 회차보다 높았다. 개별 배치 소요시간을 보존하지 않아 원인은 확인하지 못했다.

## 3. PH-13 단건 적수 계산 성능 비교 (2026-11-10)

대량 배치 집계와 별개로, 계좌 하나씩 계산할 때의 성능을 확인했다.

### 측정 조건

- 환경 및 Docker 이미지: 2절의 15만 계좌 측정과 동일
- 계좌: `100000001~100001000` (1,000개)
- 계산 기간: `[2026-09-01, 2026-10-01)`
- Java: PH-11 측정기에서 기존 적수 계산 서비스 호출
- SQL: PH-13 측정기에서 `batchSize=1`로 SQL 집계 포트 호출
- 방식별 3회, 운영 WAS 설정 변경 없음

### 측정 결과

| 방식 | 회차 | 완료 시각(KST) | 전체 시간 | 평균 | p95 | p99 |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| Java | 1 | 17:07:41 | 8.343초 | 8.332ms | 15.519ms | 20.650ms |
| SQL | 1 | 17:09:21 | 5.689초 | 5.233ms | 9.343ms | 13.023ms |
| SQL | 2 | 17:16:27 | 6.110초 | 5.591ms | 9.838ms | 15.874ms |
| Java | 2 | 17:17:11 | 8.299초 | 8.285ms | 16.120ms | 21.267ms |
| Java | 3 | 17:17:54 | 8.353초 | 8.340ms | 15.926ms | 20.258ms |
| SQL | 3 | 17:18:35 | 6.149초 | 5.644ms | 8.725ms | 12.546ms |

전체 실행시간 중앙값:

- Java: **8.343초**
- SQL: **6.110초**
- 실행시간 감소율: **26.76%**
- 처리 속도: **약 1.37배**

6회 모두 `zeroResultCount=0`이고 Fingerprint가 일치했다.

Fingerprint:

`133f4ce752880b5db85fa778e9098b6e3a89cc43002f774ae587ad5b3feae658`

Java Checksum은 3회 모두 `95,173,500,000`이었다. SQL Checksum은 11자리 숫자를 전화번호로 인식하는 로그 마스킹(`MaskingConverter`)으로 인해 가려졌다.

두 측정기는 계좌 ID와 적수값을 동일한 순서로 SHA-256 Fingerprint에 반영하며, 6회 모두 Fingerprint가 일치했다. 따라서 계좌별 계산 결과가 일치한다는 강한 정합성 근거를 확보했다. 다만 SQL Checksum 원문은 별도로 확인하지 않았다.

**측정 한계:** Java 측정기는 서비스 UseCase를 호출하지만 SQL 측정기는 집계 포트를 직접 호출한다. 또한 측정기의 로깅 오버헤드가 다르다. 따라서 이번 결과는 단건 계산 방식의 예비 성능 비교이며, 실제 만기해지·중도해지 API 응답시간의 개선율로 해석하지 않는다.

## 4. SQL 실행계획 및 RDS 자원 관측

### SQL 실행계획

2026-11-10 운영 RDS에서 1,000계좌(`100000001~100001000`)의 SQL 배치 집계를 `EXPLAIN ANALYZE`로 분석했다.

| 항목 | 기본 실행계획 | 인덱스 강제 |
| --- | ---: | ---: |
| 인덱스 | `ix_le_account_dir` | `ix_le_account_time` |
| 전체 실행시간 | 36.7ms | 38.6ms |
| 원장 Nested Loop 시간 | 8.87ms | 17.9ms |
| 기간 내 원장 처리 행 | 1,668 | 1,668 |
| 반환 계좌 수 | 1,000 | 1,000 |

두 실행계획 모두 원장 전체 테이블 스캔 없이 인덱스를 사용했다. CTE 구체화와 윈도 함수 처리에 따른 정렬·임시 테이블 사용을 확인했다.

각 실행계획을 1회씩만 측정했으므로 인덱스 간 성능 우열을 확정할 수 없다. 신규 인덱스 추가나 `FORCE INDEX` 적용을 정당화할 근거는 확인되지 않아 기존 구현을 유지한다.

### RDS 자원 관측

일반 RDS 지표는 1분 평균, CPUCreditBalance는 제공된 5분 간격 데이터를 사용했다. ReadIOPS 최고치는 09:50 KST로, 6회 측정 실행 시간 밖에서 기록됐다.

CPU 크레딧 고갈이나 지속적인 디스크 대기 누적은 관측되지 않았다. 다만 가용 메모리가 낮고 스왑이 사용 중이었다. 스왑 입출력량은 측정하지 않아 성능 병목 여부를 판정할 수 없다.

CloudWatch는 RDS 전체 부하를 집계하므로 측정 작업만의 자원 사용량과 SQL 실행 순간의 최고 부하를 분리할 수 없다.

## 5. 결론 및 적용 범위

| 검증 항목 | 결과 |
| --- | --- |
| 15만 계좌 대량 SQL 배치 처리 | 전체 실행시간 중앙값 **92.66% 감소** |
| 단건 적수 계산 반복 호출 | 전체 실행시간 중앙값 **26.76% 감소** |
| 계산 정합성 | 대량 배치 6회 Checksum·Fingerprint 일치, 단건 6회 Fingerprint 일치 |
| SQL 실행계획 | 전체 원장 테이블 스캔 없음, 기존 인덱스 유지 |
| 실제 해지 API 응답시간 | 미측정 |
| 운영 SQL 활성화 | 미수행 |

이번 측정은 동일 이미지에 포함된 Java·SQL 계산 경로를 비교한 것으로, 서로 다른 릴리스 이미지의 배포 효과를 측정한 것은 아니다. 특히 15만 계좌 배치 결과는 단건 API 응답시간 개선을 의미하지 않는다.

`app.ph13.sql-enabled`의 기본값은 `false`이며, 이번 작업에서 운영 WAS의 설정을 변경하지 않았다. 실제 해지 API에 SQL 계산을 적용하려면 별도의 통합·회귀 테스트와 배포 검증이 필요하다.

**PH-13의 대량 배치 및 단건 적수 계산 성능 검증은 완료했다.** 운영 SQL 활성화와 실제 API 응답시간 검증은 이번 측정 범위에 포함하지 않는다.
