## 2. PH-60b 15만 계좌 개선 전후 측정 (2026-11-10)

### 측정 환경

| 항목 | 값 |
| --- | --- |
| 측정일 | 2026-11-10 KST |
| 측정 환경 | 신규 AWS 3-Tier의 EC2 및 운영 RDS |
| Docker 이미지 | `corebank/corebank-server:e6dfafe4dfe64bb3fb94a82382e7a93d72ed3284` |
| 대상 계좌 | PH-60b 150,000건 |
| 계좌 ID 범위 | `100000001` ~ `100150000` |
| 계산 기간 | `[2026-09-01, 2026-10-01)` |
| 기존 방식 | PH-11 Java 계좌별 계산, `app.ph13.sql-enabled=false` |
| 개선 방식 | PH-13 SQL 집계, 배치 크기 1,000 |
| 측정 횟수 | 각 방식 3회 |
| 실행 순서 | Java 1 → SQL 1 → SQL 2 → Java 2 → Java 3 → SQL 3 |

측정 전에 팀에 운영 DB 쓰기 작업과 다른 성능 측정 중단을 공지했다. 모든 회차에서 동일한 EC2·RDS·이미지·계좌 범위·계산 기간을 사용했다.

운영 WAS는 교체하지 않았으며, 동일 이미지를 사용하는 일회성 Docker 컨테이너에서 측정했다. 측정 컨테이너는 `prod,phase2-seed`와 측정 전용 프로필을 사용하고, 임의 웹 포트(`server.port=0`)로 실행했다. Flyway를 비활성화하고 HikariCP 연결을 읽기 전용으로 설정했다.

| 방식 | 회차 | 완료 시각(KST) | totalSeconds | 평균 | p95 | p99 |

| Java | 1 | 10:06:20 | 627.338s | 4.178ms | 6.422ms | 12.901ms |

Java의 평균·p95·p99는 계좌 단위이며, SQL의 평균·p95·p99는 1,000계좌 배치 단위이다. 서로 다른 측정 단위이므로 해당 백분위 지표를 직접 비교하지 않는다.

### 전체 실행시간 비교

| 지표 | Java 기존 방식 | SQL 집계 방식 |
| --- | ---: | ---: |
| 중앙값 | 600.394초 | 44.069초 |
| 평균 | 606.660초 | 43.845초 |
| 최솟값 | 592.249초 | 41.602초 |
| 최댓값 | 627.338초 | 45.865초 |

중앙값 기준으로 전체 실행시간이 **92.66% 감소**했고, 처리 속도는 약 **13.62배 향상**됐다. 평균 기준 실행시간 감소율은 92.77%이다.

### 계산 결과 정합성

| 항목 | Java 3회 | SQL 3회 | 결과 |
| --- | --- | --- | --- |
| accountCount | 150,000 | 150,000 | 일치 |
| checksum | `14250000000000` | `14250000000000` | 일치 |
| zeroResultCount | 13,855 | 13,855 | 일치 |
| fingerprintSha256 | 동일 | 동일 | 일치 |

Fingerprint SHA-256: `186efb0a229c07976090b7818e9dddee48c01659d692551839b8567aaa66a01c`

모든 회차에서 Checksum·Fingerprint·0원 적수 건수가 일치했다. Fingerprint는 계좌 ID와 적수값을 순서대로 해시하므로 계좌별 계산 결과가 일치한다는 강한 근거다. 다만 계좌별 결과를 별도 파일로 추출해 직접 대조한 것은 아니다.

2·3회차의 Java·SQL 측정은 종료 코드 0을 확인했다. 최초 각 1회차는 측정 완료 로그를 확인했으며 종료 코드는 별도로 보존하지 않았다.

### 특이사항 및 제한사항

- 최초 Java 측정 중 Spring Session의 만료 세션 정리 작업이 읽기 전용 DB 연결에서 DELETE를 시도해 오류가 발생했다. 해당 작업은 적수 계산과 별개이며, DELETE는 차단됐다. 계산기는 15만 계좌 처리를 완료했다.
- 오류 확인을 위해 중단했던 별도 실행은 측정 결과에서 제외했다.
- SQL 2회차 배치 p99는 882.921ms로 다른 회차보다 높았다. 개별 배치 실행시간을 기록하지 않았으므로 원인은 확인하지 못했다.
- 팀 작업과 다른 성능 측정은 중단하도록 공지했으나, RDS 내부 작업과 운영 WAS의 모든 읽기 부하까지 격리한 것은 아니다.
- 기존 3만 계좌 베이스라인은 다른 환경에서 측정됐으므로 이번 개선율 계산에 사용하지 않았다.
- 동일 Docker 이미지에 포함된 두 측정 경로를 비교했으므로 서로 다른 릴리스 이미지의 배포 효과를 측정한 것은 아니다.

## 3. PH-13 측정 판정과 후속 과제

PH-60b 15만 계좌를 대상으로 한 기존 Java 방식과 SQL 배치 집계 방식의 반복 측정에서, SQL 방식의 전체 실행시간이 중앙값 기준 92.66% 감소했다. Checksum·Fingerprint·0원 적수 건수는 모든 회차에서 일치했다.

따라서 **15만 계좌 대량 적수 집계의 성능 개선 및 결과 정합성 측정은 완료**로 판정한다.

단, 이번 측정은 대량 배치 경로의 성능을 검증한 것이다. `AccumulatedDailyBalanceService.calculate()`의 개별 호출은 배치 측정과 구조가 다르며, `app.ph13.sql-enabled`의 기본값은 `false`이다. 따라서 이번 결과만으로 실제 만기해지·중도해지 API의 성능 개선이나 SQL 집계 방식의 운영 활성화를 입증하지 않는다.

후속 확인 대상은 실제 서비스 적용 설정, 단건 서비스 경로 검증, 실행계획·인덱스 검토 및 관련 회귀 테스트다.
