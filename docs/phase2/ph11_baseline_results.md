### SQL 실행계획 및 인덱스 검증

2026-11-10 신규 AWS 운영 RDS(MySQL 8.4.10)의 `minicore`에서 PH-13 적수 집계 SQL을 대상으로 `EXPLAIN ANALYZE`를 수행했다.

분석 대상은 계좌 `100000001~100001000`의 1,000계좌 배치이며, 계산 기간은 `[2026-09-01, 2026-10-01)`이다.

| 항목 | 기본 실행계획 | `ix_le_account_time` 강제 |
| --- | ---: | ---: |
| 사용 인덱스 | `ix_le_account_dir` | `ix_le_account_time` |
| 전체 실행시간 | 36.7ms | 38.6ms |
| 원장 Nested Loop 실행시간 | 8.87ms | 17.9ms |
| 기간 내 원장 처리 행 수 | 1,668 | 1,668 |
| 최종 반환 계좌 수 | 1,000 | 1,000 |
| `ledger_entry` 전체 스캔 | 없음 | 없음 |

기본 실행계획에서 MySQL은 `ix_le_account_dir(account_id, direction, occurred_at)`를 선택했다. `account_id`로 인덱스를 조회하고 `occurred_at` 범위 조건을 Index Condition으로 처리했다.

`ix_le_account_time(account_id, occurred_at DESC)`를 강제한 경우에도 전체 테이블 스캔 없이 인덱스를 사용했으나, 단일 실행에서는 전체 실행시간이 개선되지 않았다.

CTE 구체화, `ROW_NUMBER`, `LEAD` 처리에 따른 정렬 및 임시 테이블 사용을 확인했다. 실행계획의 예상 행 수와 실제 행 수에 차이가 있으나, 이번 1,000계좌 실행에서 대규모 전체 테이블 스캔은 관측되지 않았다.

두 실행계획은 각각 1회씩만 측정했으므로 1.9ms 차이로 인덱스의 일반적인 우열을 확정할 수 없다. 현재 결과만으로 신규 인덱스 추가나 `FORCE INDEX` 적용의 필요성은 확인되지 않아 기존 구현을 유지한다.

### RDS 자원 사용량 관측

2026-11-10 09:34~10:44 KST 구간의 AWS CloudWatch 지표를 확인했다. 일반 RDS 성능 지표는 1분 주기의 Average 통계를 사용했으며, CPUCreditBalance는 제공된 5분 간격 데이터를 기준으로 분석했다.

| 지표 | 관측 결과 |
| --- | --- |
| CPUUtilization | 최고 35.79% (10:16 KST) |
| FreeableMemory | 최저 약 55.3MiB (10:06 KST) |
| ReadIOPS | 최고 101.68 (09:50 KST) |
| DiskQueueDepth | 최고 약 0.410 (10:38 KST) |
| ReadLatency | 최고 12ms (09:56 KST) |
| SwapUsage | 약 258.94~344.47MiB |
| CPUCreditBalance | 약 573.53~576 크레딧 |

기존 Java 방식 측정 중에는 CPU 사용률이 주로 26~28% 수준으로 관측됐다. SQL 방식은 실행시간이 짧고 일부 구간에 CPU·읽기 I/O가 집중됐다.

DiskQueueDepth는 대부분 0에 가까웠으며 지속적인 디스크 대기 누적은 관측되지 않았다. CPUCreditBalance도 높은 수준으로 유지되어 CPU 크레딧 고갈은 관측되지 않았다.

다만 FreeableMemory가 약 55.3MiB까지 감소했고 SwapUsage는 약 259~344MiB 수준이었다. 측정 시작 이전부터 스왑 공간을 사용하고 있었으므로 PH-13이 스왑 사용을 처음 유발했다고 볼 수 없다.

SwapUsage는 사용 중인 스왑 용량을 의미하며 실제 스왑 입출력 횟수는 아니다. 이번 측정에서 `swap.in`, `swap.out`은 확인하지 않았으므로 스왑에 따른 성능 병목 여부는 판정하지 않는다.

CloudWatch는 RDS 인스턴스 전체 지표이며 운영 WAS와 RDS 내부 작업의 부하도 포함한다. 따라서 PH-13 측정만의 CPU·메모리·I/O 사용량을 분리할 수 없고, 개별 실행시간이 1분보다 짧은 SQL 측정의 순간 최고 부하도 정확히 파악할 수 없다.

최종적으로 15만 계좌 전체 실행시간의 개선과 계산 결과 정합성은 검증됐다. CPU 크레딧 고갈과 지속적인 디스크 대기 누적은 관측되지 않았으나, 운영 RDS의 낮은 가용 메모리와 스왑 사용량은 별도 운영 점검 대상으로 남긴다.

### 특이사항 및 제한사항

- 최초 Java 측정 중 Spring Session의 만료 세션 정리 작업이 읽기 전용 DB 연결에서 DELETE를 시도해 오류가 발생했다. 해당 작업은 적수 계산과 별개이며, DELETE는 차단됐다. 계산기는 15만 계좌 처리를 완료했다.
- 오류 확인을 위해 중단했던 별도 실행은 측정 결과에서 제외했다.
- SQL 2회차 배치 p99는 882.921ms로 다른 회차보다 높았다. 개별 배치 실행시간을 기록하지 않았으므로 원인은 확인하지 못했다.
- 팀 작업과 다른 성능 측정은 중단하도록 공지했으나, RDS 내부 작업과 운영 WAS의 모든 읽기 부하까지 격리한 것은 아니다.
- 기존 3만 계좌 베이스라인은 다른 환경에서 측정됐으므로 이번 개선율 계산에 사용하지 않았다.
- 동일 Docker 이미지에 포함된 두 측정 경로를 비교했으므로 서로 다른 릴리스 이미지의 배포 효과를 측정한 것은 아니다.

## 3. PH-13 측정 판정과 후속 과제

PH-60b 15만 계좌를 대상으로 한 기존 Java 방식과 SQL 배치 집계 방식의 반복 측정에서, SQL 방식의 전체 실행시간이 중앙값 기준 92.66% 감소했다. Checksum·Fingerprint·0원 적수 건수는 모든 회차에서 일치했다.

따라서 **15만 계좌 대량 적수 집계의 성능 개선 및 결과 정합성 측정은 완료**로 판정한다.

단, 이번 측정은 대량 배치 경로의 성능을 검증한 것이다. `AccumulatedDailyBalanceService.calculate()`의 개별 호출은 배치 측정과 구조가 다르며, `app.ph13.sql-enabled`의 기본값은 `false`이다. 따라서 이번 결과만으로 실제 만기해지·중도해지 API의 성능 개선이나 SQL 집계 방식의 운영 활성화를 입증하지 않는다.

후속 확인 대상은 실제 서비스의 `app.ph13.sql-enabled` 활성화 정책, 단건 서비스 경로 검증 및 관련 회귀 테스트다. 운영 규모 SQL 실행계획·인덱스 비교와 CloudWatch 자원 사용량 관측은 완료했으며, 신규 인덱스 추가는 필요성이 입증되지 않아 보류했다. RDS 메모리 여유 및 스왑 입출력 상태는 별도 운영 점검 대상으로 관리한다.
