# PH-57 용량 산정

> 원장 650만 · 분개 647만 행 기준으로 스토리지 · 목표 TPS · 인스턴스 타입을 정한다(#539).
> **여유를 일부러 적게 잡는다** — 병목이 드러나야 개선 서사가 선다. 단, 디스크가 차는 것은 병목이 아니라 장애라 §2-5에서 따로 다룬다.
> PH-51(컴퓨트) · PH-70(P2 RDS) · PH-100(온프레미스 VM)이 이 표를 참조한다.
>
> 표기 — **실측**: 문서에 기록된 측정값 · **계산**: DDL · 산식으로 낸 값 · **추정**: 가정이 들어간 값

## 2. 스토리지

### 2-1. 이체 1건의 크기

이체 1건은 이체 1행 · 원장 2행 · 전표 1행 · 분개 2행을 만든다.

| 테이블 | 행/이체 | 행 + 인덱스(계산) | 계 |
|---|---:|---:|---:|
| `ledger_entry` (보조 인덱스 3) | 2 | 약 300B | 600B |
| `transfer` (보조 인덱스 4 + FK 인덱스) | 1 | 약 360B | 360B |
| `gl_journal_entry` (보조 인덱스 3) | 2 | 약 195B | 390B |
| `gl_voucher` (보조 인덱스 2) | 1 | 약 240B | 240B |
| **계산 합계** | | | **약 1.6KB** |
| **로컬 실측** (70MB ÷ 5만 건) | | | **약 1.4 ~ 1.5KB** |

계산과 실측이 10% 안에서 맞는다. 이후는 **이체 1건 = 1.5KB**로 잡는다.

API로 들어온 이체는 시드에 없던 행을 더 만든다. 계좌비밀번호 검증과 이체 요청이 각각 멱등키(`idempotency_key`) 1행, 계좌비밀번호 검증과 OTP 검증이 각각 인증 토큰(`auth_token`) 1행이다(`perf/k6/lib/transfer.js`). 4행 합계 약 1.2KB(추정)를 더해 **API 이체 1건 = 약 2.7KB**로 잡는다. 토큰 · 멱등키는 TTL 뒤 지워져도 `.ibd` 파일은 줄지 않는다.

### 2-4. 3-Tier 가동 20일(10/19 ~ 11/9) 증가분

| 원인 | 건수(추정) | 크기 |
|---|---:|---:|
| 자동 · 예약이체 배치 | 하루 수백 건 | 무시할 수준 |
| 부하 측정 (PH-56 일반 · 핫스팟, PH-30 S4 재측정, #531, PH-101-②) | 최대 약 20만 건 | 약 0.5GB (API 이체 1건 2.7KB) |
| binlog (온프레미스 복제용) | — | 보존 24시간 동안의 쓰기량. 측정이 많은 날도 1GB 이하(추정) |

부하 측정은 3분 회차를 수준별로 4회씩 돈다. PH-56을 1 · 2 · 3 · 5 · 10/s 다섯 수준, 일반 · 핫스팟 두 계열, 1대 · 2대 두 구성으로 돌리면 약 6만 건이고, 2대에서 20 · 40/s를 더해도 약 15만 건이다. 다른 측정을 합쳐 20만 건을 넘기 어렵다. 20 TPS로 쉬지 않고 돌려도 20만 건은 약 3시간 분량이다.

**예상 사용량은 7.3GB + 0.5GB + 1GB ≈ 약 9GB, 20GiB(21.47GB)의 약 40%다**(추정).

RDS binlog는 레플리카가 따라왔는지와 상관없이 **보존 시간(`binlog retention hours`)이 지나면 지워진다.** 그래서 VPN이 끊겨도 디스크가 끝없이 차지는 않는다. 대신 보존 시간보다 오래 끊기면 레플리카가 끊긴 지점을 잃어 다시 만들어야 한다. 보존 시간은 24시간으로 정해져 있고(`tasks.md` PH-70-②), 리허설에서 복제 지연과 binlog 사용량을 보고 P2가 48시간 이상으로 늘릴지 판단한다.

### 2-5. RDS 디스크 — gp3 20GiB

- RDS MySQL gp3의 최소가 20GiB라 더 작게 잡을 수 없다. 예상 사용률은 약 40%다. 현재 운영 RDS도 gp3 20GiB이고 자동 확장은 꺼져 있다(실측).
- **gp2는 쓰지 않는다.** 10/10 적재 때 gp2 20GiB(기본 100 IOPS)의 크레딧이 바닥나 단순 COUNT가 3분을 넘겼고, gp3로 바꾸자 ReadIOPS가 약 100에서 1,500 ~ 1,900이 됐다(실측).
- **자동 확장(`max_allocated_storage`)은 걸지 않는다**(10/15 결정). 예상 사용률이 약 40%라 원칙대로 20GiB 고정으로 둔다. 아래 표의 위험(디스크가 차면 쓰기가 멈추고, 직전에 스토리지를 바꿨으면 6시간 동안 못 늘린다)은 감수한다. 대신 시드 재실행 · 대량 UPDATE처럼 디스크를 크게 쓰는 작업 전에는 CloudWatch `FreeStorageSpace`를 먼저 본다.

| | 자동 확장을 건다 | 20GiB 고정 |
|---|---|---|
| 디스크가 차면 | 여유가 10% 아래로 5분 이상 가면 AWS가 자동으로 늘린다 | 인스턴스가 `storage-full`이 되고 쓰기가 멈춘다. 사람이 콘솔에서 늘려야 한다 |
| 직전에 스토리지를 바꿨으면 | 6시간 안에는 자동 확장도 막힌다 | 6시간 동안 늘릴 수 없다 — 그 사이 장애 |
| 비용 | 늘어나기 전에는 0 | 0 |
| "여유 적게" 원칙 | 평소 할당은 20GiB 그대로라 해치지 않는다 | 원칙에 그대로 맞는다 |
| 차게 만들 수 있는 일 | 대량 UPDATE(10/10 정규화처럼 undo · binlog가 수 GB) · 365일 시산표 같은 큰 정렬의 임시 파일 · 예상보다 긴 부하 측정 | |

## 3. 목표 TPS

### 3-1. 목표 두 단계

| 단계 | 값 | 판정 |
|---|---|---|
| 서비스 목표 | 300 TPS @ p95 200ms (상향 500) | 이 사양으로 미달 — 코드 개선 뒤의 목표 |
| **이번 사양의 기대 처리량** | **약 10 TPS** (1대 실측 × 2, 선형 가정 상한) | 실측은 PH-56. 핫스팟이면 더 낮다 |
| 현재 | 단일 t3.small **5/s에서 에러 0% · p95 0.09 ~ 0.10s**, 10/s에서 포화(성공 3.17/s) | 실측 |

### 3-2. 처리량 산식 — 1대 실측에서 출발

1대가 견딘 처리량(5/s, 에러 0%)에서 출발한다.

**필요 WAS 대수 = 목표 TPS ÷ 5** (선형으로 늘어난다는 가정이라 실제로 필요한 대수의 하한이다)

| 목표 | 필요 WAS 대수 |
|---|---:|
| 10 TPS | 2대 (이번 사양) |
| 20 TPS | 4대 |
| 300 TPS | **60대** |

CPU 사용량으로 거꾸로 계산하지 않는다. harness §3-3의 "10/s × BCrypt 4회 = 초당 40회" 역산은 도착률(10/s)을 처리량으로 썼고 — 같은 회차의 실제 이체 도달은 5.7/s, 성공은 3.17/s다 — 측정 구간에는 로그인이 없어 BCrypt는 반복당 3회다(`perf/k6/load.js`의 `setup()`). 그 값으로는 이체 1건당 CPU를 한 숫자로 정할 수 없다(#627 리뷰).

harness §1-1의 "단계 2 — WAS 2대 20 TPS"는 풀 20(#555)으로 1대가 10 TPS가 된다는 전제인데, 같은 문서 §3-3이 CPU 포화를 근거로 그 전망을 낮췄다. #531 재측정에서 1대 숫자가 바뀌면 이 표의 5를 갈아 끼운다.

PH-56 완료 기준은 1대 → 2대 증가율 비교라, 사양(t3.small × 2)은 이 숫자와 무관하게 그대로다.

### 3-3. 사양을 올려도 못 넘는 상한

- **`transaction_sequence` 전역 1행 `FOR UPDATE`** — 모든 웹 이체가 이 행 하나에 줄 선다(harness §3-3 ②). 상한 = 1 ÷ 락 보유 시간이다. 예를 들어 20ms 쥐면 인스턴스와 무관하게 50 TPS가 한계다(예시, 실측 아님).
- **DB CPU는 측정한 적이 없다.** WAS CPU가 먼저 막혀 DB까지 부하가 가지 않았다(harness §1-2 #4).
- 세션이 RDS로 옮겨가(ADR-0007) 요청마다 세션 조회 · 갱신이 붙는다. 영향은 PH-101-②(#593)가 잰다.

## 4. 인스턴스 타입

### 4-1. WAS — t3.small × 2

| 항목 | 값 |
|---|---|
| 사양 | 2 vCPU · 2GiB, 버스트형(vCPU당 기준 20%) |
| 메모리 | 부하 중 521MB / 1.86GB, 27%(실측) |
| CPU 크레딧 | **unlimited로 명시한다.** t3는 기본이 unlimited라 크레딧이 바닥나도 CPU를 묶지 않고 초과분을 과금한다. standard 모드면 부하 중 CPU가 기준(20%)으로 묶여 PH-56이 사양이 아니라 크레딧 소진을 재게 된다. PH-51 시작 템플릿에 `credit_specification { cpu_credits = "unlimited" }`를 적어 기본값에 맡기지 않는다. 초과 과금은 3분 회차 위주라 작다 |
| 로그 디스크 | 롤링 상한 1GB(`logback-spring.xml` `totalSizeCap`) |

### 4-2. RDS — db.t3.small Multi-AZ

| 항목 | 현재 (db.t4g.micro, 1GiB — 10/15 ~ 10/16 콘솔 확인) | 계획 (db.t3.small, 2GiB) |
|---|---|---|
| 파라미터 그룹 | 사용자 지정 `rds-parameter-group`(패밀리 `mysql8.4`) | PH-70에서 새로 만든다(P2) |
| `max_connections` | 공식 `{DBInstanceClassMemory/12582880}` → 60(실측) | 같은 공식 → 약 140(추정) |
| 필요 커넥션 (풀 × 대수 + 그 밖의 접속 15) | 서버 1대: 풀 10(현재) 25 · 풀 20(#555 머지 전제) 35 — 60 안 | 서버 2대: 풀 20이어도 55, 3대도 75 — 약 140 안 |
| 버퍼 풀 | **미지정 → MySQL 기본값 128MB**(실측). AWS 공식(메모리 × 3/4)을 따르지 않는다 | **`{DBInstanceClassMemory*3/4}`로 명시한다**(약 1.3GB). 새 그룹이 이 값을 어떻게 갖고 시작하는지는 확인하지 않았다 — 지금 그룹처럼 비어 있으면 2GiB여도 128MB라, 기본값에 맡기지 않는다 |
| 겪은 병목 | 적재 중 메모리 부족으로 재시작, 버퍼 풀 27MB로 자동 축소(실측) | — |
| 전수 스캔 | 원장 약 1.95GB가 버퍼 풀의 약 15배 | 원장 약 1.95GB · 분개 약 1.26GB는 1.3GB 버퍼 풀에도 다 안 들어간다 → 대사 · 시산표는 여전히 디스크 I/O를 탄다(#556 베이스라인에서 드러날 지점) |

버퍼 풀을 명시하는 것은 "여유를 적게" 원칙과 부딪히지 않는다. 사양을 키우는 게 아니라 이미 산 메모리를 캐시로 쓰게 하는 것이고, 병목은 여전히 인스턴스 크기(2GiB)에서 드러난다. **현재 운영 RDS는 바꾸지 않는다** — 10/10 적재 때 메모리 부족으로 재시작한 1GiB 인스턴스이고, #556 베이스라인 · PH-101-② 측정이 이 RDS에서 돌아 중간에 설정이 바뀌면 비교가 깨진다.

서버를 여러 대 붙이는 건 새 계정의 3-Tier(db.t3.small)뿐이다. 지금 운영 RDS에는 서버가 1대라 harness §1-2의 "WAS 3대부터 막힘"(#3, 풀 20 × 3대 + 15 = 75 > 60)은 일어나지 않고, 새 RDS에서는 `max_connections`가 약 140이라 풀 20 · 3대여도 들어간다. #555 본문의 "서버가 2대가 되면 다시 계산한다"도 같은 이유로 다시 계산할 일이 없다.

#555 본문과 harness §1-2 #3은 "기본 파라미터 그룹을 써서 `max_connections`를 바꾸려면 새 그룹을 붙이고 재부팅해야 한다"고 적었다. 지금 운영 RDS에는 이미 사용자 지정 그룹이 붙어 있고 `max_connections`는 동적 파라미터라, 그룹 값만 바꾸면 재부팅 없이 반영된다(10/16 콘솔 확인). 결론(DB 설정은 안 바꾼다)에는 영향이 없다.

### 4-3. 온프레미스 VM

| 항목 | 크기(추정) |
|---|---:|
| MySQL 레플리카 | 5 ~ 6GB |
| 릴레이 로그 | 약 1GB |
| **정보계 마트** — 계좌 18만 × 약 45영업일 × 행당 약 350B | **약 3GB** |
| MySQL 인스턴스 2개 시스템 영역 | 약 1GB |
| Docker 이미지 (MySQL · 앱 2 · Nginx · Prometheus · Grafana) | 약 3GB |
| Prometheus · 로그 | 1 ~ 2GB |
| **합계** | **약 15GB → 여유를 넣어 20GB 이상** |

**테스트 VM(10/15 확인)은 디스크 30GB 중 8.2GB만 LVM에 할당돼 있다.** `/`는 8.1G에 여유 2.8G지만, 파티션되지 않은 공간이 약 20GB 남아 있다(`lsblk`: `sda` 30G, `sda2` 1.8G + `sda3` 8.2G · `vgs` VFree 0).

```bash
sudo growpart /dev/sda 3
sudo pvresize /dev/sda3
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
```

늘리면 `/`가 약 28GB, 여유가 약 22GB가 되어 20GB 조건을 넘긴다. 증설 요청은 필요 없다. 단 이 VM은 테스트용이다 — 최종 VM을 받으면 같은 명령(`df -h` · `lsblk` · `vgs` · `docker system df`)으로 구조를 다시 확인하고, 공용이라 파티션 변경 전에 강사님께 알린다.

- 마트가 크다. 잔액 행을 영업일마다 계좌 전부 넣는 구조(PH-75 §2)라 영업일 하나에 약 63MB씩 는다.
- CPU 1코어에서 레플리카 반영 · ETL · Prometheus가 같이 돈다. 강사님이 CPU는 늘려 줄 수 있다고 했다.

## 5. 일부러 남기는 병목

1. **WAS CPU 포화** (BCrypt) → PH-56: 2대로 늘려도 10 TPS(선형 상한)에 못 미치는 곡선
2. **버퍼 풀보다 큰 전수 스캔** → #556 COB 베이스라인, PH-45 병렬화 전후
3. **`transaction_sequence` 직렬화** → P4 LOCK-TUNE (하드웨어로 못 푸는 병목)
