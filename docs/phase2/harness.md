# 부하 harness · 성능 리포트 양식 (PH-30 ④)

> 소유 **P1**(`YounaJ00`) · 이슈 `#385`(부하)·`#384`(정합성) · 기획 [D-03](README.md#d-03--918--p1p4-합의)
> **모든 트랙의 성능 리포트가 이 양식을 쓴다**([tasks.md PH-30](tasks.md) ④).
> 수치를 싣기 전 §2 지표 정의를 먼저 본다. 측정 결과는 [`harness_results.md`](harness_results.md).

## 1. 무엇을 재는 도구인가

k6 로 이체 API 를 실제 HTTP 로 때려 **처리량(TPS) · 지연(p95·p99) · 동시성 정합성**을 남긴다.
S1 에 「개선 전」을 재고 S4 에 **같은 스크립트 · 같은 수준 · 같은 환경**으로 다시 재서 개선폭을 증명한다.

**k6 로 확정한 이유** — 이체가 4요청 체인(§5)이라 앞 응답에서 값을 꺼내 다음 요청에 넣어야 해
`wrk`·`ab` 는 쓸 수 없고, 시나리오를 코드로 저장소에 두어야 누구나 재실행할 수 있다.

**서비스 레벨 동시성 테스트는 이미 있다** — `TransferExecutionServiceConcurrencyTest`(원장 복식부기,
60건/16스레드) · `TransferLimitReserveConcurrencyTest`(한도 적립, 30스레드) ·
`AccountLockDeadlockAvoidanceTest`(데드락 회피). 이 harness 는 그것을 **HTTP 레벨로 올리고
성능 수치를 붙이는** 일이다.

## 2. 지표 정의 — 먼저 읽을 것

### 2-1. 공식 TPS·지연은 **이체 호출 구간만** 잰다

이체 1건에 HTTP 요청이 4개 필요하지만(§5), **공식 수치는 `POST /transfers` 구간만** 집계한다.
전체 플로우 합계는 참고로 병기한다.

**이유** — 이 양식으로 판정하는 대상이 **P4 LOCK-TUNE 전/후 · P4 HOOK-MERGE · P3 PH-24 훅 전/후**인데,
전부 이체 실행 경로만 고치고 토큰 발급 경로는 건드리지 않는다. 합산하면 개선이 희석된다.

| 잣대 | 개선 전 | 이체를 50 → 25ms 로 개선 후 | 보이는 개선 |
|---|---|---|---|
| 합산 (4요청, 토큰 150ms 가정) | 200ms | 175ms | 12.5% |
| **이체만** | 50ms | 25ms | **50%** |

토큰 발급 경로는 OTP(P6)·계좌비밀번호(P2) 도메인이라 2차 중 변경될 수 있다는 것도 이유다.

**지연뿐 아니라 처리량에도 적용된다.** `iterations/s` 를 이체 처리량으로 옮겨 적으면 안 된다 —
앞 단계가 실패해 이체를 호출조차 못 한 반복도 완료로 세기 때문이다.

| 쓸 것 | 쓰지 말 것 |
|---|---|
| `transfer_duration` 분위수 · **`/transfers` 호출 수 ÷ 측정 시간** · 이체 도달률 | `iterations/s` 를 「이체 TPS」로 적기 |

**리포트에 옮기기 전에 표 안 산술을 본다.** 체인의 뒤 단계는 앞 단계보다 많을 수 없다 —
이체 처리량 × 4 가 `http_reqs/s` 를 넘으면 지표를 잘못 집은 것이다.

### 2-2. 한도 경로는 이체와 분리해 잰다

`checkAndReserve` 는 이체 안에서 돌아 HTTP 레벨에서 안 보인다. `limit` 에 Micrometer Timer 를 넣어
**p95·p99 를 따로** 기록한다(REQ-NFR-001 · [#532](https://github.com/corebank-tech/corebank-server/issues/532)).

경계: **계측은 각 도메인 소유자**, **수집·표시 기반(Prometheus·Grafana)은 P5 PH-47**.

## 3. 측정 방식 — 부하와 정합성을 나눈다

| 계열 | 스크립트 | 계좌 | 부하 | 보는 것 | 판정 |
|---|---|---|---|---|---|
| **부하** | `load.js` | **분산** | **수준별 고정 도착률** | 최대 안정 처리량 · 변곡점 | **기록** |
| **정합성** | `integrity.js` | **동일 계좌 1개** | 동시 **100건 고정** | 잔액·원장 짝·한도 적립 | **pass/fail** |

**구분 기준은 규모가 아니라 「계좌를 분산하느냐 한 계좌에 몰아넣느냐」다.** 정합성은 락 경합을
**일부러 만들어야** 틀리는 게 드러나고, 부하는 경합을 **없애야** 순수 처리량이 나온다.

두 스크립트 모두 `BASE_URL` 과 부하 파라미터를 인자로 받는다 — P5 PH-56 이 3-Tier ALB DNS 에 재사용한다.

### 3-1. 부하는 **수준을 고정해 따로** 잰다

| executor | 올리는 것 | 한계점을 볼 수 있나 |
|---|---|---|
| `ramping-vus` | 동시 **사용자 수** | ❌ 서버가 느려지면 사용자가 대기에 묶여 **실제 도착률이 안 오른다** |
| `ramping-arrival-rate` | 초당 **iteration 시작 수** | 🔶 범위는 좁히지만 **종료 요약이 전 구간을 합산**해 변곡점이 사라진다 |
| **`constant-arrival-rate`** | 초당 iteration 수 **고정** | ✅ **수준마다 따로 돌려야** 「어디까지·어디서부터」를 말할 수 있다 |

**`rate` 의 단위는 HTTP 요청이 아니라 iteration 이다.** 이체 1건 = iteration 1회 = **HTTP 4콜**(§5).
`RATE=10` 은 초당 10 요청이 아니라 **초당 10 이체 시도 ≈ 40 HTTP 요청**이다.

| 판정 | 기준 |
|---|---|
| **견딤** | 에러율 **< 1%** · 성공률 100% · 이체 p95 **< 1초** |
| **열화** | 에러율 1~10% 또는 p95 1초 초과 |
| **포화** | 에러율 **> 10%** 또는 유실(`dropped_iterations`) 발생 |

**최대 안정 처리량 = 「견딤」을 만족한 가장 높은 수준.** 수준은 한계 추정값의 **아래·위 2~3개**로
잡는다 — 이미 무너진 값만 재면 변곡점이 안 보인다. 램프업은 **범위를 좁히는 데만** 쓴다.

### 3-2. 정합성은 100 에서 pass/fail 로 본다

100 에서 잔액이 틀리면 버그이고 안 틀리면 설계가 맞다 — **규모를 키운다고 답이 달라지는 종류가
아니다.** 서비스 레벨에서 이미 60건/16스레드로 검증 중이라 HTTP 레벨 100 이면 충분히 위다.

`perf/sql/verify_integrity.sql` 로 대조한다. 검증 쿼리는 위 동시성 테스트에서 이식했다.

| 판정 불변식 | 기준 |
|---|---|
| 잔액 오차 | **0** |
| 원장 차변/대변 짝 (이체 1건당 2행, 입금합 = 출금합) | **100% 일치** |
| 한도 적립 합 = 실제 이체액 | **일치** |
| 데드락률 | 기록 — **판정 기준이 아니다** |

**결함 판정 경계** — 데드락 롤백 후 **실패 응답**이 나간 건은 **정상 거절**이다.
**성공 응답이 나갔는데 원장이 안 맞는 것**만 결함으로 센다.
결함이 나오면 소유를 나눈다: 원장 짝은 `transfer`(P4), 한도 적립은 `limit`(P1).

**고부하에서의 정합성**은 부하 테스트 종료 후 같은 SQL 을 한 번 더 돌려 확인한다.
별도 시나리오를 만들지 않는다.

## 4. 리포트 양식 — 전 트랙 공용

**이 네 단계가 다 있어야 리포트다.** 하나라도 빠지면 「숫자는 있는데 그래서 뭐」가 된다.
적용 예는 [`harness_results.md`](harness_results.md).

### 4-1. 목표

**몇 TPS 를 p95 몇 초 안에.** 목표가 숫자로 없으면 **그 사실과 정하는 안**을 쓴다 — 비워 두지 않는다.
목표가 없으면 ②~④를 「달성/미달」로 판정할 수 없다.

**p95 는 부하 수준과 묶어서만 의미가 있다.** 「p95 M초」만 적지 않는다 — 같은 서버에서 p95 가
1/s 0.07초 → 10/s 9.87초로 **141배** 변했다. 반드시 **「N TPS 에서 p95 M초」** 형태로 쓴다.

### 4-2. 측정 조건

```
측정 대상: (사양·구성)   부하 생성: (별도 기기)
데이터 규모: 고객 N · 계좌 N · 원장 N (PH-60 기준)
수준: N1 · N2 · … /s 고정   회차: 수준마다 N회 · 1회 N분
```

### 4-3. 수준별 결과

| 목표 도착률 | 회차 | 이체 접수/s | 이체 성공/s | 도달률 | p95 | p99 | 에러율 | 유실 | 판정 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|
| | | | | | | | | | |

- **이체 도달률** = 이체 호출 수 ÷ iteration 수. 낮으면 병목이 이체 앞단에 있다
- **유실**이 0 이 아니면 **설정 도착률을 달성하지 못한 측정**이다(§3-1)
- **p99 는 `--summary-trend-stats` 를 붙인 회차에서만 나온다**
- 수치를 손으로 옮기지 않는다 — 스크립트 출력을 붙인다

### 4-4. 결론

| 항목 | 쓰는 법 |
|---|---|
| **어디까지 견뎠나** | 「견딤」을 만족한 **가장 높은 수준**의 처리량**과 그 지점의** p95 |
| **어디서부터 이슈인가** | 변곡점과 **증상 3가지**(처리량 하락 · p95 급증 · 에러율). 원인은 증거를 겹쳐서 |
| **어떻게 개선할 것인가** | 순위별 조치 + 소유 트랙. **다음 병목이 어디로 옮겨갈지**도 적는다 |
| **상용 기준 충족 여부** | 「~해서 충족」/「~해서 개선 필요」 + **원인이 코드인지 설정인지** |

### 4-5. 본문에 넣지 않는 것

「처음엔 X 로 적었는데 틀렸다」·미해결 논의·수치 정정 경위는 **개인 보고서로** 옮긴다.
팀 문서에 섞으면 리포트가 아니라 수사 기록이 된다. 판정에 걸리는 단서만 **한 덩이로 압축**해 남긴다.

## 5. 이체 1건의 요청 체인

| 순서 | 요청 | 산출물 | 재사용 |
|---|---|---|---|
| 1 | `POST /auth/login` | 세션 쿠키 | `setup()` 에서 1회 |
| 2 | `POST /accounts/{accountId}/password/verify` | `accountPasswordAuthToken` | **1회용** |
| 3 | `POST /otp/issue` → `POST /otp/verify` | `otpAuthToken` | **1회용** |
| 4 | `POST /transfers` (`Idempotency-Key` 필수) | 이체 | — |

- OTP 는 거래정보에 바인딩된다 — 발급 본문과 이체 본문이 어긋나면 `OTP0102` 로 실패한다.
- `otp.expose-code: true`(1차 Mock OTP 범위) 덕에 `/otp/issue` 응답에서 6자리를 읽는다.
  **이 값이 꺼지면 harness 가 동작하지 않는다.**
- **정합성 시나리오는 2번 토큰을 미리 발급해 측정 구간 밖으로 뺀다.** 계좌비밀번호 실패 횟수가
  `account` **행**에 있어, 비번 검증이 이체가 잠그는 바로 그 행을 건드리기 때문이다.

## 6. 실행법

k6 설치(Debian/Ubuntu). **부하 생성기는 측정 대상과 다른 기기에 둔다.**

```bash
curl -fsSL https://dl.k6.io/key.gpg | sudo gpg --dearmor -o /usr/share/keyrings/k6-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/k6-archive-keyring.gpg] https://dl.k6.io/deb stable main" | sudo tee /etc/apt/sources.list.d/k6.list
sudo apt-get update && sudo apt-get install k6
```

**수준별 측정 — 리포트에 싣는 것은 이쪽이다.** 수준마다 `RATE` 를 고정해 따로 돌리고,
회차마다 요약 JSON 을 남긴다. 수치를 눈으로 옮기지 않으려면 `--summary-export` 가 필수다.

```bash
BASE="https://<측정 대상>/api/v1"
for rate in 1 2 3 5 10; do
  for run in 1 2 3 4; do
    k6 run -e BASE_URL="$BASE" -e RATE=$rate -e DURATION=3m \
      --summary-trend-stats="avg,min,med,p(90),p(95),p(99),max" \
      --summary-export="level${rate}_run${run}.json" perf/k6/load.js
  done
done
```

**전체 실행 전에 짧게 한 번 돌려 확인한다** — 긴 측정을 날리지 않으려면
요약 JSON 에 `transfer_duration`·`transfer_success`·`iterations` 가 들어 있는지 먼저 본다.

```bash
k6 run -e BASE_URL="$BASE" -e RATE=1 -e DURATION=20s --summary-export=check.json perf/k6/load.js
```

나머지 용도.

```bash
k6 run -e BASE_URL=... perf/k6/smoke.js                      # 흐름 확인 (이체 1건 발생)
k6 run -e BASE_URL=... perf/k6/integrity.js                  # 정합성 — 동일 계좌 100건 동시
k6 run -e BASE_URL=... perf/k6/load.js                       # 램프업 (범위 좁히기)
```

| 환경변수 | 기본값 | 쓰임 |
|---|---:|---|
| `BASE_URL` | **없음 (필수)** | 측정 대상 — 아래 주의 |
| **`RATE`** | 없음 | **주면 고정 수준 측정**. 초당 이체 시도 수 |
| `DURATION` | `3m` | 고정 수준 측정의 길이 |
| `START_RATE` · `PEAK_RATE` · `STEP_DURATION` | 5 · 60 · `45s` | 램프업 모드 |
| `SESSION_POOL` | 20 | 미리 만들 세션 수 |
| `CONCURRENCY` | 100 | 정합성 동시 건수 |
| `AMOUNT` | 19876 | 건당 금액 |

**`BASE_URL` 에 기본값을 두지 않는다.** 스크립트는 실제로 이체를 실행하므로, 기본값이 있으면
명령을 복사한 사람이 의도 없이 그 서버의 잔액·원장을 바꾼다. `https://api.corebank.cloud/api/v1` 은
[`swagger_ui_guide.md`](../swagger_ui_guide.md) §1 이 **배포 서버**로 정의한 주소다.

**금액이 1,000 으로 안 나눠떨어지는 이유** — PH-60 시드 이체가 전부 1,000원 단위라
(`Phase2MinimumSeedService.transferAmount`), 1,000 배수를 피하면 원장에서 harness 가 만든 건만 골라낼 수 있다.

### 6-1. 스크립트를 고칠 때 알아야 할 것

k6 로 옮기며 네 번 막혔다. 같은 자리를 다시 밟지 않도록 적어 둔다.

| 제약 | 내용 |
|---|---|
| `Idempotency-Key` | 이체는 **UUID v4 만** 받는다(`CMN0001`). 계좌비밀번호 검증은 형식을 안 봐서 이체에서야 드러난다 |
| VU 재사용 없음 | arrival-rate 는 반복마다 풀에서 빈 VU 를 아무거나 집는다. VU 지역 캐시는 무용하므로 세션은 `setup()` 에서 만든다 |
| CSRF 쿠키가 둘 | 로그인 응답이 `XSRF-TOKEN` 을 두 번 내린다(만료용 빈 값 + 새 값). **마지막 비어 있지 않은 값**을 쓴다 |
| 쿠키 저장소 | jar 하나를 재사용하면 여러 고객 세션이 섞여 `CMN0101`·`CMN0102` 가 번갈아 난다. **요청마다 새 jar** |
| 세션 10분 | 로그인 응답 `sessionExpiresAt` 이 10분 뒤다. 그보다 긴 측정은 재로그인이 필요하다 |

`#384` 본문도 「100/500/1000 스레드」다. 조정한 내용이다.

| 항목 | tasks.md 원문 | 조정 | 이유 |
|---|---|---|---|
| 시나리오 수 | 3종 | **2계열** | 「핫스팟(동일계좌 100)」과 「동일계좌 100」이 같은 시나리오였다 |
| 동일계좌 구간 | 100/500/1000 | **100 고정** | 정합성은 pass/fail 이라 규모를 키워도 답이 안 달라진다 |
| 부하 방식 | (명시 없음) | **수준별 고정 도착률** | 램프업 1회는 전 구간이 합산돼 「어디까지·어디서부터」를 못 말한다(§3-1) |
