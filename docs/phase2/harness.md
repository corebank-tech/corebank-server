# 부하 harness · 성능 리포트 양식 (PH-30 ④)

> 소유 **P1**(`YounaJ00`) · 이슈 `#385`(부하)·`#384`(정합성) · 기획 [D-03](README.md#d-03--918--p1p4-합의)
> **모든 트랙의 성능 리포트가 이 양식을 쓴다**([tasks.md PH-30](tasks.md) ④). 수치를 싣기 전 §2 지표 정의를 먼저 본다.

## 1. 무엇을 재는 도구인가

k6 로 이체 API 를 실제 HTTP 로 때려 **처리량(TPS) · 지연(p95·p99) · 동시성 정합성**을 남긴다.
S1 에 「개선 전」을 재고 S4 에 **같은 스크립트 · 같은 구간 · 같은 환경**으로 다시 재서 개선폭을 증명한다.

도구는 **k6** 로 확정했다. 이체가 4요청 체인(§5)이라 앞 응답에서 값을 꺼내 다음 요청에 넣어야 하므로 `wrk`·`ab` 는 쓸 수 없고, 시나리오를 코드로 저장소에 두어 누구나 재실행할 수 있어야 하기 때문이다.

**서비스 레벨 동시성 테스트는 이미 있다** — `TransferExecutionServiceConcurrencyTest`(원장 복식부기 정합, 60건/16스레드) · `TransferLimitReserveConcurrencyTest`(한도 적립, 30스레드) · `AccountLockDeadlockAvoidanceTest`(데드락 회피). 이 harness 는 그것을 **HTTP 레벨로 올리고 성능 수치를 붙이는** 일이다.

## 2. 지표 정의 — 먼저 읽을 것

### 2-1. 공식 TPS·지연은 **이체 호출 구간만** 잰다

이체 1건에는 HTTP 요청이 4개 필요하지만(§5), **공식 수치는 `POST /transfers` 구간만** 집계한다. 전체 플로우 합계는 참고 칸에 같이 적는다.

**이유** — 이 양식으로 판정하는 대상이 **P4 LOCK-TUNE 전/후 · P4 HOOK-MERGE 저하율 · P3 PH-24 훅 전/후**인데, 이들은 전부 이체 실행 경로만 고치고 토큰 발급 경로는 건드리지 않는다. 합산으로 재면 개선이 희석된다.

| 잣대 | 개선 전 | 이체를 50 → 25ms 로 개선 후 | 보이는 개선 |
|---|---|---|---|
| 합산 (4요청, 토큰 150ms 가정) | 200ms | 175ms | 12.5% |
| **이체만** | 50ms | 25ms | **50%** |

토큰 발급 경로는 OTP(P6) · 계좌비밀번호(P2) 도메인이라 2차 중 변경될 수 있다는 것도 이유다. 남의 도메인 변경이 이체 수치를 흔들면 S1 ↔ S4 비교가 무너진다.

**참고 칸을 버리지 않는 이유**: 고객 체감은 4요청 합계이고, **P5 PH-57 용량 산정**은 실제로 4요청이 다 일어나므로 이 수치를 써야 맞다. k6 가 자동 집계하므로 추가 비용은 없다.

### 2-2. 한도 경로는 이체와 분리해 잰다

`checkAndReserve`(한도 검사·적립)는 이체 안에서 도므로 HTTP 레벨에서 보이지 않는다. `limit` 에 Micrometer Timer 를 넣어 **p95·p99 를 따로** 기록한다(REQ-NFR-001, `#385`).

경계: **계측(어디를 잴지 코드에 심는 것)은 각 도메인 소유자**, **수집·표시 기반(Prometheus·Grafana)은 P5 PH-47**.

## 3. 테스트 2계열 — 부하와 정합성을 나눈다

| 계열 | 스크립트 | 계좌 | 부하 형태 | 보는 것 | 판정 |
|---|---|---|---|---|---|
| **정합성** | `perf/k6/integrity.js` | **동일 계좌 1개** | 동시 **100건 고정** | 잔액 오차 · 원장 짝 · 한도 적립 · 데드락 | **pass/fail** (0이어야 함) |
| **부하** | `perf/k6/load.js` | **분산** | **초당 요청 수를 단계적으로 상향** | TPS 한계점 · 그 지점의 p95·p99 | **기록** (베이스라인) |

**구분 기준은 규모가 아니라 「계좌를 분산하느냐 한 계좌에 몰아넣느냐」다.** 정합성은 락 경합을 **일부러 만들어야** 틀리는 게 드러나고, 부하는 경합을 **없애야** 순수 처리량이 나온다. 같은 1000 이라도 분산이면 부하, 한 계좌면 정합성이다.

두 스크립트 모두 **`BASE_URL` 과 부하 파라미터를 인자로** 받는다 — P5 PH-56(WAS 스케일아웃 실증)이 같은 스크립트를 3-Tier ALB DNS 에 재사용한다.

### 3-1. 부하는 고정 VU 가 아니라 **도착률**을 올린다

k6 executor 선택이 결과를 바꾼다.

| executor | 올리는 것 | 한계점을 볼 수 있나 |
|---|---|---|
| `ramping-vus` | 동시 **사용자 수** | ❌ 서버가 느려지면 사용자가 대기에 묶여 **실제 TPS 가 안 올라간다** |
| **`ramping-arrival-rate`** | **초당 요청 수** | ✅ 서버가 느려도 계속 쏘므로 한계가 드러난다 |

**`ramping-arrival-rate` 를 쓴다.** 고정된 몇 개 지점을 재면 「이 서버가 초당 몇 건까지 버티는가」에 답할 수 없다.

**한계점 정의** — 도착률을 올려도 **TPS 가 더 오르지 않고 p99 만 치솟기 시작하는 구간.** 「이 서버는 초당 N건까지 버틴다」가 여기서 나온다. 리포트에는 한계점 직전 구간의 수치를 베이스라인으로 싣는다.

### 3-2. 정합성은 100 에서 본다

정합성은 **「틀리는가」의 pass/fail** 이다. 100 에서 잔액이 틀리면 버그이고, 안 틀리면 설계가 맞다 — 규모를 키운다고 답이 달라지는 종류가 아니다. 이미 서비스 레벨에서 60건/16스레드로 검증 중이라 HTTP 레벨 100 이면 충분히 위다.

**고부하에서의 정합성**은 부하 테스트 종료 후 `verify_integrity.sql` 을 **한 번 더 돌려** 확인한다. 별도 시나리오를 만들지 않는다.

## 4. 정합성 판정 (`#384`)

`perf/sql/verify_integrity.sql` 로 대조한다. 검증 쿼리는 기존 `TransferExecutionServiceConcurrencyTest`·`TransferLimitReserveConcurrencyTest` 의 것을 이식한다.

| 판정 불변식 | 기준 |
|---|---|
| 잔액 오차 | **0** |
| 원장 차변/대변 짝 (이체 1건당 2행, 입금합 = 출금합) | **100% 일치** |
| 한도 적립 합 = 실제 이체액 | **일치** |

**결함 판정 경계** — 데드락 롤백 후 **실패 응답**이 나간 건은 **정상 거절**이다. **성공 응답이 나갔는데 원장이 안 맞는 것**만 결함으로 센다.

결함이 나오면 소유를 나눈다: 원장 짝은 `transfer`(P4), 한도 적립은 `limit`(P1).

## 5. 이체 1건의 요청 체인

| 순서 | 요청 | 산출물 | 재사용 |
|---|---|---|---|
| 1 | `POST /auth/login` | 세션 쿠키 | VU 당 1회 |
| 2 | `POST /accounts/{accountId}/password/verify` | `accountPasswordAuthToken` | **1회용** |
| 3 | `POST /otp/issue` → `POST /otp/verify` | `otpAuthToken` | **1회용** |
| 4 | `POST /transfers` (`Idempotency-Key` 필수) | 이체 | — |

- OTP 는 거래정보에 바인딩된다 — 발급 본문과 이체 본문이 어긋나면 `OTP0102` 로 실패한다.
- `otp.expose-code: true`(1차 Mock OTP 범위) 덕에 `/otp/issue` 응답에서 6자리 코드를 읽을 수 있다. 이 값이 꺼지면 harness 가 동작하지 않는다.
- **정합성 시나리오는 2번 토큰을 미리 발급해 측정 구간 밖으로 뺀다.** 계좌비밀번호 실패 횟수가 `account` **행**에 있어 비번 검증이 이체가 잠그는 바로 그 행을 건드리기 때문이다. 빼지 않으면 지연 원인이 이체 락인지 비번 검증인지 구분할 수 없다.

## 7. 실행법

k6 설치(Debian/Ubuntu). 부하 생성기는 측정 대상과 다른 기기에 둔다.

```bash
curl -fsSL https://dl.k6.io/key.gpg | sudo gpg --dearmor -o /usr/share/keyrings/k6-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/k6-archive-keyring.gpg] https://dl.k6.io/deb stable main" | sudo tee /etc/apt/sources.list.d/k6.list
sudo apt-get update
sudo apt-get install k6
```

스크립트가 도는지만 확인한다(이체 1건 발생).

```bash
k6 run perf/k6/smoke.js
```

정합성을 본다. 동일 계좌 100건 동시.

```bash
k6 run perf/k6/integrity.js
```

부하를 올려 한계점을 찾는다. 기본은 3분간 초당 5 → 60건이다.

```bash
k6 run perf/k6/load.js
```

| 환경변수 | 기본값 | 쓰임 |
|---|---:|---|
| `BASE_URL` | `https://api.corebank.cloud/api/v1` | 측정 대상 |
| `START_RATE` · `PEAK_RATE` | 5 · 60 | 초당 요청 수 시작·최대 |
| `STEP_DURATION` | `45s` | 단계당 길이(4단계) |
| `SESSION_POOL` | 20 | 미리 만들 세션 수 |
| `CONCURRENCY` | 100 | 정합성 동시 건수 |
| `AMOUNT` | 19876 | 건당 금액 |

금액 기본값이 1,000 으로 나눠떨어지지 않는 이유가 있다. PH-60 시드 이체는 전부 1,000원 단위라(`Phase2MinimumSeedService.transferAmount`), 1,000 배수를 피하면 원장에서 harness 가 만든 건만 골라낼 수 있다.

### 스크립트를 고칠 때 알아야 할 것

k6 로 옮기며 네 번 막혔다. 같은 자리를 다시 밟지 않도록 적어 둔다.

| 제약 | 내용 |
|---|---|
| `Idempotency-Key` | 이체는 **UUID v4 만** 받는다(`CMN0001`). 계좌비밀번호 검증은 형식을 안 봐서 이체에서야 드러난다 |
| VU 재사용 없음 | `ramping-arrival-rate` 는 반복마다 풀에서 빈 VU 를 아무거나 집는다. VU 지역 캐시는 무용하므로 세션은 `setup()` 에서 만든다 |
| CSRF 쿠키가 둘 | 로그인 응답이 `XSRF-TOKEN` 을 두 번 내린다(만료용 빈 값 + 새 값). **마지막 비어 있지 않은 값**을 쓴다 |
| 쿠키 저장소 | k6 는 응답 `Set-Cookie` 를 jar 에 쌓는다. 하나를 재사용하면 여러 고객 세션이 섞여 `CMN0101`·`CMN0102` 가 번갈아 난다. **요청마다 새 jar** |
| 세션 10분 | 로그인 응답 `sessionExpiresAt` 이 10분 뒤다. 그보다 긴 측정은 재로그인이 필요하다 |
