## 프로젝트 소개

### 1. 프로젝트 요약

- 프로젝트명 : CoreBank 2차 — 채널계·계정계·정보계·대외계 통합 뱅킹 시스템
- 주제 영역 : 금융·핀테크 / 기술 분야 : SW·AI
- 한 줄 소개 : 1차에 구축한 인터넷뱅킹(채널계·계정계)에 회계 원장(GL), 정보계, 대외계를 더해 은행 4계 구조를 완성하고, 원장 300만 건 규모에서 정합성과 성능을 측정·개선한다.

### 2. 핵심 가치

- 정합성 검증 : 금액변조·분개누락 같은 회계 결함과 타행 무응답 같은 대외 장애를 주입하고, 탐지율과 자금 정합성을 측정한다.
- 수치 기반 개선 : 10/8까지 베이스라인을 확보하고, 동일 환경에서 평균·p95·p99를 재측정한다.
- AI 권한 제한 : AI는 화면 안내와 문서 검색만 수행한다. 이체 실행과 원장 변경은 사용자가 한다.

### 3. 요구사항 도출

- 오픈소스 코어뱅킹 엔진 Apache Fineract를 분석해 요구사항을 도출했다. 예금 계좌 상태 전이(만기와 해지 분리), 계정과목 체계, 일마감(COB) 구조를 참고했다.
- 1차도 같은 방식으로 요구사항 정의서(v1.7)에 11개 도메인, 요구사항 219건(필수 199건), 화면 47개를 정의해 MVP를 완성했다.

## 추진 배경 및 필요성

### 1. 현황 및 문제 정의

은행 시스템의 장애는 주로 동일 계좌에 요청이 몰릴 때, 데이터가 수백만 건 쌓였을 때, 대외기관이 응답하지 않을 때 발생한다. 교육 과정 프로젝트는 소량 데이터와 정상 흐름에서 끝나는 경우가 많아 이런 상황을 다루기 어렵다. 1차 결과물도 마찬가지였다.

**1차 결과물 점검 — 2026.09.23 코드 기준**

1차는 요구사항 219건을 구현했고 테스트 1,681개, 병합된 PR 211건이 쌓였다. 다만 코어뱅킹으로 보기에는 다음이 빠져 있었다.
- 회계 원장(GL) 부재 : 이체가 거래원장에만 기록되고 전표·분개가 없어, 원장 전체의 대차 일치를 검증할 수 없다.
- 잔액 체계 미분리 : 지급정지 보류액을 차감한 출금가능액이 없어, 이체 가능 여부를 원장잔액으로 판단한다.
- 영업일 부재 : LocalDate.now()를 9곳에서 직접 호출해, 휴일·마감 후 거래를 익영업일 거래일로 처리하지 못한다.
- 타행이체·지연이체 부재 : 1차 요구사항 정의서에서 범위 밖(EX-001·EX-002)으로 제외했다. 이체 상태도 SUCCESS·ERROR뿐이라 처리 불명(TIMEOUT)을 표현할 수 없다.
- 도메인 이벤트 부재 : 알림 테이블은 있지만 이벤트 발행 코드가 0건이다.
- 측정 수단 부재 : 레포에 부하 테스트 도구가 없어 성능·정합성 수치가 없다.

**2차에서 해결할 운영 문제**

- 동시성 : 동일 계좌에 요청이 몰리면 락 경합과 데드락이 발생하고 잔액 정합성이 깨질 수 있다.
- 원자성 : 거래원장과 회계 전표는 하나의 트랜잭션으로 커밋되어야 한다. 알림은 커밋 이후 유실·중복 없이 전달되어야 한다.
- 대외 장애 : 타행 무응답 시 출금 여부를 알 수 없다. 재전송하면 이중 출금이 되고, 성급히 취소하면 원장이 어긋난다.
- 규모 : 데이터가 쌓이면 시산표 집계와 COB가 느려진다. WAS를 늘려도 핫스팟 계좌 요청은 락 때문에 처리량이 늘지 않는다.

**서비스·협업 측면의 문제**

- 이체와 상품 가입이 여러 화면에 걸쳐 있어, 금융 절차에 익숙하지 않은 고객은 메뉴를 찾기 어렵다.
- 팀 규약 문서가 18개로 늘었고, 코딩 에이전트(Claude Code)가 기존 결정과 충돌하는 코드를 생성하는 일이 반복됐다.

### 2. 기존·유사 서비스 분석

- 일반 교육용 웹 프로젝트 : 정상 흐름 CRUD 중심이라 장애·동시성·대용량 데이터를 다루지 않는다. 본 프로젝트는 원장 300만 건과 동일 계좌 동시 요청 최대 1,000건을 의도적으로 재현한다.
- Apache Fineract : 검증된 오픈소스 엔진이지만 코드 규모가 커서 설계 의도를 파악하기 어렵다. 예금 상태를 MATURED(만기)·CLOSED(해지)·PRE_MATURE_CLOSURE(중도해지)로 나누는 방식, 계정과목 5분류(자산·부채·자본·수익·비용), COB 구조를 참고하되, 국내 업무(영업일, 이자소득세 원천징수, 지연이체)에 맞춰 직접 구현한다.
- CoreBank 1차 : 기능은 갖췄지만 원장 검증 수단과 측정 수치가 없다. 2차는 베이스라인부터 기록한다.
- 스크린 리더·화면 보정 확장 프로그램 : 화면 낭독과 표시 보정만 제공하고, 메뉴 탐색은 사용자 몫이다. 서비스 안내 내비게이션은 질의를 받아 대상 화면으로 이동하고 입력 항목을 안내한다.
- 노션·Swagger : 규격이 여러 곳에 흩어져 있어 직접 찾아야 한다. 개발자 협업 RAG는 레포 문서를 검색해 근거 문서와 함께 반환한다.

### 3. 해결 방안 및 차별점

- 모든 트랙에 측정 → 원인 분석 → 개선 → 재측정 절차를 적용한다. 베이스라인은 10/8에 마감하고, 전후 비교는 동일한 단일 EC2에서 한다.
- 성능 지표는 평균과 함께 p95·p99를 기록해 꼬리 지연(tail latency)을 드러낸다.
- 회계 결함 4종(금액변조·분개누락·편측기표·중복기표)과 대외 장애 3종(타임아웃·무응답·중복응답)을 주입해 탐지율과 자금 정합성을 측정한다.
- AI 기능은 원장을 변경하는 API를 호출하지 않는다. AI 서버에 장애가 나도 이체·가입은 영향을 받지 않는다.
- 인프라는 Terraform(IaC)으로 구성해 약 20일만 가동한 뒤 삭제하고, 필요하면 동일 환경을 재구성한다.

## 프로젝트 내용

### 1. 타깃 사용자 정의

- 개인 고객 : 웹에서 계좌 조회, 당행·타행 이체, 예적금 가입·해지를 한다.
- 금융 절차가 익숙하지 않은 고객 : 서비스 안내 내비게이션의 주 대상이다.
- 운영 관리자 : 고객 계정 운영, 시산표·대사 결과 확인, 경영 현황 조회를 한다. 조회 전용 관리자와 변경 권한 관리자로 직무를 분리한다.
- 개발팀 : 개발자 협업 RAG로 설계 문서와 규약을 검색한다.

### 2. User Journey Map

- 타행 이체 : 입력 → 인증 → 전문 송신 → 무응답 → 조회거래로 확정
  무응답 상태에서 고객이 재요청하면 이중 출금이 될 수 있다. 화면은 재시도 버튼을 비활성화하고 "처리 확인 중"으로 안내하며, 서버는 재전송 없이 조회거래로 결과를 확정한다.
- 예금 만기 수령 : 만기 도래 → 만기 안내 → 입금 계좌 선택 → 원리금 지급
  만기일이 지나도 계좌를 자동 해지하지 않는다. 만기(MATURED)와 해지(CLOSED)를 별도 상태로 두고, 고객 요청 시에만 해지한다.
- 관리자 업무 : 관리자 로그인 → 조회 사유 선택 → 고객 계정 처리 → 대사 불일치 확인 → 경영 현황 조회
  개인정보 조회 시마다 사유 코드를 감사로그에 남긴다. 조회 전용 관리자의 변경 요청은 거부된다. 경영 현황 수치에는 모두 기준시점(as-of)을 표기한다.
- 내비게이션을 통한 이체 : 질의 → 화면 이동 → 입력 항목 안내 → 고객이 직접 입력·실행
  계좌번호·비밀번호 입력과 이체 실행은 고객이 직접 한다.

### 3. 시스템 아키텍처

#### 1) 서비스 흐름도 (별첨 그림 1)

- 채널계 : 고객 웹과 관리자 화면. 인증, 인가, 레이트리밋을 담당한다.
- 계정계 : 원장을 변경하는 유일한 계층이다. 자금 이동은 거래원장과 회계 전표에 함께 기록된다.
- 정보계 : 마감된 데이터를 마트로 적재해 통계만 제공한다. 원장은 읽기만 한다.
- 대외계 : 고정길이 전문으로 모의 대외기관과 통신한다. 대외계 장애 시에도 당행 이체는 계속 처리된다.
- AI : 별도 서버(FastAPI)로 분리하고, 원장 변경 API는 호출하지 않는다.

#### 2) 데이터 흐름도 (별첨 그림 2)

- 이체 1건 : 출금가능액 사전검사 → 계좌 락·한도·잔액 검증 → 거래원장·회계 전표·아웃박스 이벤트를 하나의 트랜잭션으로 커밋 → 아웃박스 릴레이(5초 주기 폴링)가 알림 발송
  전표 기표에 실패하면 이체도 롤백된다. 알림 발송 실패는 이체에 영향을 주지 않고 릴레이가 재시도한다.
- 일마감(COB) : 영업일 확인 → 자동·예약이체 → 원장 대사 → 만기 감지 → 휴면 전환 → 정보계 ETL → 영업일 전환
  스텝별 실행 기록을 남기고, 실패 시 실패한 스텝부터 재실행한다.

#### 3) 인프라 아키텍처 (별첨 그림 3)

- 현행 : 단일 EC2(t3.small)에 애플리케이션과 Redis를 Docker로 구동하고 RDS MySQL에 연결한다.
- 2차 : 2AZ VPC, 서브넷 6개(public·app·data × 2). ALB – WAS ASG(1~2대) – RDS MySQL Multi-AZ로 구성하고, Redis와 AI 서버는 별도 util 노드에 둔다. 앞단에 WAF를 두고, 서버 접근은 SSH 없이 SSM Session Manager로만 한다.
- 10/19~23 리허설, 10/26 구축, 10/27 전환(컷오버). 컷오버 실패 시 기존 EC2로 운영을 유지한다.

### 4. 주요 기능 (1차 세부 요구사항은 요구사항 정의서 v1.7, 2차 태스크와 규약은 레포 docs 참조)

**채널계**

- 관리자 인증·인가 : 관리자 전용 로그인(세션 30분), 권한 5종(GL_READ·GL_WRITE·CUSTOMER_READ·CUSTOMER_WRITE·AUDIT_READ), 권한 부여·회수 감사
- 고객 계정 운영 : 고객 검색(마스킹), 잠금 해제, 비밀번호 초기화, 계정 상태 변경
- 감사 : 감사로그 5W(Who·When·Where·What·Why) 표준화. 개인정보 조회 시 사유 코드(X-Access-Reason) 4종 중 하나를 필수로 받는다.
- 접근 보안 : 로그인·OTP·이체 레이트리밋, 계정 열거(account enumeration) 방지. MFA·Step-up은 정책 매트릭스만 정의한다.
- 지연이체 : 기준 금액 이상 이체를 지정 시간 후 입금하고, 입금 전까지 취소를 허용한다.
- 알림 : 즉시이체·예약이체·자동이체·상품 가입 4종. 아웃박스 At-Least-Once 발행과 멱등 소비로 유실·중복을 막는다.

**계정계**

- 회계 원장(GL) : 계정과목 15개 내외, 전표·분개 기표, 대차 불일치 전표 거부, 시산표 조회
- 예적금 생명주기 : 상태 5종 × 이벤트 12종 전이 매트릭스, 가입·이자·만기·중도해지·휴면
- 이자 : 적수(일말잔액 합계) 기준, 실일수/365, 원 단위 절사, 이자소득세 15.4% 원천징수
- 잔액 체계 분리 : 원장잔액과 출금가능액(원장잔액 − 지급정지 보류액)을 분리하고, 이체는 출금가능액으로 판정한다.
- 원장 대사 : 매일 원장 합계와 계좌 잔액을 대조해 불일치 목록을 남긴다. 자동 정정은 하지 않는다.
- 일마감(COB) : 영업일 관리, 7단계 스텝 체인, 실패 스텝 재실행, 청크·병렬 처리

**정보계**

- 마트 2종(일별 계정잔액, 상품별 가입·해지), ETL, 조회 API
- 모든 응답에 기준시점(asOf)을 포함하고, 개인정보는 적재하지 않는다.

**대외계**

- 모의 대외기관 : 별도 프로세스, 고정길이 전문, 지연·무응답·중복응답 주입 스위치
- 타행 이체 : 무응답 시 TIMEOUT(처리 불명)으로 두고 조회거래로 확정한다. 자동 재시도는 금지한다. 미결제타점권 계정으로 기표한다.
- 정정 체인 : 거래를 삭제하지 않는다. 원거래 INVALID 표기 → 취소정정 거래 → 정상 거래 순으로 기록한다(DELETE 0건).

**AI**

- 서비스 안내 내비게이션 : 질의를 받아 대상 화면으로 이동하고 입력 항목을 안내한다. 실행 가능한 동작은 허용 목록(allowlist)으로 제한해 이체 실행 버튼은 누르지 않고, 계좌번호·잔액 등 고객 데이터는 저장하지 않는다.
- 개발자 협업 RAG : 레포 규약 문서 18개(537개 청크)를 색인하고, Claude Code가 MCP 도구로 검색해 근거 문서와 함께 답한다. 문서 변경 PR이 병합되면 변경 파일만 재색인한다. 9월에 1단계를 배포했다.

**운영·인프라**

- 3-Tier 전환 : 2AZ 네트워크, WAS ASG(1~2대), RDS 스냅샷 복원 이관
- 보안 : WAF, IAM 역할 분리, Secrets Manager, 감사로그 WORM 저장(S3 Object Lock), 개인정보 컬럼 암호화, 로그 마스킹
- 운영 : Prometheus·Grafana 대시보드와 알람, 무중단 롤링 배포, DR Tier별 복구 훈련

**2차 범위 제외**

결산·역분개, 타행 미결제 정산, 감사로그 조회 화면, Read Replica, Spring Batch·MQ 도입은 범위에서 제외했다. 6인 × 30영업일 안에서 완료할 수 있도록 범위를 조정한 결과다.

### 5. 적용 기술

- 헥사고날 아키텍처 + ArchUnit : 도메인 로직을 영속성·웹 어댑터와 분리해 6인 병렬 개발 시 충돌을 줄인다. 레이어 의존 규칙 위반은 ArchUnit 테스트가 차단한다.
- Flyway : 스키마 변경은 마이그레이션 파일로만 한다. 운영 환경은 기동 시 ddl-auto: validate로 스키마를 검증한다.
- 이체 파이프라인 확장점(seam) : 출금가능액 사전검사(TransferPreCheck), 회계 기표(LedgerPostingHook), 거래일 대입을 훅으로 연결한다. execute()는 담당자 1명만 수정한다.
- GL 기표 동기 포트 : 전표를 이벤트로 비동기 기표하면 원장과 다른 커밋에 들어가 분개누락이 정상 상태가 된다. 그래서 같은 트랜잭션에서 동기로 기표한다.
- Transactional Outbox : BEFORE_COMMIT 리스너가 이벤트를 거래와 같은 트랜잭션에 적재하고, 릴레이가 이후 발송한다. 커밋 직후 프로세스가 종료돼도 이벤트가 유실되지 않는다.
- Resilience4j : 타행 응답 지연 시 타임아웃·서킷브레이커로 차단해 당행 이체로 장애가 전파되지 않게 한다.
- Spring Session Redis : 세션을 외부화해 WAS 2대에서도 로그인 상태를 유지한다. ALB 스티키 세션은 쓰지 않는다.
- Terraform : 인프라를 코드로 관리해 단기 가동·삭제 후에도 동일 환경을 재구성한다.
- k6 : 분산·핫스팟(동일 계좌 동시 100·500·1,000건) 시나리오로 TPS와 p95·p99를 측정한다.
- Prometheus·Grafana : 거래·배치·JVM·DB 메트릭을 수집하고, 알람마다 런북을 연결한다.
- FastAPI 분리 : AI 서버 장애가 본 서비스로 전파되지 않게 분리하고, 3초 타임아웃 초과 시 정해진 안내 문구로 대체(degrade)한다.
- Qdrant + MCP : 협업 RAG의 벡터 저장소와 Claude Code 연동 방식이다. 임베딩 모델을 서버에서 직접 구동해 외부 API 비용이 없다.

### 3. 협업 방식 및 Ground Rule

**1차에서 효과를 본 방식 유지**

- 6명이 각자 하나 이상의 도메인을 끝까지 소유한다.
- 매일 아침 스크럼에서 진행 상황과 블로커를 공유한다.
- 도메인 간 이슈는 디스코드에서 먼저 합의한 뒤 개발한다.
- 선행 기능을 기다리지 않는다. 인터페이스와 스텁을 먼저 공개하고 병렬로 개발한다.

**사람과 AI의 코드 리뷰 분담**

- 모든 PR은 AI 리뷰(PR-Agent)를 먼저 거친다.
- 사람 리뷰는 주간 리뷰어와 관련 도메인 담당자가 맡고, 지적 사항은 R1~R5 등급으로 구분한다.
- 병합 승인은 항상 사람이 한다. AI가 작성한 코드도 이해하지 못한 채 반영하지 않는다.

**문서 단일 원본**

규격과 결정 근거는 레포 문서와 ADR에만 남긴다. 사람, 코딩 에이전트, 협업 RAG가 같은 원본을 참조한다.

**2차 추가 규칙**

- 이체 실행 메서드(TransferExecutionService.execute())는 담당자 1명만 수정하고, 다른 기능은 확장점에 구현체만 등록한다. 병합 순서도 담당자가 정한다.
- 공개된 API 응답은 Expand-Contract 원칙에 따라 필드 추가만 허용한다.
- 성능 전후 비교는 동일 환경에서만 한다. 컷오버 기간(10/26~27)에는 측정하지 않는다.
- 11/2부터 BE 기능을 동결한다.
- 일정 지연은 야근으로 메우지 않고, 트랙별로 미리 정한 순서에 따라 범위를 축소한다.

## 성과목표 및 기대효과

### 1. 성과목표

베이스라인은 10/8까지 측정한다. "잠정" 목표는 베이스라인 확인 후 확정한다.

**정합성**

- 동시 이체(동일 계좌 100·500·1,000건) : 잔액 오차 0원, 원장 쌍(LedgerPair) 무결성 100%
- 대외 장애 3종(타임아웃·무응답·중복응답) : 자금 정합성 100%(원장 합계 = 잔액 합계 + 미결제)
- 회계 결함 4종(금액변조·분개누락·편측기표·중복기표) : 탐지율 100%
- 예적금 : 상품 12종 이자 계산 오차 0원, 15만 계좌 원리금 전수 대조 오차 0원, 상태 전이 매트릭스 60/60 정의·불법 전이 차단 100%

- 정보계 : 마트 합계 = 원장 합계, 마트 PII 0건, 기준시점 표기 100%

**성능 — 동일 단일 EC2 전후 비교, 원장 300만 건 기준**

- 이체 : TPS·p95·p99 기록, 락 튜닝 후 핫스팟 시나리오 p99 30% 이상 단축(잠정)
- 적수 계산(15만 계좌) : 계좌별 단건 루프를 집계 SQL 1문으로 전환해 10배 이상 단축(잠정)

- COB(15만 계좌) : 순차 → 청크 → 병렬 전환으로 순차 대비 50% 이상 단축(잠정), 실패 시 스텝 단위 재실행
- WAS 스케일아웃(3-Tier, 1대 → 2대) : 분산 시나리오와 핫스팟 시나리오의 처리량 증가율을 비교해, 핫스팟은 스케일아웃 효과가 낮다는 것을 수치로 입증한다.

**보안·운영**

- 무차별 대입 로그인 1만 건 차단율 100%, 오탐률 기록
- 조회 전용 관리자의 변경 API 거부율 100%, 권한 부여·회수와 개인정보 조회의 감사 기록률 100%
- WORM 저장소 삭제·수정 거부율 100%, 로그 민감정보 노출 0건, 마스킹 미적용 응답 필드 0건, 미문서화 API 0건
- DR : Tier1 원장 RTO 15분·RPO 0, Tier2 온라인 거래 RTO 1시간·RPO 5분, Tier3 알림·관리자 RTO 4시간, Tier4 정보계·AI RTO 24시간
- 배포 다운타임 0초(ASG 롤링 교체)

**AI**

- 내비게이션 : 출금 동작 자동 실행 0건, 고객 데이터 저장 0건, 평가 시나리오 목표 화면 도달률 90% 이상(잠정)
- 협업 RAG : 평가 질의 정답 문서 top-5 포함률 90% 이상(잠정), 문서 변경 반영률 100%

### 2. 기대효과

**운영 환경을 가정한 사용자 효과**

- 타행 무응답 상황에서도 이중 출금이 발생하지 않는다.
- 원장 불일치는 다음 영업일 COB의 대사 스텝에서 탐지된다.
- 관리자는 직무가 분리된 권한으로 업무를 수행하고, 개인정보 조회와 권한 변경이 모두 WORM 감사로그로 남는다.
- 금융 절차에 익숙하지 않은 고객도 안내를 받아 직접 거래를 완료할 수 있다.

**참여자 역량 — 금융 도메인 개발자로서의 경험**

- 거래원장 → 전표·분개 → 시산표 → 대사로 이어지는 원장 구조를 구현하고, 결함 주입으로 검증한다.
- 락 튜닝, 쿼리 전환, 배치 병렬화의 전후 차이를 p99까지 수치로 설명할 수 있게 된다.
- 대외 전문 무응답을 재시도 없이 조회거래와 정정 체인으로 처리하는 방식을 설계·검증한다.
- IaC로 인프라를 구축하고 컷오버, 복구, 삭제까지 직접 수행한다.
- AI에 위임할 작업과 사람이 수행할 작업의 경계를 정하고 지킨다.
트랙별 리포트와 ADR은 각자의 포트폴리오와 면접에서 근거 자료로 쓸 수 있다.

### 3. 활용 분야 및 확장성

- 규모 확장 : 고객 10만·원장 1,000만 건, Read Replica 분리, 대외 장애 6종(부분 실패·순서 역전·지연 추가)
- 기능 확장 : 2차에서 제외한 결산·역분개, 타행 미결제 정산, 권한 관리 화면
- 내비게이션 : 화면 구조만 저장하는 방식이라 다른 금융·공공 사이트로 이식할 수 있다.
- 협업 RAG : 신규 팀원 온보딩에 활용하고, FE 레포 문서까지 색인 범위를 넓힌다.
