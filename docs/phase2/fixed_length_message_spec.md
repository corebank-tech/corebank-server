# 고정길이 전문 규격 (PH-31)

> **정본이다.** 당행과 모의 대외기관이 주고받는 타행 이체 전문은 이 문서를 따른다.
> 직렬화 코드와 모의 서버는 [tasks.md](tasks.md) §PH-33-①, 송신·조회거래 흐름은 §PH-33-②다.
> 용어는 [glossary.md](glossary.md) 9번 처리 불명(TIMEOUT) · 10번 조회거래를 따른다.

---

## 1. 기본 약속

| 항목 | 정한 것 |
|---|---|
| 문자셋 | **EUC-KR 계열.** 구현은 Java `MS949`(CP949)로 한다 — 순수 EUC-KR은 한글 2,350자만 담아 `똠`·`햏` 같은 글자가 `?`로 깨진다. 두 문자셋 모두 한글 1자 = 2바이트, 영문·숫자 1자 = 1바이트로 같다 |
| 길이 단위 | **바이트.** 글자 수로 세지 않는다 |
| 전체 길이 | **모든 전문이 124바이트로 같다.** 요청·응답, 이체·조회거래가 같은 배치를 쓴다 |
| 전문길이 값 | 전문길이 필드(4바이트)를 **뺀** 나머지 바이트 수다. 항상 `0120` |
| 전송 단위 | TCP 한 연결에 요청 1건 · 응답 1건. 받는 쪽은 전문길이 4바이트를 **다 받을 때까지** 읽고, 이어서 그 값(120)만큼 **다 받을 때까지** 읽는다. TCP는 한 번 읽기에 다 오지 않을 수 있다. 다 받으면 연결을 닫고 그 뒤에 오는 바이트는 읽지 않는다 |

**다 받기 전에 연결이 끊기면(EOF) 그 전문은 받지 않은 것으로 본다.** 당행이 응답을 받다 끊기면 응답이 오지 않은 것과 같아 처리 불명(TIMEOUT)이고, `INQ001`로 결과를 확인한다. 상대가 이미 입금했을 수 있으므로 실패로 확정하지 않는다. 모의 서버가 요청을 받다 끊기면 그 요청을 처리하지 않는다.

국내 은행 전문이 EUC-KR 계열을 쓰는 이유는 바이트로 정한 칸에 한글이 항상 2바이트로 들어가 "예금주 20바이트 = 한글 10자"가 성립하기 때문이다. UTF-8은 한글이 3바이트라 영문과 섞이면 칸에 들어가는 글자 수가 들쭉날쭉하다.

## 2. 필드 배치

시작 위치는 0부터 센 바이트 오프셋이다. 타입 `N`은 숫자, `AN`은 문자다.

### 헤더 (55바이트)

| # | 필드 | 타입 | 길이 | 시작 | 값 |
|---|---|---|---|---|---|
| 1 | 전문길이 | N | 4 | 0 | `0120` 고정 |
| 2 | 전문종별 | N | 4 | 4 | `0200` 요청 · `0210` 응답 |
| 3 | 거래코드 | AN | 6 | 8 | `TRF001` 타행이체 · `INQ001` 조회거래 |
| 4 | 전송일시 | N | 14 | 14 | 보내는 쪽 시각 `yyyyMMddHHmmss` |
| 5 | 기관코드 | N | 3 | 28 | **상대 기관(수신 은행) 코드.** 요청·응답 모두 같은 값. 당행 `088`은 담지 않는다 |
| 6 | 일련번호 | AN | 20 | 31 | **원거래의 `transfer.transaction_number`.** 조회거래도 원거래 번호를 그대로 싣는다 |
| 7 | 응답코드 | AN | 4 | 51 | 요청은 공백 4바이트 · 응답은 §3 코드 |

### 본문 (69바이트)

| # | 필드 | 타입 | 길이 | 시작 | 값 |
|---|---|---|---|---|---|
| 8 | 계좌번호 | AN | 16 | 55 | 수취 계좌번호. 숫자만, 하이픈 없이. 은행마다 자릿수가 달라 당행 12자리보다 넉넉히 둔다 |
| 9 | 금액 | N | 13 | 71 | 원 단위 정수 |
| 10 | 예금주 | AN | 20 | 84 | 요청은 공백 · 응답은 상대 기관이 확인한 수취인 이름(한글 10자) |
| 11 | 적요 | AN | 20 | 104 | 받는 분 통장 표시(`recipient_passbook_memo`, 최대 10자 = 20바이트) |

헤더 55 + 본문 69 = **124바이트**, 전문길이 값 = 124 − 4 = **120**.

**일련번호를 원거래 번호로 쓰는 이유:** 무응답 뒤 조회거래로 원거래를 짚어야 하고, 중복응답도 이 번호로 가려낸다. 원거래와 1:1이라 전문용 번호를 따로 채번하지 않는다.

**조회거래(`INQ001`) 요청**은 본문에 원거래와 같은 값을 싣는다. 상대 기관이 계좌·금액까지 맞춰 볼 수 있게 하기 위해서다.

## 3. 응답코드

이 프로젝트가 정한 값이다. 실제 기관 코드표가 아니다.

| 코드 | 뜻 | 이체(`TRF001`) | 조회거래(`INQ001`) |
|---|---|---|---|
| `0000` | 정상 | 입금 완료 | 원거래가 입금 완료돼 있다 |
| `1001` | 수취 계좌 없음 | 미입금 확정 | 원거래가 이 사유로 거절됐다 |
| `1002` | 수취 계좌 거래 불가(해지·정지) | 미입금 확정 | 원거래가 이 사유로 거절됐다 |
| `1003` | 전문 형식 오류 | 미입금 확정 | 조회 전문 자체가 잘못됐다 — 고쳐서 다시 조회한다 |
| `2001` | 중복 거래 — 같은 일련번호를 이미 처리함 | 재처리하지 않음. 결과는 조회거래로 확인 | — |
| `3001` | 원거래 미수신 | — | 상대 기관에 원거래 기록이 없다 = 처리 안 됨. 형식 오류(`1003`)로 거절된 원거래도 기록을 남기지 않으므로 여기에 해당한다 |
| `9999` | 상대 기관 시스템 오류로 처리하지 못함 | 미입금 확정 | 결과 확인 불가 — 다시 조회한다 |

조회거래 응답의 `1001`·`1002`는 **원거래**의 결과이고, `1003`·`9999`는 **조회 전문 자체**의 결과다.

**처리 불명(TIMEOUT)은 응답코드가 아니다.** 응답코드는 상대 기관이 무언가를 판정해 돌려준 값이고, TIMEOUT은 **응답 자체가 오지 않은 상태**다. TIMEOUT이면 자동 재시도하지 않고 `INQ001`로 결과를 확인한다.

## 4. 패딩 규칙

| | 숫자 `N` | 문자 `AN` |
|---|---|---|
| 정렬 | 오른쪽 | 왼쪽 |
| 채움 문자 | 왼쪽에 `0`(0x30) | 오른쪽에 공백(0x20) |
| 빈 값 | 전부 `0` | 전부 공백 |
| 부호·소수점·쉼표 | 쓰지 않는다. 음수 없음 | — |
| 길이 초과 | **거부** — 전문을 만들지 않는다 | 식별자(거래코드·일련번호·계좌번호)는 **거부**. 표시용(예금주·적요)은 **바이트 경계에서 자른다** |
| 받는 쪽 해석 | 정수로 읽는다. 숫자 아닌 바이트가 있으면 `1003` | 오른쪽 공백만 걷어낸다. 왼쪽 공백은 값으로 본다 |

- **한글 1자를 반으로 쪼개지 않는다.** 예금주·적요를 자를 때 마지막 한글이 1바이트만 들어갈 자리면 그 글자를 빼고 남는 1바이트를 공백으로 채운다.
- **`MS949`로 표현할 수 없는 문자(이모지 등)는 거부한다.** `?`로 바꿔 보내지 않는다. 입력 단계(PH-33-②)와 전문 직렬화(PH-33-①) **둘 다** 막는다. 저장된 데이터나 다른 호출 경로는 입력 검증을 거치지 않으므로 직렬화가 마지막 관문이다.
- 전체 길이가 124바이트가 아니거나 전문길이 값이 `0120`이 아니면 `1003`이다.

## 5. 예시

`·`은 공백(0x20)이다. 두 전문 모두 124바이트다.

**요청** — 국민은행(`004`) 계좌로 50,000원, 적요 "홍길동"

```
01200200TRF0012026102310301500420261023WB0000000123····1234567890123···0000000050000····················홍길동··············
```

**응답** — 정상, 예금주 "김민수"

```
01200210TRF0012026102310301600420261023WB000000012300001234567890123···0000000050000김민수··············홍길동··············
```

| 필드 | 요청 | 응답 |
|---|---|---|
| 전문길이 | `0120` | `0120` |
| 전문종별 | `0200` | `0210` |
| 거래코드 | `TRF001` | `TRF001` |
| 전송일시 | `20261023103015` | `20261023103016` |
| 기관코드 | `004` | `004` |
| 일련번호 | `20261023WB0000000123` | `20261023WB0000000123` |
| 응답코드 | `····` | `0000` |
| 계좌번호 | `1234567890123···` | 같음 |
| 금액 | `0000000050000` | 같음 |
| 예금주 | 공백 20 | `김민수` 6바이트 + 공백 14 |
| 적요 | `홍길동` 6바이트 + 공백 14 | 같음 |

## 6. 넘기는 것과 범위 밖

**PH-33-①에 넘기는 것**
- 이 배치 그대로 직렬화·역직렬화 코드(`adapter/out/external`)와 단위 테스트를 만든다. 패딩, 한글 경계 자르기, 길이 초과 거부, 124바이트 검증을 테스트한다
- 인코딩은 `String.getBytes(Charset)`를 쓰지 않는다. 이 메서드는 표현할 수 없는 문자를 `?`로 조용히 바꾼다. `CharsetEncoder`에 `CodingErrorAction.REPORT`를 걸어 직렬화를 실패시키고, 이모지가 `?`로 바뀌지 않고 거부되는지 단위 테스트로 고정한다
- 수신은 §1대로 4바이트와 120바이트를 각각 다 받을 때까지 읽는다. 나눠 도착하는 경우와 중간에 끊기는 경우를 테스트한다
- 모의 서버는 응답코드 §3을 돌려주고, 응답 지연 · 무응답 · 중복응답 스위치를 둔다. **중복응답은 같은 연결에 같은 응답을 두 번 쓴다.** 받는 쪽이 첫 응답 뒤 연결을 닫아 두 번째 쓰기가 실패해도 무시한다

**PH-33-②에 넘기는 것**
- 응답 대기 시간(TIMEOUT 기준)은 Resilience4j 설정에서 정한다
- 같은 원거래의 결과는 **한 번만 반영**한다. 같은 연결의 중복응답은 §1대로 첫 응답만 읽어 걸러진다. 조회거래를 여러 번 보내 같은 일련번호의 결과가 다시 오면 이미 확정된 상태를 바꾸지 않는다(PH-80 상태 역행 금지)
- 은행코드 시드 5개를 정한다. 예시의 `004`는 설명용이다
- `transfer`에 타행 거래를 담도록 Flyway 증분 하나로 바꾼다. 지금 구조로는 타행 거래를 저장할 수 없다
    - `deposit_account_number`를 `CHAR(12)` → `VARCHAR(16)`으로 넓힌다. 전문 계좌번호 칸(16바이트)과 맞춘다
    - `deposit_account_id`의 NOT NULL을 푼다. 타행 수취 계좌는 당행 `account`에 없다
    - 입금 은행코드 컬럼을 추가한다
    - `schema_reference.md`·`corebank_erd.md`를 함께 고치고(AGENTS.md §3-6), 13자리·16자리 계좌번호의 저장과 전문 왕복을 테스트한다
- `AccountNumberPolicy`의 12자리 패턴은 당행 전용으로 두고, 타행 계좌번호는 따로 검증한다

**범위 밖**
- 수취인 사전 조회 전문 — 예금주는 이체 응답으로만 받는다
- 타행 계좌의 즐겨찾기·자동이체·예약이체 등록 — `favorite_account`·`auto_transfer`·`scheduled_transfer`의 계좌번호 `CHAR(12)`는 그대로 둔다
- 당행이 수취 측이 되는 타행 입금 — 그때는 당행 `customer.user_name`(최대 50자)을 예금주 칸에 담아야 하므로 20바이트를 다시 정한다
- 타행 수수료(`FEE = 0L` 유지), 미결제 정산(PH-35)
- 암호화·MAC 같은 전문 보안 필드
