# PH-49c JDBC 세션 적용 후 운영 성능 재측정 결과 (C)

측정 계획과 구현 검증은 [ph49c_jdbc_session.md](ph49c_jdbc_session.md#운영-성능-재측정-계획)를 따른다. 이 문서는 2026-10-26 KST 기준 C 측정의 회차별 결과와 4회 종합 판정을 기록한다.

## 측정 조건

기존 ALB → 단일 EC2 → 기존 RDS에서 `provider=jdbc`, Hikari 메인 풀 10개로 측정했다. 사용한 운영 이미지 SHA는 `176fe574b6b5d2a1008ce9ce9359753b4d658cdb`다. 부하 스크립트는 `perf/k6/load.js`이며, 목표 도착률 1·2·3·5·10/s를 각 3분 적용했다. 측정 당시 PH-30 성능 개선은 아직 운영에 적용되지 않았다. 아래 시각은 KST이고, 검사 구간은 시작 시각 이상·종료 시각 미만이다.

[PH-30 측정 기준](harness_results.md#2-측정-결과--2026-10-05-수준별)의 견딤은 **성공률 100%·HTTP 오류율 1% 미만·이체 p95 1초 미만**, 포화는 **HTTP 오류율 10% 초과 또는 유실 발생**이다. 목표 도착률은 이체 완료 처리량이 아니므로 두 값을 혼동하지 않는다. B′는 같은 운영 ALB·단일 `t3.small` EC2·RDS `db.t4g.micro`·Hikari 풀 10개에서 `SESSION_POOL=MAX_VUS=200`으로 측정했다([PH-101-② 측정 조건](ph101_redis_removal_results.md#1-측정-조건)). C에서도 같은 인프라·풀·목표 도착률을 사용했으나, 데이터 규모와 부하 생성 기기 조건이 B′와 같았는지는 기록으로 확인되지 않았다.

### 모니터링 지표의 집계 단위

두 자원의 표본 간격이 달라 CloudWatch 조회 결과를 다음처럼 배치했다. 이는 수집한 지표의 집계 방식이며, 서버 오류 로그의 건수 집계와는 별개다.

| 자원 | 실제 반환 표본 | 문서의 집계 단위 | 선택 이유 |
|---|---|---|---|
| RDS | 각 3분 요청률 구간에 60초 표본 3~4개 | **회차 × 요청률** | 같은 5/s·10/s 수준끼리 B′ 기록값과 대조할 수 있고, 구간 안의 범위·평균·최대값을 계산할 표본이 있다. |
| EC2 | CPU·네트워크 표본이 약 5분 간격; 각 3분 요청률 구간에는 0~1개 | **회차 전체** | 요청률별 평균을 낼 표본이 부족하고 5분 표본에 인접 구간의 부하가 섞일 수 있다. 회차 중 자원 변화와 최고값 시각을 확인하는 용도로 묶었다. |

EC2 표의 **구간 평균**은 회차 전체 조회에서 반환된 표본 `Average`들의 산술평균이고, **최대값**은 표본 `Maximum` 중 가장 큰 값이다. 둘 다 1·2·3·5·10/s와 구간 사이 공백이 함께 들어간 회차 전체의 관측값이므로 특정 요청률의 CPU 사용률이나 B′의 5/s·10/s 값과 직접 비교하지 않는다. EC2를 `--period 60`으로 조회해도 실제 반환 간격은 약 5분이었다. RDS도 요청률 경계에 걸친 60초 표본에는 이웃 구간의 시간이 일부 포함될 수 있으며, B′ RDS 값의 집계 조건은 별도로 확인되지 않았다.

10/s 구간의 서버 로그에는 13:47:51부터 `HikariPool-1 - Connection is not available, request timed out after 3000ms`가 반복됐다. 당시 풀은 `total=10, active=10, idle=0`이고 대기 요청은 41건에서 60건 이상으로 증가했다. 근본 예외는 `SQLTransientConnectionException`이며, JDBC 세션 조회·저장, 계좌 비밀번호 확인, OTP 발급, 이체 사전검사 등에서 커넥션 획득에 실패했다. 이는 10/s의 HTTP 500 급증과 직접 연결된다. 커넥션 점유가 길어진 상위 원인은 이 로그만으로 확정하지 않는다.

EC2 그래프에서 13:50 전후의 자원 상승이 관측됐다. CloudWatch API 조회에서 CPU·네트워크 입출력의 최대 표본 시각은 **13:45**, CPU 크레딧 사용량은 **13:46**이었다. EC2 지표가 약 5분 간격으로 반환돼 표본 시각만으로 이를 5/s 부하 단독 값으로 귀속할 수 없다. 기존 운영 분석은 WAS CPU 포화를 풀 대기 초과의 상위 원인으로 확인했다([harness_results.md §3](harness_results.md#3-측정-결과--2026-10-06-세션-풀-보정-후)). 이번 집계 지표만으로 커넥션 점유의 인과관계나 DB 부하·락 대기를 배제할 수는 없다.

운영 `corebank-server` 인스턴스(`i-0c861fe2dc634f3af`, `t3.small`)의 CloudWatch `AWS/EC2` 지표를 조회했다. 실제 측정 시각을 분 단위로 넓혀 CPU·네트워크는 `--period 60`, CPU 크레딧은 `--period 300`으로 요청했다. 그러나 CPU·네트워크 표본은 약 **5분 간격**으로 반환됐다. 요청률별 3분 구간에는 표본이 0~1개만 있어 EC2는 회차 전체로 요약한다. `--period 60`은 조회 요청의 집계 주기이며 60초마다 원본 표본이 있었다는 뜻이 아니다. **반환 표본 범위와 구간 평균은 각 표본의 `Average`, 최대값은 각 표본의 `Maximum` 기준**이므로 최대값이 표본 범위의 상한보다 클 수 있다. 네트워크 바이트·패킷 지표는 해당 표본 기간의 양이며 초당 값이 아니다. 모든 최대값 시각은 KST다.

단위는 ms이고 모두 4회 중앙값이다. 1~5/s는 네 회차 모두 이체 성공률 100%, HTTP 실패·유실 0이며 이체 p95가 매회 1초 미만이었다. 10/s는 네 회차 모두 이체 성공률 66.13~71.98%, HTTP 실패율 20.91~23.59%와 유실 50~53건을 보였다. [기존 판정 기준](harness_results.md#2-측정-결과--2026-10-05-수준별)에 따라 **측정한 수준 중 최고 견딤은 5/s, 10/s는 포화**다. 5/s와 10/s 사이의 포화 시작점은 측정하지 않았다. 네 회차 모두 정합성 불일치 세 항목은 0이었다.

[B′ JDBC 기준선](harness_results.md#8-2-수준별-중앙값--4회-중앙값)과 같은 이체 지표를 비교하면, 5/s p95 중앙값은 B′ 94.8ms → C 153.2ms(**+61.6%**)이고 C의 4회 범위(136.7~171.1ms)는 B′의 4회 범위(84.2~123.8ms)보다 높다. 10/s p95는 6,058.8 → 9,469.9ms(**+56.3%**), 이체 성공률은 75.35 → 68.54%(**−6.81%p**), 유실 중앙값은 23 → 52건이다. 이체 성공률의 분모는 두 측정 모두 이체 API까지 도달한 호출이며, 이체 전 계좌 비밀번호·OTP 단계에서 실패한 반복은 포함하지 않는다. 두 측정 모두 최고 견딤 5/s·10/s 포화라는 등급은 같다. B′와 C는 운영 이미지가 `1709c355`와 `176fe574b6b5d2a1008ce9ce9359753b4d658cdb`로 다르고 릴리스 2의 이체 경로 변경도 함께 포함하므로, 관측한 지연 증가를 PH-49c 단독 효과로 돌릴 수는 없다.

B′의 나머지 견딤 구간 이체 p95 중앙값도 C보다 낮다: **1/s 144.9 → 147.8ms, 2/s 103.8 → 126.1ms, 3/s 85.3 → 126.0ms**다. 이 값은 B′와 C의 각 4회 중앙값 비교이며, 모든 회차가 동일한 폭으로 느려졌다는 뜻은 아니다. 과거 [PH-30 보정 후 측정](harness_results.md#3-측정-결과--2026-10-06-세션-풀-보정-후)의 10/s p95 약 9.85초는 Redis 모드 당시 수치다. [PH-101-② 판정](harness_results.md#8-3-개선-전-기준선--2--3--6-의-10s-값과-비교하지-않는다)은 Redis 제거 후 JDBC 모드의 10/s 지연이 달라졌음을 명시하므로, C의 10/s 비교 기준은 과거 PH-30 수치가 아닌 B′ 6,058.8ms다.

요청률별 RDS 표본에서는 C의 **5/s RDS CPU 구간 평균이 15.3~16.6%**(4회 중앙값 16.35%), **10/s는 16.1~18.2%**(중앙값 17.7%)다. [B′ 회차별 표](ph101_redis_removal_results.md#7-회차별-원자료)의 JDBC 4회는 5/s **12.7~15.0%**(기록값 중앙값 14.15%), 10/s **11.7~14.2%**(기록값 중앙값 13.65%)로 기록돼 있다. 연결 수는 C의 해당 표본이 모두 14개이고 B′는 5/s에 13~14개, 10/s에 13~14개다. **B′ 문서에는 RDS CPU 값이 평균인지 최대인지, 집계 주기와 조회 경계가 무엇인지 적혀 있지 않다.** 따라서 B′ 기록값과 C의 60초 표본 구간 평균을 같은 통계로 간주해 증감률을 계산하지 않는다. C도 각 수준에 3~4개의 표본만 반환됐다. 이 수치만으로 PH-49c 단독 효과나 DB 병목을 판정하지 않는다.

[B′ 정합성 기록](ph101_redis_removal_results.md#5-정합성--여덟-회차-전부-합격)은 JDBC 네 회차를 포함한 전체 여덟 회차에서 원장 짝·잔액·한도 불일치가 모두 0건이고, C도 네 회차의 같은 세 검사가 모두 0건이다. 이는 두 측정에서 검사한 범위의 불일치가 없었다는 비교이며, C의 `limit_usage_mismatches`는 각 회차만이 아닌 당일 누계를 대조한다. DB `ERROR` 건수는 정합성 불일치 건수가 아니다.

B′ 결과는 [PH-101-② 측정 문서](ph101_redis_removal_results.md)에 기록돼 있다. 해당 문서의 Git 작성자는 P1이며, 문서에는 P4가 RDS CloudWatch 원자료를 제공한 것으로 표기돼 있다. 실제 k6 실행자와 부하 생성 노트북의 사양·네트워크는 기록되지 않았다. 부하 생성 기기의 CPU·네트워크 상태, 회선 경로와 k6 버전 차이는 도착률 유지·유실·클라이언트에서 잰 응답시간에 영향을 줄 수 있다. 특히 B′와 C의 지연 차이를 해석할 때 이 조건이 통제됐다고 가정하지 않는다. 첨부 EC2 CloudWatch 그래프는 서버 자원 사용량을 보여주지만 부하 생성 기기의 상태는 보여주지 않는다.

네 회차의 10/s 서버 오류 로그에서 Hikari 메인 풀 `active=10, idle=0`과 3초 커넥션 획득 타임아웃이 반복됐다. 다만 3·4회차 제공 로그는 `head -80`으로 잘린 발췌이고, DB의 `ERROR` 건별 원인과 전체 timeout 건수는 확정하지 못했다. **C의 네 회차 RDS CPU·연결 수·ReadIOPS·WriteIOPS 1분 표본은 요청률별로 확보했다.** 각 요청률 구간의 반환 표본은 3~4개이며 연결 수는 모두 14개였다. 이는 RDS 전체 연결 수이므로 애플리케이션의 Hikari 풀 대기 여부를 대신 보여주지 않는다. 잠금 대기·세션 테이블 조회 및 갱신 지표는 아직 확보되지 않았다. P4가 나머지 RDS 및 기타 모니터링 지표를 확인·제공한다. 첨부 EC2 CloudWatch 화면은 RDS 상태를 보여주지 않는다. 미확보 지표를 받기 전에는 RDS 부하와 풀 고갈의 인과관계를 판정하지 않는다. C는 PH-30 성능 개선 전 현 운영 이미지의 기준선 후보이며, RDS 세부 지표 미확보와 동시 릴리스 변경을 비교의 한계로 둔다.

## RDS 요청률별 모니터링 조회 명령어

AWS CloudShell에서 실행했다. 입력 시각은 UTC이며 각 요청률 구간의 실제 시작·종료 시각이다. 출력의 최대값 시각은 KST로 변환한다. CloudWatch의 60초 표본은 구간 경계에서 일부 겹칠 수 있다.

```bash
DB_ID='corebank-database'
set -o pipefail

while read -r run rate start_at end_at; do
  echo
  echo "### ${run}회차 ${rate}/s RDS 지표"
  echo '| 지표 | 표본 수 | 반환 표본 범위 | 구간 평균 | 최대값 (KST) |'
  echo '|---|---:|---:|---:|---:|'

  for metric in CPUUtilization DatabaseConnections ReadIOPS WriteIOPS; do
    aws cloudwatch get-metric-statistics \
      --namespace AWS/RDS \
      --metric-name "$metric" \
      --dimensions Name=DBInstanceIdentifier,Value="$DB_ID" \
      --start-time "$start_at" \
      --end-time "$end_at" \
      --period 60 \
      --statistics Average Maximum \
      --output json |
    jq -r --arg metric "$metric" '
      .Datapoints as $d |
      if ($d | length) == 0 then
        [$metric, "0", "표본 없음", "—", "—", "—"] | @tsv
      else
        ([$d[].Average] | min) as $low |
        ([$d[].Average] | max) as $high |
        ([$d[].Average] | add / length) as $mean |
        ($d | max_by(.Maximum)) as $peak |
        [
          $metric,
          ($d | length | tostring),
          "\($low * 10 | round / 10)~\($high * 10 | round / 10)",
          "\($mean * 10 | round / 10)",
          "\($peak.Maximum * 10 | round / 10)",
          $peak.Timestamp
        ] | @tsv
      end
    ' |
    while IFS=$'\t' read -r name count range mean peak timestamp; do
      if [[ "$timestamp" == "—" ]]; then
        echo "| $name | $count | $range | $mean | $peak |"
      else
        peak_kst=$(TZ=Asia/Seoul date -d "$timestamp" '+%H:%M')
        echo "| $name | $count | $range | $mean | $peak ($peak_kst) |"
      fi
    done
  done
done <<'WINDOWS'
```

## EC2 전체 회차 모니터링 조회 명령어

AWS CloudShell에서 실행했다. 조회 시각은 UTC이며 출력의 최대값 시각은 KST로 변환한다. CPU·네트워크는 `--period 60`, CPU 크레딧은 `--period 300`으로 요청했다. 실제 CPU·네트워크 반환 시각은 약 5분 간격이었다.

```bash
INSTANCE_ID='i-0c861fe2dc634f3af'
set -o pipefail

for window in \
  '1 2026-10-26T04:26:00Z 2026-10-26T04:51:00Z' \
  '2 2026-10-26T05:49:00Z 2026-10-26T06:07:00Z' \
  '3 2026-10-26T07:09:00Z 2026-10-26T07:27:00Z' \
  '4 2026-10-26T07:49:00Z 2026-10-26T08:07:00Z'
do
  read -r run start_at end_at <<< "$window"

  echo
  echo "### ${run}회차 EC2 지표"
  echo '| 지표 | 반환 표본 범위 | 구간 평균 | 최대값 (KST) |'
  echo '|---|---:|---:|---:|'

  for metric in CPUUtilization NetworkIn NetworkOut NetworkPacketsIn NetworkPacketsOut CPUCreditUsage CPUCreditBalance; do
    case "$metric" in
      CPUCreditUsage|CPUCreditBalance) period=300 ;;
      *) period=60 ;;
    esac

    aws cloudwatch get-metric-statistics \
      --namespace AWS/EC2 \
      --metric-name "$metric" \
      --dimensions Name=InstanceId,Value="$INSTANCE_ID" \
      --start-time "$start_at" \
      --end-time "$end_at" \
      --period "$period" \
      --statistics Average Maximum \
      --output json |
    jq -r --arg metric "$metric" --arg period "$period" '
      .Datapoints as $d |
      if ($d | length) == 0 then
        [$metric + " (" + $period + "초)", "표본 없음", "—", "—", "—"] | @tsv
      else
        ([$d[].Average] | min) as $low |
        ([$d[].Average] | max) as $high |
        ([$d[].Average] | add / length) as $mean |
        ($d | max_by(.Maximum)) as $peak |
        [
          $metric + " (" + $period + "초)",
          "\($low * 10 | round / 10)~\($high * 10 | round / 10)",
          "\($mean * 10 | round / 10)",
          "\($peak.Maximum * 10 | round / 10)",
          $peak.Timestamp
        ] | @tsv
      end
    ' |
    while IFS=$'\t' read -r name range mean peak timestamp; do
      if [[ "$timestamp" == "—" ]]; then
        echo "| $name | $range | $mean | $peak |"
      else
        peak_kst=$(TZ=Asia/Seoul date -d "$timestamp" '+%H:%M')
        echo "| $name | $range | $mean | $peak ($peak_kst) |"
      fi
    done
  done
done
```
