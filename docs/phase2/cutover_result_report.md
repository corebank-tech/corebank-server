### 특이사항 (오류 아님)

- Flyway가 `Using MySQL 8.4 which is newer than the version Flyway has been verified with. The latest verified version of MySQL is 8.1.` 경고를 남긴다. 이번에는 새로 적용한 마이그레이션이 없어 영향이 없다. 앞으로 8.4에서 DDL을 실행하는 마이그레이션이 들어올 때 확인이 필요하다.
- 앱이 뜬 시각(15:35:38)과 대상 그룹에서 healthy를 처음 확인한 시각(15:41:16) 사이에는 약 5분 반의 차이가 있다. 15:41:16은 확인한 시각일 뿐 healthy가 된 시각이 아니다.
- **두 계정 모두 스케줄러가 돈다**(코드 확인). COB 23:30, 일별 이체 00:10, 영업일 00:00, 자동 · 예약이체 재확정(짝수 시 :30 · :45, **멈춘 건만 처리**하므로 대상이 없으면 거래를 만들지 않고 `batch_execution_lock`만 갱신), 정리 작업(매시). 새 환경의 서버 2대는 DB 락으로 한 대만 실행한다.
- 10/28 밤 23:30 COB는 기존 환경에서는 베이스라인(#689)의 세 번째 점(대사 1,219.9초)이고 새 환경(`db.t3.small`)에서는 첫 COB(대사 93.3초)다. 두 값은 환경이 달라 섞어 비교하지 않는다.
- VPN은 **재부팅하면 끊긴다.** `vti1`과 경로는 메모리 설정이고 strongswan은 자동 시작을 꺼 두었다(§4-4에서 영속화).

## 6. 아직 검증하지 못한 것

- DNS 전환 뒤 실제 사용자 요청이 새 환경으로 오는지, 전환 뒤 전파 중 기존 쪽으로 오는 요청. (CNAME과 health 200은 09:41:59에 확인함)
- 터널 2 장애 전환. 터널 1은 10/28 16:23 이후 끊김 기록 없이 유지됐고 재부팅 후 자동 복구도 확인했다(재협상은 자식 SA 번호가 늘어난 것으로 보인다, 추정).
- WAS → VM 정보계 API · 모의 서버. 정보계 API는 VM에서 기동했고(`192.168.0.211:8081`) WAS 보안 그룹 규칙과 환경변수는 #804(PR #805)다. 모의 서버는 #761이다. 새 환경은 `main` 릴리스(11/3) 뒤에 수동으로 갱신한다.
- binlog 레플리카 복제(P2)는 시작 전이다. RDS는 `gtid-mode=ON`(파라미터 그룹 조회로 확인), VM 레플리카 `info-replica-mysql`은 GTID `ON` · `server_id=101`로 준비했고 서비스 DB는 비어 있다. 초기 적재(덤프) 방식과 시점은 미정이다.
- 새 환경 COB는 한 점(93.3초)뿐이라 변동 폭을 모른다.
- 데이터 공백: 기존 환경의 쓰기를 중단하지 않은 채 스냅샷을 떴다. 12:12:51 이후 `transfer` · `ledger_entry`는 0건이지만, 그 밖의 테이블과 DNS 전환 직전까지의 새 거래를 전환 직전에 다시 확인한 기록은 없다(확인 필요).
