# PH-43 COB 운영 베이스라인 측정 결과

> 측정일: 2026-10-26 ~ 10-29 밤(COB 날짜 기준). 작성: 2026-10-29, 10/29 밤 점 추가 2026-10-30. 이슈 #689.
> 새 환경(`db.t3.small`)의 COB 시간은 이 기준선과 섞지 않고 따로 기록한다(§7, PH-38 문서 원칙).

> 운영 COB 전체(영업일 전환, 대사, 만기 감지)의 개선 전 실행 시간을 기록한다.
> PH-45(청크·병렬)를 적용한 뒤 같은 조건으로 다시 재서 비교한다.
> 재측정 시 기존 결과를 지우지 않고 추가한다.

## 0. 왜 별도 실행기 없이 운영 기록으로 재는가

- 처음 계획은 측정 전용 실행기(`CobBaselineRunner`)로 COB를 여러 회차 돌려 재는 것이었다(이슈 #689의 처음 계획).
- 운영에 쌓이는 야간 COB 기록으로 바꾼 이유:
    - 회차 사이에 영업일을 되돌려야 하는데 운영 코드에 되돌리는 포트가 없다. 실행기를 만들면 운영 코드에 영업일을 되돌리는 경로가 새로 생긴다.
    - 만기 감지는 계좌 상태를 바꿔서 첫 회차만 유효하다. COB 시간 대부분은 대사다(1,183.6초 중 만기 감지는 약 1.7초).
    - 컷오버(10/27~28) 측정 금지 기간과 겹쳐 실행기를 돌릴 창이 좁다.
    - P4의 PH-38 실측(10/25)과 운영 첫 COB(10/26)가 약 0.4% 차이로 맞아, 운영 기록을 기준선으로 써도 된다고 판단했다.
- README §3-1은 10/27~28 컷오버 이틀 동안 전 트랙 측정을 금지한다. 이 문서는 그 기간에 새로 측정하지 않았고, 운영 COB가 매일 밤 자동으로 남긴 기록을 나중에 읽기만 했다. P5는 이 읽기를 측정이 아니라 관찰로 본다. 운영 기록을 읽기 전용으로 조회했을 뿐이라 10/27~28 기록도 기준선에 포함하고 별도 예외 결정(D-번호)은 만들지 않는다. 측정 방식 변경(전용 실행기 → 운영 기록)과 이 판단에 이의가 있으면 이슈 #689에서 다룬다.
- 이 문서는 읽기 전용이다. 운영 DB에서 `batch_execution_history`와 `business_date_cutoff`를 조회한 값만 쓴다. 실행기를 돌리지 않았으므로 영업일 · cutoff · 락을 바꾼 것이 없고 되돌릴 것도 없다.

## 1. 측정 방법과 조건

- 기록: 운영 DB의 `batch_execution_history`(스텝별 `started_at`~`ended_at`, `status`)와 `business_date_cutoff`(마감 기준일, 시각)
- 조회: 기존 AWS 계정 Session Manager에서 `mysql:8.4` 클라이언트 임시 컨테이너로 읽기 전용 조회(끝난 뒤 이미지 삭제)
- 환경: 기존 단일 EC2 · 이전 RDS(1차 계정). RDS는 `db.t4g.micro`, 버퍼 풀 128MB(기본값), gp3
- 운영 이미지: 릴리스 2 기준 `176fe574`(10/24 배포)
- 실행 시각: 매 영업일 23:30 시작(`CobScheduler`)
- 데이터 규모(PH-38 측정 시점, 10/25): 계좌 180,011 / `ledger_entry` 6,598,319행
    - COB 날짜별 규모는 조회하지 않았다. 운영 거래로 조금씩 늘어난다. 그래서 기존 환경 값에는 같은 날의 계좌 수 · `ledger_entry` 행 수가 없다(PH-38 시점 한 점뿐이고, 기존 환경은 다시 셀 수 없다). 새 환경에서 쌓는 점에는 같은 날의 두 값을 함께 적는다. `ledger_entry` 전체를 세는 `COUNT(*)`는 테이블을 처음부터 끝까지 읽어 데이터를 메모리에 올리므로 COB 직전에 돌리지 않고 COB가 끝난 뒤(다음 날 아침)에 센다.
- 직전 배포: 릴리스 2(10/24 11:43). #717(COB 재시작과 대사 hard 정책)은 10/26 머지

## 3. PH-38 실측과의 비교

PH-38(P4, 10/25)은 대사 스텝의 `reconcileAll()` 부분만 같은 EC2·RDS에서 3회 쟀다. 불일치 저장과 soft/hard 판정은 포함하지 않는다.

| 회차 | elapsedMs | 분 |
| --- | ---: | ---: |
| 1 | 1,212,571 | 20.2 |
| 2 | 1,186,309 | 19.8 |
| 3 | 1,188,096 | 19.8 |
| 중앙값 | 1,188,096 | 19.8 |

- 운영 첫 COB(10/26)의 대사는 1,183.6초(1,183,588ms)로 PH-38 중앙값(1,188,096ms)과 약 0.4% 차이다.
- 두 측정은 조건이 다르다. PH-38은 측정용 jar를 일회성 컨테이너로 돌린 `reconcileAll()`이고, 이 문서는 운영 COB 스텝의 실제 실행 시간이다.
- PH-38의 해석: `ledger_entry`(1,946MB)가 버퍼 풀(128MB)보다 약 15배 커서 회차마다 디스크를 다시 읽는다. 회당 약 20분은 예상(2~3분)의 약 8배다.
- §7의 정황: 같은 데이터를 다시 읽는 일은 회차 사이가 아니라 COB 한 번 안에서도 일어났을 가능성이 있다(기존 환경은 한 번 도는 동안 인스턴스 전체로 `ledger_entry` 페이지 수의 약 13.6배를 읽었다. 다른 테이블 · 인덱스 · 로그 I/O가 섞인 값이라 확정이 아니다). PH-45 목표로 쓰기 전에 Performance Insights나 InnoDB 지표로 확인한다.

## 4. PH-45 비교 기준

PH-45를 적용한 뒤 다음 조건을 같게 유지해 다시 잰다(PH-38 문서 §3과 같은 원칙).

- 같은 방법: 운영 `batch_execution_history`에서 같은 스텝을 같은 방식으로 읽는다.
- 같은 데이터 규모: 계좌 수와 `ledger_entry` 행 수를 `SELECT COUNT(*)`로 세어 비교한다(`information_schema`의 `table_rows`는 추정치라 쓰지 않는다).
    - 기존 환경 기준선에는 같은 날의 계좌 수 · `ledger_entry` 행 수가 없어(§1) 이 조건은 기존 기준선과 직접 비교해서 검증할 수 없다. 개선 후 점에서 값을 세어 PH-38 시점(10/25: 계좌 180,011 · `ledger_entry` 6,598,319행)과의 차이로 가늠할 수 있을 뿐이다. 새 환경에서 쌓는 점부터는 같은 날 값으로 비교한다(§7).
- **같은 환경.** 개선 후 재측정은 README(S4)와 #689 계획대로 기존 환경(`db.t4g.micro`, 11/6까지 유지)에서 이 기준선과 같은 방법으로 한다. 새 환경(`db.t3.small`)은 사양이 달라 이 값과 섞지 않고 참고값으로 따로 쌓는다(§7).
- 기존 환경은 `main` 배포가 자동으로 가므로 11/3 릴리스에 PH-45 코드가 들어가면 그날부터 밤마다 쌓이는 운영 COB 기록으로 재측정 점을 만들 수 있다. 코드가 그 릴리스에 들어가는지는 PH-45(#692)에 달려 있고 아직 시작 전이다.
- 개선 PR 머지는 기준선 확정 뒤로 한다(순차 → 청크 → 병렬 순서로 한 번에 하나씩).

## 5. 한계와 특이사항

- 점이 하루에 한 개씩 쌓인다. 회차를 임의로 늘려 통계를 많이 쌓을 수 없다. 이 문서는 네 점(월·화·수·목)이다.
- README는 성능 수치에 평균 · p95 · p99를 적으라고 한다. COB는 하루 한 번 도는 배치라 점이 네 개뿐이다. p95 · p99는 선형 보간(numpy `percentile` 기본값)으로 계산했고 표본이 적어 최대값에 가깝다. 꼬리 값으로 읽지 않고 규칙을 맞추는 참고값이다.
- 편차는 네 점으로 낸 값이라 참고용이다. 최소와 최대의 차이는 54.6초(최소 대비 4.6%)다.
- 네 점의 데이터 규모는 운영 거래와 일별 이체 배치로 조금씩 다르다.
- 수요일(10/28) 밤은 컷오버 당일이다. 대사는 1,219.9초로 월(1,183.6)보다 36.3초(3.1%), 화(1,192.7)보다 27.3초(2.3%) 길었고 PH-38 중앙값(1,188.1)보다 31.8초(2.7%) 길다. 원인은 확인하지 못했다(데이터 증가, 같은 시각의 다른 조회나 측정 등은 추정).
- 대사 시간이 월 → 목으로 날마다 늘었다(1,183.6 → 1,192.7 → 1,219.9 → 1,238.2초, 월 대비 +4.6%). 같은 날의 데이터 규모를 세지 않아 원인은 확인하지 못했다(데이터 증가 추정). 개선 후 재측정과 비교할 때는 이 기준선이 날마다 늘 수 있다는 점을 감안해 가장 가까운 날의 점과 데이터 규모(`COUNT(*)`)를 함께 본다.
- 만기 감지는 계좌 상태를 바꾸므로 반복 측정에 적합하지 않다. 운영 기록은 하루 한 번 실제 실행이라 이 문제와 무관하다.
- 대사 외 스텝(영업일 전환 약 0.2초, 만기 감지 약 1초)은 합계에서 차지하는 비율이 작아 개선 효과 비교의 중심은 대사 스텝이다.
- 이 값은 개선 효과를 비교하는 기준선일 뿐 개선 결과가 아니다. 청크·병렬 전환은 시작 전이다.

## 6. 남은 일
1. 새 환경(`db.t3.small`)의 COB 기록을 며칠 더 쌓아 참고값으로 둔다(§7). 하루 한 점이다.
2. 대사 시간이 월 → 목으로 늘어난 원인(데이터 규모 `COUNT(*)` 등)은 필요할 때만 확인한다.
3. PH-45 적용 뒤 기존 환경에서 같은 방법으로 다시 잰다(§4).

## 7. 새 환경(db.t3.small) COB — 기준선과 섞지 않고 따로 기록

- 조회: 10/29 아침 새 계정 서버 `i-09f7f7dd29bc6357a` Session Manager, 같은 쿼리. 새 RDS 복원본(스냅샷 12:12:51)이라 10/26·10/27 행은 기존 환경에서 복사된 기록이다. 새 환경에서 직접 돈 COB는 10/28 · 10/29 두 점이다(10/29 점은 10/30 11:27 조회).
- 새 환경 10/28: 영업일 전환 약 0.06(cutoff 마감 23:30:00.395 → 대사 시작 23:30:00.455), 대사 93.3초(23:30:00.5 → 23:31:33.7, 조회 `sec`는 93), 만기 감지 1.4초, 대사 시작 ~ 만기 끝 약 94.8초, 모두 SUCCESS. cutoff 10/28 CLOSED, 현재 영업일 2026-10-29.
- 같은 날 기존 환경(§2)은 대사 1,219.9초, 합계 약 1,221초였다. 새 환경은 대사가 약 13배(약 92%) 짧다.
- 새 환경 10/29(두 번째 점): 영업일 전환은 조회하지 않음, 대사 82.1초(23:30:01.4 → 23:31:23.5, 조회 `sec`는 82), 만기 감지 1.3초, 대사 시작 ~ 만기 끝 약 83.5초, 모두 SUCCESS. 같은 날 기존 환경(§2)은 대사 1,238.2초라서 새 환경이 약 15배(1,238.2 / 82.1) 짧다.
- 데이터 규모(10/30 11:27 조회, 10/29 밤 COB 뒤): 계좌 180,011, `ledger_entry` 6,624,587행. 10/28 밤 COB 때의 값은 세지 않았다. 사용자 요청과 일별 이체 배치(10/29 · 10/30 00:10)로 행이 바뀌었을 수 있어서 두 날의 규모가 같다고 확인한 것은 아니다. 기존 환경은 같은 날 값을 세지 않았다(§1).
- 두 환경은 스냅샷 이후 거래가 0건이라 같은 데이터에서 돌았다. 그래서 차이는 환경(RDS 사양 등)에서 온 것으로 본다. 원인을 CloudWatch 지표로 확인했다.
- **디스크 읽기(`ReadIOPS`)**
    - 기존 환경(`corebank-database`, `db.t4g.micro`, 5분 평균): COB 23:30 ~ 23:50 내내 1,353 ~ 1,432, 최대 약 1,437에서 평평하게 이어졌다. 5분 평균 × 300초를 더하면 약 169만 번이다(근사).
    - 새 환경(`corebank-rds`, `db.t3.small`, 1분 평균): COB 구간 23:30 ~ 23:32에 분당 평균 452 · 854 · 134다. 분당 평균 × 60초를 더하면 약 8만 6천 번이다(근사).
    - 읽기 횟수는 기존 환경이 약 19.6배이고 소요 시간은 약 13배다.
    - `ledger_entry`(약 1,946MB)를 16KB 페이지로 한 번 읽으면 약 12만 5천 번이다. 새 환경은 그것의 약 0.7배, 기존 환경은 약 13.6배를 읽었다. 기존 환경이 같은 데이터를 여러 번 다시 읽었을 가능성을 보인다. 인스턴스 전체 읽기 횟수 기준이라 다른 테이블 · 인덱스 · 로그 I/O가 섞였을 수 있고 `ledger_entry` 단위의 근거는 없다.
- **데워진 상태였는지**: 새 RDS는 10/28 12:12 스냅샷으로 복원되어 COB(23:30)까지 약 11시간이 있었다. 그 사이 `ReadIOPS`(15분 평균)는 대부분 한 자릿수였고, 14:30대에 평균 약 47(최대 약 491), 19:45대에 평균 약 13이었다. 15분 평균 20을 넘는 구간만 더해도 약 6.9만 번(약 1.1GB)을 읽어서, 일부가 COB 전에 메모리에 올라왔을 가능성이 있다(14:30대는 복원 검증 시간대로 보이며 작업 내용은 확인하지 못했다). 다만 COB 중에도 약 8.6만 번을 읽어서 완전히 데워진 상태는 아니었다. 그래서 93.3초가 평소보다 유리한 조건에서 나온 값인지 불리한 조건인지는 한 점으로 판단하지 않는다.
- 10/29 낮에 레플리카용 전체 덤프(RDS에서 `mysqldump`, 약 4분 33초와 4분 35초 두 번)가 RDS의 모든 테이블을 읽었다. 그 뒤 23:30 COB(82.1초)는 메모리가 일부 데워진 상태였을 가능성이 있다(추정이며 그날의 `ReadIOPS`는 확인하지 않았다).
- **CPU 포화는 관찰되지 않았다.** 기존 환경 `CPUUtilization`은 평균 약 10%(최대 약 23%), `CPUCreditBalance`는 약 288에서 거의 줄지 않았다. 새 환경 CPU는 COB 구간 최대 약 27%였다. 두 DB 모두 2 vCPU라서 한 스레드가 포화하면 약 50%가 보여야 하는데 그렇지 않았다. 다만 인스턴스 수준 지표라 엔진 내부 부하까지 배제한 것은 아니며, 확정하려면 Performance Insights나 Enhanced Monitoring가 필요하다.
- 기존 환경의 읽기가 최대 약 1,437에서 평평하게 이어진 것은 입출력 한도에 걸렸을 가능성을 보인다. 한도가 어디(인스턴스 · 저장소)인지는 확인하지 못했다.
- 확인하지 못한 것: 두 DB의 실제 `innodb_buffer_pool_size`(기존 128MB는 PH-57 문서, 새 약 1.3GB는 파라미터 그룹 계획값). 사양만 바꿔 다시 재는 실험이 아니라서 "버퍼 풀이 작아 같은 페이지를 반복해서 읽었다"는 설명은 정황 증거이고 인과가 증명된 것은 아니다.
- 한계: 새 환경은 두 점(93.3 · 82.1초)뿐이라 변동 폭을 모른다. 기준선으로 쓰려면 세 점 이상 쌓아야 하고, 점이 모이면 이 절에 추가한다(기존 값은 지우지 않는다).
- 이 값(약 94초)은 새 환경의 참고값이다. PH-45 개선 후 재측정은 기존 환경에서 이 문서의 기준선과 비교하므로(§4), 새 환경 값은 기준선으로 쓰지 않고 따로 쌓아 두는 참고 자료다. 팀이 새 환경에서 비교하기로 정하면 그때 세 점 이상 쌓은 뒤 확정한다.
