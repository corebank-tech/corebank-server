# 팀 협업 가이드 (Ground Rule)

DB·API 관련 기술 문서는 `docs/team_db_setup_guide.md`, `docs/api_conventions.md` 등 각 전용 문서를 참고한다. 이 문서는 회의·커뮤니케이션·코드리뷰·Git/PR 등 **팀 운영 컨벤션**만 다룬다.

## 1. 정기 회의

- 정기 회의는 **매주 수요일 오전 10시**.
- 회의는 문서를 **사전 검토 후 의견을 공유·발전시키는 자리**다.
- 회의 전 전달된 기획안 및 CC 자료 숙지 필수.
- 파트별 내부 의견은 **회의 전 기록 형태로 먼저 공유**한다.
- 파트장들은 정기 회의 전 브리핑 + 아젠다를 작성한다.
- 서기는 다음 회차 회의록을 만들고, 다음 서기를 멘션한다.
- 불참 관련
  - 사전에 불참 예정인 경우 팀장에게 미리 알린다.
  - 팀장은 회의록에 1) 사전 안내 불참자, 2) 사전 미안내 불참자를 구분해서 기록한다.

## 2. 일반 커뮤니케이션

- 메시지는 24시간 내로 확인한다.
- 메시지를 이해했으면 👍, 봤으면 👀 이모지로 표시한다.
- 업무 관련 메시지는 **디스코드**, 급하거나 사적인 이야기는 **카톡**으로 구분한다.

## 3. 협업 커뮤니케이션

- 피드백은 노션/피그마 댓글에 기록하고 디스코드로 알린다.
- 문서 확인 후 디스코드에 이모지로 확인 표시를 남긴다.
  - 👀 메시지 확인 완료
  - ✅ 내용 확인, 피드백 반영 완료
- 피드백이 없어도 "확인했습니다", "피드백 없습니다" 등 간단한 응답을 남긴다.

## 4. 툴 사용 원칙

| 툴 | 용도 |
| --- | --- |
| 노션 | 문서화, 피드백 및 논의 내용 기록, 중요 정보(credentials) 공유, 스터디/취업 자료 공유 |
| 피그마 | 디자인 작업, 디자인 피드백, 시각화 자료 생성 및 피드백 |
| 디스코드 | 확인·공지·진행 상황 공유, 노션/피그마 작성 또는 깃허브 작업 후 알림 |

## 5. 코드리뷰 규칙

1. 요청에 실시간으로 응답하거나, 요청하지 않는 커뮤니케이션은 지양한다. 개인의 업무 시간을 존중하며 업무에 몰입할 수 있는 기회를 제공한다.
2. 질문하거나 답할 때 "내가 아는 걸 상대방도 알고 있을 것"이라 가정하지 않는 커뮤니케이션을 지향한다.

### 코드리뷰 로테이션

개인 업무 몰입을 위해 코드리뷰는 역할 로테이션제로 운영한다. 주 단위로 역할을 부여하며, 해당 주의 담당자가 코드 리뷰 전문가로 활동한다.

1. P1 & P4
2. P2 & P5
3. P3 & P6

- PR 리뷰 수행, Approve 시 👍 표시.

### Rn 룰

리뷰어가 코멘트를 강조하는 정도를 표현하는 규칙이다.

| 등급 | 의미 | GitHub 액션 |
| --- | --- | --- |
| R1 | 꼭 반영해주세요 | Request changes |
| R2 | 적극적으로 고려해주세요 | Request changes |
| R3 | 웬만하면 반영해주세요 | Comment |
| R4 | 반영해도 좋고 넘어가도 좋습니다 | Approve |
| R5 | 그냥 사소한 의견입니다 | Approve |
| just ask | 궁금한 점을 물어볼 때 | — |

예시:
> r4;
> 해당 코드에서는 `for` 문 대신 `forEach`를 사용하는 것이 더 좋을 것 같아요.

위는 `r4` 등급 리뷰로, 반영해도 좋고 넘어가도 좋다는 의미다. **R4, R5 등급의 리뷰는 Approve를 하되 추가 의견을 남기는 것**이며, **R1, R2 등급은 Request changes**, **R3 등급은 Comment**를 남긴다.

> 처음에는 `Pn`으로 시작했으나, `docs/api_conventions.md`가 `P1`~`P6`을 **파트 배정**(오류코드 접두어 담당)으로
> 쓰고 있어 같은 기호가 두 뜻으로 읽혔다. 리뷰 등급만 `Rn`(review)으로 분리한다.
> 아래 로테이션의 `P1`~`P6`은 **파트 번호**이므로 그대로 둔다. 과거 PR 코멘트의 `pn` 표기는 소급하지 않는다.

### PR 태그 달기

작업 상황을 서로 알아볼 수 있도록 PR에 태그를 단다.

- 마감 D-Day: 오늘까지 마감해야 하는 중요한 PR
- 마감까지 D-1: 마감 하루 전
- 마감까지 D-2: 마감 이틀 전
- 머지하면 안돼요: 버그가 발견되어 수정이 필요한 PR (동료의 실수를 줄이기 위한 태그)
- 작업 중이에요: 미리 올려두었으나 아직 작업 중인 PR (Draft PR에도 사용)
- 리뷰 남겨주세요!: 리뷰를 요청하는 태그

### Approve 기준

코드 리뷰어 역할 부여자 **2인**의 👍(Approve).

## 6. 협업 컨벤션 (Git & PR)

### 6-1. 브랜치 전략 (Gitflow 기반)

배포용과 개발용 브랜치를 분리하여 관리하며, 개별 작업은 **어느 이슈의 작업인지**를 브랜치명에 드러낸다.

- `main`: 실제 서비스 배포용 브랜치
- `dev`: 다음 출시 버전을 대비하여 개발하는 통합 브랜치
- 작업 브랜치: `타입/{이슈번호}-{설명}` — 타입은 6-3의 커밋 태그와 같다.
  - `feat/338-scheduled-transfer-withdrawal-account-id`
  - `fix/342-account-number-sequence-test-prefix`
  - `chore/352-spotless-format`
- 이슈 없이 진행하는 작업은 번호를 빼고 설명만 쓴다 — `docs/readme-overhaul`
- 일반 작업 PR은 **`dev`를 base로** 연다. `main`은 배포 시점에 `dev`를 병합해서만 갱신한다.
- `dev → main` 릴리스 PR은 `main`을 base로 연다.

### 6-2. PR 및 Issue 제목 규칙

작업 목적과 **어느 도메인인지**를 한눈에 파악할 수 있도록 말머리(태그)를 사용한다.

- 형식: `[타입/도메인] 작업 내용` — 타입은 아래 6-3의 커밋 태그와 같은 소문자를 쓴다.
- 예시:
  - `[feat/scheduled-transfer] 예약이체 목록 응답에 출금계좌 ID 추가`
  - `[fix/account] 상품 채번 행 누락으로 10개 상품 가입이 ACC9001(500) (#342)`
  - `[test/product] REQ-PRDT 인수기준 미커버 6건 테스트 보강`
- 도메인이 없는 전역 변경은 타입만 쓴다 — `[docs] README에 문서 색인 추가`
- `dev → main` 릴리스 PR은 `[RELEASE] dev → main 릴리스 배포`
- 관련 이슈가 있으면 제목 끝에 `(#이슈번호)`를 붙인다.

> GitHub 라벨도 같은 형식(`feat/product`, `fix/account`)으로 붙인다. 라벨이 없으면 새로 만든다.

### 6-3. 커밋 컨벤션

어떤 도메인에서 무슨 작업을 진행했는지 명확하게 작성한다.

- 형식: `태그(도메인명 또는 프로젝트명): 작업 내용`
- 예시:
  - `feat(deposit): 자동 이체 로직 구현`
  - `docs(common): 세팅 가이드라인 수정`

커밋 태그(Type) 목록:

| 태그 (Type) | 설명 및 작업 내용 |
| --- | --- |
| `feat` | 새로운 기능 구현 |
| `fix` | 버그, 에러, 형식 오류 수정 |
| `refactor` | 코드 개선, 폴더 구조 변경 (기능의 변화는 없음) |
| `docs` | 문서 작업 (`.md` 파일 수정, 주석 추가 등) |
| `test` | 테스트 코드 작성 및 수정 |
| `chore` | 자잘한 업무, 빌드 설정, 패키지 매니저 설정, `git init` 등 |


- 로컬 브랜치 작업 전 꼭 원격과 동기화(`git pull`)한다.
- 컨벤션은 Spring Boot 기본 스타일에 레이어드(Controller-Service-Repository) 구조를 준수하며, 도메인형 구조(DDD) + 헥사고날 아키텍처를 지향한다.
